# 工单

**工单**是一张客户支持单据。每个客户报告的问题、疑问或功能请求都以工单的形式存在，以便团队能够一致地路由、处理和解决它。

## 7 种工单状态

| 状态 | 含义 |
| --- | --- |
| ⚪ **New** | 刚收到，尚未分配给客服 *(默认)* |
| 🟠 **In Progress** | 客服正在积极处理 |
| 🟡 **Waiting on Customer** | 等待客户回复 |
| 🔵 **Waiting on Support** | 等待另一团队（工程、财务等） |
| 🔴 **Escalated** | 上交给资深客服或管理层 |
| 🟢 **Resolved** | 修复已交付，等待客户确认 |
| 🟢 **Closed** | 工单已完成 |

一个典型的快速解决工单：**New → In Progress → Resolved → Closed**。
一个典型的卡住工单：**New → In Progress → Waiting on Customer → In Progress → Resolved → Closed**。

## 4 个优先级级别

| 优先级 | SLA 目标（SMB → Strategic） | 使用场景 |
| --- | --- | --- |
| 🔵 **Low** | 7 天 → 4 天 | 外观问题、低影响的疑问 *(默认)* |
| 🟠 **Medium** | 2 天 → 24 小时 | 标准问题，工作继续 |
| 🔴 **High** | 8 小时 → 6 小时 | 影响显著，客户不满 |
| 🔴 **Critical** | 4 小时，各层级一致 | 生产中断，需要立即响应 |

**现在四行背后都有一只时钟。** `case_sla_defaults` 钩子按一张**优先级 × 客户层级矩阵**给每一张工单标记 `sla_due_date`，Strategic 与 Enterprise 客户的目标更紧，每小时一轮的违约扫描在四个优先级上都生效 —— 完整表格与机制详见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)。这些是**日历**小时：本应用没有营业时间日历，所以夜间、周末与节假日一律照算进目标里。

当工单被设为 **Critical** 时，工单升级流程通过站内消息 + 邮件提醒**工单负责人**——它的收件人列表只有 `{caseRecord.owner_id}` 这一项，本应用中不存在 `support_manager@example.com` 这个收件人。**High** 工单永远不会被自动升级，无论账户是什么：没有任何升级条件会读取账户，要升级它靠的是手动的 **Escalate Case** 按钮。

## 工单类型

| 类型 | 用于 |
| --- | --- |
| **Question** | 操作类咨询 |
| **Problem** | 某项功能无法使用 |
| **Feature Request** | 客户请求新功能 |
| **Bug** | 已确认的软件缺陷 |

## 工单来源

工单的来源：**Email · Phone · Web · Chat · Social Media**。

这驱动报表（哪些渠道产生的工单量最大），并在工单从来访渠道创建时自动填充（例如，邮件转工单集成会将来源设为 Email）。

## 工单记录存储的内容

`crm_case` 一共声明 **25 个字段**（`src/objects/case.object.ts`），而把它们组织起来的东西有三样：对象自己的字段分组、工单详情界面、工单表单。三者里只有第一样是六个分区，而且两两都不一致——所以要紧的是分清你看的是哪一样。

### 对象自己的字段分组

下面这六个名字都是真的，但没有一个是界面：它们是 `crm_case` 的**字段分组**（`fieldGroups`），是对象给自己字段定的归档方案。详情界面和表单都不渲染它们——两者各自声明了自己的分区，见下文。不过，这确实是唯一一份把对象全部字段都交代到的清单：

| 字段分组 | 字段 |
| --- | --- |
| **Case Information** | 工单编号、主题、显示名称、描述、账户、联系人、状态、类型 |
| **Origin & Routing** | 负责人、来源 |
| **SLA & Priority** | 优先级、创建日期、关闭日期、首次响应日期、解决时间（小时）、SLA 截止日期、SLA Violated |
| **Resolution** | 解决方案、解决所用文章 |
| **Escalation** *(默认折叠)* | 升级标记、升级日期、升级原因 |
| **System** *(默认折叠)* | 内部备注、关闭标记 |

这六行里有五行，本页原先写的是另一个样子，而且差的不是细枝末节：**状态**与**类型**在 *Case Information* 里，不在 *SLA & Priority*；**关闭日期**在 *SLA & Priority* 里，不在 *Resolution*；*System* 装的是**内部备注**与**关闭标记**——工单上根本没有名为「审计跟踪」的字段，时间戳则待在 *SLA & Priority* 里。六行里只有 *Escalation* 原样就是对的。**优先级排序**——把 *我的待处理工单* 排出先后的那个隐藏排序键——则不属于任何一个分组。

### 详情界面

工单详情页（`src/pages/case_detail.page.ts`）的 **Details** 页签声明了**三个**分区，装着 25 个字段中的 **16** 个：

| 分区 | 字段 |
| --- | --- |
| **Case Information** | 工单编号、主题、账户、联系人、类型、来源 |
| **Status & SLA** | 状态、优先级、负责人、升级标记、升级原因、SLA 截止日期、SLA Violated、解决时间（小时） |
| **Description** *(可折叠)* | 描述、解决方案 |

三个分区里只有 *Description* 是可折叠的，而且没有任何地方把它标成折叠态，所以它和其余两个一样是展开着的。

### 表单

工单表单（`src/views/case.view.ts`）是分页签的，自己另有三个分区——名字不同、内容也不同，覆盖 25 个字段中的 20 个：

| 表单页签 | 字段 |
| --- | --- |
| **Case** | 工单编号、主题、账户、联系人、状态、优先级、来源、负责人、描述 |
| **SLA** | 创建日期、首次响应日期、SLA 截止日期、解决时间（小时）、SLA Violated、升级标记、升级原因 |
| **Resolution** | 解决方案、内部备注、关闭日期、关闭标记 |

这两者并不是同一个界面换了层皮。**类型**只在详情界面上有——表单的任何一个页签里都没有它。`/forms/support` 上那张公开支持表单又是第三种排布：一个分区、四个字段（主题、描述、类型、优先级）。

## 自动发生的事

- **认领时写入的负责人**——一张**没有负责人**的工单，只要有人把它转到 *In Progress*、*Waiting on Customer* 或 *Waiting on Support*，就会在同一次保存里把做这个动作的人标记为它的负责人。已经有负责人的工单不受影响；自动化写入或种子写入也永远不构成认领——它们让工单保持无主，继续留在 **未分派 — 待分诊** 标签页里被看见。见下文*认领待分流的工单*。
- **首次响应日期**（`first_response_date`）——在工单上记录一次**已经发生过**的互动时才打戳，而且只打第一次。它唯一的写入方是 `event_activity_bubble` 钩子（`src/objects/event.hook.ts`）：任何一条以该工单为关联记录、状态到达 **Held** 的 `crm_event` 都会触发它——所以 **Log a Call** 与 **Log a Meeting** 会打戳，用别的方式录入的互动（包括直接在工单的活动列表上录入）同样会。它写之前先把库里存着的值读回来，所以第二次互动不会覆盖第一次。有两件事被刻意排除在「首次响应」之外：**状态变更**（客服可以把工单转到 *In Progress* 然后自己查一小时，客户什么都没听到），以及仅仅**预约**了一场会议——那是 `planned` 而不是 held。所以一张全程靠评论处理的工单，这个字段始终是空的。
- **关闭标记**——状态变为 *Closed* 时自动设置。
- **关闭日期**——状态变为 *Closed* 时标记为 NOW。
- **解决时间（小时）**——按 *Created date* 与 *Closed date* 之间的差值计算。
- **SLA 截止日期**——给**每一张**优先级可识别的工单标记。`case_sla_defaults` 拿工单的优先级去和其账户的**客户层级**对查，把该字段填成 *当前时间 + 相应的日历小时数*；建单时打戳，此后只要该字段仍为空也会打。它只写一次、从不重算，有人手工填过的日期也永远不会被覆盖。
- **SLA Violated**（`is_sla_violated`）——不存在名为 *SLA Breached?* 的字段。每小时一次的 `case_sla_monitor` 扫描把它置真，选中的是**仍未结**（状态既不是 *Resolved* 也不是 *Closed*）且 **SLA 截止日期** 已经过去的工单。它从不拿解决时间去比对目标，所以没有截止日期的工单永远不是候选，晚解决但赶在下一次扫描前解决的工单也永远不会被标记。
- **账户的最后活动日期**——工单更新时刷新为今天。

## 内置规则

- **已关闭工单必须有解决方案**——解决方案字段为空时无法关闭工单。
- **升级工单必须有升级原因**——解释为何引入了资深客服。
- **状态推进是建议，不是闸门**——转换表写的是 *New* 之后可以去 *In Progress*、*Waiting on Customer*、*Escalated* 或 *Closed*，所以直接跳到 *Resolved* 是走出了这张表。但这拦不下保存：工单照样以 *Resolved* 落库，引擎只在服务端日志里写一行 `WARN Validation rule 'case_status_progression' (warning): Invalid status transition`。与上面两条不同——那两条是 `error` 级、确实会拒绝保存——这一条只做提示。转换表到底有什么用，见[状态机](/zh-Hans/docs/administration/state-machines)。

## 流程与对象钩子自动化

- **紧急时通知**——当优先级被设为 Critical 时，工单升级流程的 `notify` 节点发出站内消息 + 邮件，只发给**工单负责人一人**：收件人列表只有 `{caseRecord.owner_id}` 这一项。本应用中不存在 `support_manager@example.com` 这个收件人。
- **升级时通知**——当状态变更为 *Escalated* 时，不会发出任何邮件：`escalation_team@example.com` 在本应用中根本不存在，也不存在「升级团队」这样一个收件目标。状态转为已升级真正触发的是 `case_status_side_effects` 钩子，它开出的是一条**次日到期、优先级为紧急、归账户负责人的跟进任务**——且仅限有关联账户的工单，因为该任务是挂在那个账户上的。
- **计算解决时间**——关闭时自动进行。
- **自动设置关闭日期和标记**——状态变更时。

## 工单升级

[工单升级流程](/zh-Hans/docs/service/sla-and-escalation)只在一个条件下运行：**工单处于 Critical 优先级**。不存在 High 优先级这一分支，也没有任何升级条件会读取账户——Customer 的 High 工单与潜在客户的 High 工单待遇完全相同：两者都不会自行升级，要升级它靠的是手动的 **Escalate Case** 按钮。

它会执行：

1. **标记**为已升级，标记升级日期。
2. **设置状态**为 *Escalated*。
3. **移交工单**——归属转给当前未结工单最少的服务经理。
4. **通知工单负责人**——通过站内消息与邮件送达，带上工单编号和优先级。

移交的对象是一个**岗位池**，而不是向上的汇报链。本应用的岗位是扁平的，解析不出「负责人的经理」；工单交给持有 **Service Manager** 岗位、且未结（既非 *Resolved* 也非 *Closed*）工单最少的那个人，连续多次升级因此会自然分摊到整个团队。三种情况下它刻意什么都不做：**无人持有该岗位**（全新安装即是此状态），工单保留原负责人，升级照常完成；工单**已经归池内成员所有**，则留在正在处理它的那位经理手里；或者同一次写入**自己指定了负责人**，那个指定优先于岗位池的计算。

状态转为 *Escalated* 随后会触发 `case_status_side_effects` 钩子，由它开出一条**次日到期、优先级为紧急、归账户负责人的跟进任务**——且仅限有关联账户的工单，因为该任务是挂在那个账户上的。

以下两件事这份清单刻意不写，因为升级并不做：

- **通知只发给移交前的那位工单负责人。** 收件人列表只有 `{caseRecord.owner_id}` 这一项，且它是在移交之前读取的——因此通知送达的正是被移交走工单的那位客服，这本就是它的用意。不含其经理，也不含更广泛的 `support-team@example.com` 列表，这个地址在本应用中根本不存在。
- **跟进任务不落在原客服身上。** 它归**账户负责人**所有，既不归正在处理该工单的客服，也不归某位资深客服。流程里根本没有任务节点——跟进任务由钩子独家创建，因此每次升级恰好一条。

完整机制参见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)。

## 认领待分流的工单

有些工单到达时**完全没有负责人**——最常见的一种：没有人担任服务坐席时，Web 提交的工单就这样落了下来。它们停在 **未分派 — 待分诊** 标签页里，在有人接手之前，每一位客服都能看到并编辑它们。

**接手一张工单靠的是改状态，不是改负责人。** 把一张无主工单转到 **In Progress**、**Waiting on Customer** 或 **Waiting on Support**，它就归你了：应用会在同一次保存里把你标记为它的负责人。随后这张工单离开 **未分派 — 待分诊**（该标签页只列无主工单），出现在 **我的待处理工单** 里。

除此之外没有任何操作构成认领，每一项排除都是刻意的：

| 把无主工单转到 | 归属会怎样 |
| --- | --- |
| **New** | 什么都不会发生——待分流的行本来就处在这个状态，这根本算不上一次转移 |
| **Escalated** | 与你无关：这个转换属于升级移交，工单会交给未结工单最少的那位**服务经理**（见上文*工单升级*） |
| **Resolved**、**Closed** | 什么都不会发生——把工单做完不等于把它接过来。你完全可以把一张无主工单直接从待分流状态解决掉；它仍然无主，记录上留下的只是你这位最后更新人 |

> **你无法靠编辑负责人来认领工单，也无法替别人认领。** 负责人不是客服能在工单上设置的字段——带着这个字段的保存一律被拒绝，无论填的是谁，填你自己也一样——所以改状态是认领唯一的写法，而它能写入的名字只有你自己。对已经有负责人的工单，这个动作同样是空转：改它的状态，变的就只有状态。真正需要易主的工单要找管理员或服务经理，见[共享与安全](/zh-Hans/docs/administration/sharing-and-security)。

## 共享——谁可以看到哪个工单

- 默认情况下，工单是**私有的**——只有所有者可见。岗位是扁平的，**什么都不会上卷**，没有哪位经理因为“在所有者之上”就能看到某个工单。
- **紧急未结工单**由两条规则自动共享，一个层级一条：*Escalated Cases Sharing* 把读/写授予 `service_manager`，*Escalated Cases — Service Director* 把读授予 `service_director`。两个层级都被显式点名，因为谁也不会从对方那里继承。
- **无主的未结工单**由 *Unassigned Cases — Triage* 共享给每一位 `service_agent`，读 + 编辑——这就是 **未分派 — 待分诊** 标签页背后的那条授权。它的有效期恰好是「这张工单没有负责人，且既不是 *Resolved* 也不是 *Closed*」这段时间，而认领正是终结它的那个动作：从那一刻起，你以负责人的身份、用最普通的方式持有这张工单。

## 字段级安全

- **SLA Violated**（`is_sla_violated`）和**解决时间**对客服是**只读的**——这些是自动计算的，无法手动篡改。锁是字段级安全给的：Service Agent 配置文件把这两个字段掩码为可读不可编辑。

## 标准列表视图

`crm_case` 一共发布 **8 个**视图（`src/views/case.view.ts`），工单列表把它们做成页签，每个页签用的就是视图自己的名字：

| 视图 | 展示什么 |
| --- | --- |
| **全部工单** | 全部工单，先按优先级、再按 SLA 截止日期排序，行底色键在**优先级**上 |
| **服务流转** | 未结工单的看板，按状态分列 |
| **SLA 日历** | 按 **SLA 截止日期** 把工单铺在日历上——现在每张工单都带截止日期，所以它显示的是整个未结积压 |
| **工单时间线** | 工单按「创建 → 关闭」铺在时间轴上，按负责人分组 |
| **已升级工单** | `is_escalated` 为真 |
| **未分派 — 待分诊** | 完全没有负责人的未结工单，先按紧急程度、再按最近的截止日期——没有人担任服务坐席时，Web 提交的工单就落在这里 |
| **⏰ SLA 风险预警** | 未结的 **High 与 Critical** 工单，截止日期最近的排在前面 |
| **我的待处理工单** | 你名下状态既不是 *Resolved* 也不是 *Closed* 的工单 |

本节原先列的七个名字里，有六个根本不是视图：

- **Critical Cases** 是指标磁贴，不是列表。*Breached SLA* 这个名字本应用根本没有：按违约计数的是 **SLA Violations** 磁贴。[服务概览](/zh-Hans/docs/analytics/dashboards)（Service Overview；该仪表盘自身的标题是 **Customer Service**）上有 **Critical Cases**（未结且 Critical）和 **SLA Violations**（`is_sla_violated` 为真）两个磁贴；本应用里没有任何一个列表视图按违约过滤。真要有一份能逐条处理的清单，用 **已升级工单**——SLA 扫描会把它标记的每一条都升级，所以每次违约都会落到那里。
- **Service Board** 不是本应用里任何东西的名字。看板叫 **服务流转**，页签上写的也是这个名字。
- **Cases Due Today**、**Recently Closed** 与 **By Account** 以任何形式都不存在：没有任何视图按「截止日期 = 今天」或 `closed_date` 过滤，`crm_case` 上也没有任何分组视图。

## 工单详情布局

打开一个工单时，你会看到：

- **页眉**——标题是工单编号与主题（`{case_number} · {subject}`），副标题是**账户**，此外只有一个图标、面包屑和几个动作按钮。页眉就这些：上面**没有状态徽章、没有优先级徽章，也没有 SLA 倒计时**。本应用里没有任何东西会计算剩余时间或超时时长——页眉上没有，工单上别的任何地方也没有——所以根本没有倒计时可渲染。那两个 SLA 字段实际做什么，见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)。
- **关键信息**——紧贴页眉下方的摘要栏，也是**状态**与**优先级**真正待的地方：它们在这里是普通字段而不是徽章，与 **SLA 截止日期**、**SLA Violated**、**负责人**、**账户**并排。
- **状态路径**——一个 Salesforce 风格的水平流程，显示 New → In Progress → Waiting on Customer → Escalated → Resolved → Closed，让客服一眼就能看出工单的进展和下一站。
- **客户面板**——不存在这样一个面板。这一页（`src/pages/case_detail.page.ts`）只声明了两个区域，再无其他：一个页眉区域装着上面那三个组件，一个主区域装着下面那组页签。客户上下文就散落在这两处：**账户**在页面上出现了三次——页眉副标题、关键信息摘要栏，以及 *Details* 页签里的一个字段；**主要联系人**则是同一页签 *Case Information* 分区里的一个字段。**合同等级**与**本月未结工单**在工单的任何界面上都没有承载：工单不关联任何合同，`crm_contract` 上也没有等级字段；最接近的真实字段是账户记录上的 **Customer Tier**（中文界面作「客户分层」），而这一页并不展示它。本应用里也没有任何东西按月统计一个客户的工单数。
- **三个标签页：**
  - **Details**——完整的工单描述和解决方案是有的，但不是「所有元数据字段」：是对象 **25** 个字段里的 **16** 个，分在上文《工单记录存储的内容》列出的那三个分区里。不在这个页签上的九个是：**首次响应日期**、**创建日期**、**关闭日期**、**升级日期**、**关闭标记**、**内部备注**、**优先级排序**、**显示名称**、**解决所用文章**。其中五个在工单表单上；剩下四个在工单的任何界面上都没有——**升级日期**由升级流程写入，但哪里都不展示，**优先级排序**是 *我的待处理工单* 背后的排序键，**显示名称**是对象的 `nameField`，一个在任何地方引用工单时给它命名的标题公式，而不是你在这里能读到的字段，**解决所用文章**则是被知识库转移率指标读取，而不是被某个界面读取。这里面最该知道的缺席者是**首次响应日期**：上文《自动发生的事》整整一段讲清了它是怎么打戳的，而你读不到它的地方正是这个页签。
  - **Related**——只有一个列表，不是四个：**Open Tasks**——通过**关联工单**（`related_to_case`）指向本工单的 `crm_task` 记录，过滤掉状态为 *Completed* 的，一次最多十条。整个页签就这些。没有附件列表：工单是可以挂附件的（对象上开了这项能力），但这一页没有任何组件把它们列出来。没有关联商机列表，因为 `crm_case` 与商机之间双向都不存在任何关系字段。也没有里程碑列表——工单的三个里程碑（*escalated*、*resolved*、*closed*）是以条目形式发到 **Activity** 时间线上的，不是在这里当记录列出来。
  - **Activity**——统一的时间线（下文详述）。
- **AI 参考栏**——这一页上不存在任何形式的参考栏。主区域里除了那组页签什么都没有，页面上也没有任何一个组件是 AI 驱动的。服务技能本身是真实存在的——见下文《AI Copilot 如何提供帮助》一节——但你是靠提问去用它们，而不是靠工单旁边的一块面板。本应用里唯一真正渲染出来的参考栏在商机详情页上，而且即便在那里，它列的也是关联记录（报价、产品、未完成任务），不是什么建议。

### 活动时间线

Activity 标签页是工单上发生过什么的唯一可信来源。它将四个数据流合并为一个按时间排序的信息流：

| 数据流 | 来自哪里 | 你会看到什么 |
|--------|---------------------|------------------|
| **评论** | 队友或客户在工单上发布 | 主题式讨论、@提及、内部/外部可见性 |
| **已记录通话** | "Log a Call" 操作——存储为类型为 *completed* 的 `sys_activity` | 通话主题、时长、结果、记录人 |
| **外发邮件** | "Send Email" 操作——通过 `sys_email` 排队 | 主题、收件人、投递状态（queued / sent / bounced） |
| **字段变更** | 工单上每个被跟踪字段的每次变更 | 改了什么、谁改的、何时、变更前 → 变更后 |

你无需配置任何这些内容——每个 CRM 对象都自带 `trackHistory: true`，平台的 feeds 引擎会自动将评论、活动和审计日志接入同一时间线。

> 提示——如果你只想看讨论，使用 Activity 标签页顶部的筛选下拉菜单；你也可以从那里订阅该工单，这样任何未来的发布都会在铃铛中提醒你。

## AI Copilot 如何提供帮助

[服务技能](/zh-Hans/docs/ai-copilot/service-copilot) 会在任何工单上自动激活。你可以问：

- *"分流这个工单"*——工单分流技能根据主题和描述推荐优先级。
- *"建议一个解决方案"*——没有哪个技能能端到端做完这件事。**工单分流**只声明了 `describe_object` 与 `get_record` 两个工具，完全没有检索类工具，因此它什么都不检索。请向 **Customer 360°** 要按工单分类或标签匹配出来的已发布[知识文章](/zh-Hans/docs/service/knowledge-base)，再向**邮件撰写**要客户回复——草稿的依据是联系人与账户记录，而不是那些文章，需要援引哪一篇请自己贴进去。
- *"Customer 360"*——拉取完整的账户上下文（未结商机、过往工单、合同等级）。

如果 Copilot 判断优先级为 *Critical*，它还会建议立即升级并起草内部通知消息。

## 给服务客服的提示

- ✅ **及时分流来访工单**——但要知道，应用里没有任何东西在盯着这件事。不存在可供违反的首次响应目标：**First Response Date** 只是记录在工单上，从不与任何东西比对，`case_metrics` 里没有首次响应这个度量，所以没有任何报表或仪表盘磁贴报它，也没有任何流程为它告警。这里的「及时」是团队自己的承诺，不是应用跑着的一只时钟。
- ✅ **当你确实被阻塞时使用 "Waiting on Customer"**——但它**不会停止 SLA 计时**，任何配置下都不会。`sla_due_date` 只写一次，从不重算；每小时的 `case_sla_monitor` 扫描收的是状态既不是 *Resolved* 也不是 *Closed* 的未结工单，而 *Waiting on Customer* 不在这份排除名单上。一张挂在客户那边的工单照样把时钟走完，照样被标记 **SLA Violated** 并按时升级——四个优先级都是如此。
- ✅ **始终写下解决方案**——这是强制的，但也会为未来的工单提供知识库素材。
- ✅ **关联一个任务**——当工单需要未来跟进时（例如"7 天后验证修复是否有效"）。
- ❌ 不要在未确认修复有效之前关闭工单。

## 给服务经理的提示

- ✅ 没有 *Breached SLA* 这个视图可看，也没有什么红色徽章——工单列表上唯一的颜色规则是 *全部工单* 的行底色，它键在**优先级**上，不是违约。每天改看 **已升级工单**，数量则看服务概览上的 **SLA Violations** 磁贴。
- ✅ 用看板开每日站会——它叫 **服务流转**，在工单列表的 **服务流转** 页签上。
- ✅ 辅导那些 **Resolution Time** 趋势上升的客服——但这个趋势只能从工单本身读出来。不存在什么客服排行榜：`case_metrics` 这个数据集（服务侧每一张报表和每一个仪表盘部件都建在它上面）只声明了 Status、Priority、Origin、Type、Created、Resolving Article 六个维度，所以分析层里没有任何东西能按客服分组。

## 给管理员的提示

- 按优先级与客户层级划分的 SLA 目标存储在工单对象的自动化中。要更改它们，请同时编辑 `src/objects/_case-sla.ts` 与 `src/objects/case.hook.ts` 里 `case_sla_defaults` 内部那张表——两处都要改，因为沙箱化的钩子体无法 import 常量——参见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)与 [管理 › 自动化](/zh-Hans/docs/administration/automation)。
- `escalation_team@example.com` 和 `support_manager@example.com` 都没有在任何地方配置过——这两个地址在本应用中根本不存在。真实存在的收件人列表只有一处：工单升级流程 `notify` 节点的 `recipients: ['{caseRecord.owner_id}']`，即工单负责人一人；它在 `src/flows/case-escalation.flow.ts` 里改，不是 Setup 界面上的配置项。
- 邮件转工单接入（从来访邮件自动创建工单）需要邮件插件——参见 [定制 › 扩展对象](/zh-Hans/docs/customization/extending-objects)。
