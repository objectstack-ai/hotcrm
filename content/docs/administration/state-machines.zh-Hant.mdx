# 狀態機

某些物件有嚴格的 **生命週期** —— 潛在客戶從 *New* 推進到 *Working* 再到 *Qualified*，絕不會倒退回 *New*。狀態機把這條路線 **宣告** 出來，但並不強制執行：本應用的五條狀態機全是 **警告** 級，使用者把記錄挪出這條路線，**儲存照樣通過** —— 詳見下文《宣告出來的路線是建議，不是閘門》。

## 狀態機在哪裡適用

HotCRM 在 **五個** 物件上使用狀態機：

- **潛在客戶** —— *New → Working → Qualified → Converted / Disqualified*
- **商機** —— 經過 7 個階段 *Prospecting → Qualification → Proposal → Negotiation → Closed Won / Closed Lost / Closed Without Decision*
- **案例** —— *New → In Progress → Resolved → Closed*；*Waiting on Customer* 與 *Waiting on Support* 用來把未結案的案例掛起，*Escalated* 從任何未解決的狀態都能進入，*Resolved* 與 *Closed* 都可以重新開啟回 *In Progress*
- **合約** —— *Draft → In Approval → Activated → Expired*；*In Approval* 可以把文件退回 *Draft*，三種在途狀態都能直接走到 *Terminated*，*Expired* 與 *Terminated* 都是終點
- **報價** —— *Draft → In Review → Presented → Accepted*；*In Review* 可以退回 *Draft*，*Rejected* 會回到 *Draft* 重來，*Expired* 可從 *Draft*、*In Review*、*Presented* 進入，*Accepted* 與 *Expired* 都是終點

五者的宣告方式完全相同 —— 都是物件上一條具名的 `state_machine` 驗證規則，作用於該物件的生命週期欄位（`status`，商機上是 `stage`）。案例、合約、報價用的不是比潛在客戶和商機更輕的機制，就是同一套機制。頂層 `stateMachines` 鍵在平台 7.7 被移除後，所有狀態機都遷到了各自的物件上。

**宣告出來的路線是建議，不是閘門。** 五條規則都是 **警告** 級：走出轉換表的狀態變更只會寫進伺服器日誌——比如 *「Invalid contract status transition」*——而 **儲存照樣通過**。記錄在 **新建** 時也根本不受檢查：規則拿新值與前一個值比對，因此只在更新時執行，直接匯入到後期狀態的記錄不會被碰。轉換表給你的是一條宣告出來、機器可讀的路線，供自動化、報表和 Copilot 依賴——而不是給欄位上鎖。

**行銷活動沒有狀態機，這是有意的。** 行銷活動的狀態是描述性的（*Planning / In Progress / Completed / Aborted*），不是受控的生命週期；行銷活動成員、活動、知識文章和任務的狀態欄位同理。給它們中任何一個加轉換表，只會在正常編輯時報警告，教使用者忽略警告。

## 潛在客戶狀態機

```
        ┌──────────────┐
        │     New      │
        └──────┬───────┘
               │ Begin working
               ▼
        ┌──────────────┐
        │   Working    │
        └──┬────────┬──┘
   Disqual │        │ Qualify
           ▼        ▼
   ┌────────────┐  ┌────────────┐
   │Disqualified│  │ Qualified  │
   └────────────┘  └─────┬──────┘
                         │ Convert
                         ▼
                  ┌────────────┐
                  │ Converted  │
                  └────────────┘
```

**允許的轉換**：

| 從 | 到 | 觸發 |
| --- | --- | --- |
| New | Working | 手動（「Begin Working」）或首次活動時自動更新 |
| Working | Qualified | 手動（「Mark Qualified」） |
| Working | Disqualified | 手動（「Disqualify」），需填寫原因 |
| Qualified | Converted | 轉化精靈（建立客戶/聯絡人/商機） |
| Disqualified | （終態） | — |
| Converted | （終態） | — |

**不允許**：從 *New* 直接跳到 *Converted*；將 *Converted* 退回到 *Working*。

## 商機狀態機

```
Prospecting → Qualification → Proposal → Negotiation
                                              │
                            ┌─────────────────┼────────────────────────┐
                            ▼                 ▼                        ▼
                        Closed Won      Closed Lost        Closed Without Decision
```

**規則**：

- 你可以自由地 **向前** 經過 *Prospecting → Qualification → Proposal → Negotiation*。
- 你可以 **向後** 移動（例如從 *Negotiation* 退回 *Proposal*）—— 有時交易會滑落。
- 從任何開放階段，你都可以移動到三個 **已關閉** 階段之一。
- 一旦 *Closed*，商機的金額/階段編輯就被 **鎖定**（除非重新開啟 —— 僅限管理員）。

系統還強制執行：

- 移動到 *Proposal* 之前 **必須填寫關閉日期**。
- 移動到 *Negotiation* 之前 **必須填寫金額**。
- 進入 *Closed Lost* 或 *Closed Won* 時 **必須填寫贏單/丟單原因**。
- 如果金額 > $500K 且尚未授予折扣審批，進入 *Closed Won* **可能需要審批**。

## 狀態機給你的是什麼

不是攔截。本節原先列為「不會發生」的幾件事，在轉換表宣告之後照樣發生：代表仍可能不小心把潛在客戶標記為 *Converted*，商機仍可以從 *Prospecting* 直接跳到 *Closed Won*，記錄仍會跳過階段。這些寫入各自只在伺服器日誌裡留下一條警告，然後照樣落庫。所以漏斗報表並不會因為存在一張表就 **反映現實** —— 它報的是記錄實際走過的那些階段。

轉換表真正給你的，就是這條路線本身 —— **寫在一個機器能讀的地方**：

- **生命週期只有一處定義。** 審閱者、報表作者、為本應用撰寫中繼資料的 AI，都能直接從物件上讀到設計意圖中的路線，而不必從每一條寫這個欄位的流程和鉤子裡去反推。
- **非法的移動會被報出來，而不是無聲無息。** 移動照樣落庫，但引擎會在日誌裡點名 —— *「Invalid opportunity stage transition」*，並帶上規則自己的名字 —— 所以一次糟糕的匯入或一個行為異常的整合，事後是能被找出來的。走在表內的移動一條日誌都不記，這正是那些警告值得一讀的原因。
- **給自動化與報表一個可以指向的基準。** 流程條件、報表或技能可以按宣告出來的路線來寫，而不是把一串狀態手工抄過去。

如果你需要某個狀態變更真正不可能發生，狀態機不是那個工具：能擋下儲存的是 `error` 級的驗證規則。這五條保持建議級是有意的 —— 理由就寫在規則自己身邊（`src/objects/quote.object.ts`）：售後的更正不該還要靠一次資料修復才能做到。

## 自訂狀態機

管理員可以：

- **新增狀態**（例如為行銷跟進新增 *Lead status = Nurturing*）。
- **移除轉換**（例如禁止在商機階段中向後移動）。
- **新增進入條件**（例如 *沒有決策者聯絡人角色就不能進入 Proposal*）。
- **新增退出條件**（例如 *沒有更新關閉日期就不能離開 Negotiation*）。
- 在每次轉換時 **觸發自動化**（物件鉤子、流程、通知）。

上面這些都是改原始碼，不是在設定裡點幾下：**並不存在「設定 → 物件 → 狀態 → 狀態機」這個設定面**。每張轉換表都是物件上的一條 `validations[]` 條目（型別 `state_machine`，見 `src/objects/*.object.ts`），而這條條目只帶一張轉換對應表，別的什麼都沒有 —— 所以上面前兩項是改這張對應表，進入/退出條件是另外的 `validations[]` 規則或相關欄位上的 `requiredWhen` 述詞，按轉換觸發自動化則是 `record_change` 流程或物件鉤子。每一項都是程式碼改動加一次重新部署。

## 使用者看到什麼

- **狀態下拉選單不會被過濾。** 無論記錄目前處於什麼狀態，它都列出該欄位宣告的全部選項。平台 *能* 算出合法的下一批狀態 —— `@objectstack/objectql` 裡的 `legalNextStates`，透過 `GET /objects/{name}/state/{field}?from=…` 可以取到 —— 但本應用沒有任何一處呼叫它，也沒有任何列表、表單或詳情頁按它收窄選項列表。
- **不被允許的轉換不會報錯，也不會跳出對話框。** 儲存照樣通過，記錄就停在新值上；唯一的痕跡是伺服器端的一行日誌 —— `WARN Validation rule 'lead_status_progression' (warning): Invalid lead status transition` —— 在介面裡工作的人永遠看不到它。
- 強制執行新狀態的必填欄位 —— 使用者在儲存前內聯看到它們。這是另一套機制：欄位上的 `requiredWhen` 述詞（例如階段變為 *Closed Won* 時的 `win_reason`），它確實會拒絕儲存。

## 狀態機與 AI Copilot

Copilot 理解狀態機。在建議操作時：

- *「確認這個潛在客戶的資格」* → 僅當狀態為 *Working* 時建議。
- *「轉化這個潛在客戶」* → 僅當狀態為 *Qualified* 時建議。
- *「將這個商機標記為 Closed Won」* → 僅當贏單條件滿足時建議（金額、關閉日期、贏單原因、必要時的審批）。

這可以防止 Copilot 建議非法的轉換。

## 給管理員的提示

- ✅ **不要過度約束** —— 太多轉換規則會成為團隊的摩擦稅。
- ✅ 新增狀態時，**先決定進入和退出條件** —— 其餘的自然就有了。
- ✅ 使用狀態機轉換來 **觸發自動化**，而非在每次儲存時執行自動化 —— 效能要好得多。
- ✅ 每次變更後 **測試精靈流程**（轉化潛在客戶、關閉商機）。

## 給使用者的提示

- 狀態下拉選單從不會因為狀態機而少給你一個選項 —— 它根本不過濾這個選項列表。缺了你期望的選項，去看該欄位自己的選項設定或你所屬設定檔的欄位級安全，而不是轉換表。
- 不存在 *「繞過狀態機」* 這項權限可申請，也沒有什麼需要繞過。把遺留資料直接匯入到後期狀態不需要任何授權：**新建** 路徑根本不查轉換表，更新時走出轉換表也是記一條日誌然後照樣儲存。真正該做的是知會管理員一聲，好讓日誌裡冒出來的那些警告被認成這次匯入，而不是被當成 bug 去追。
