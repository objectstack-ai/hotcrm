# 设置清单

为新 HotCRM 管理员准备的实用的第一周清单。请按顺序逐项完成 —— 每个部分都建立在前一个之上。

## ✅ 第 1 天 —— 基础

### 1. 公司资料

导航至 **设置 → 公司信息**：

- [ ] 公司名称、地址、时区、默认货币
- [ ] 财年起始月份（所有预测报表都会用到）
- [ ] 默认语言

### 2. 营业时间 —— 没有需要配置的东西

**不存在“设置 → 营业时间”这个屏幕。** 本应用没有工作日日历，没有工作时段设置，也没有节假日清单 —— 这里没有任何可填的项，也不存在任何可供截止时间去对照的东西。这一节保留下来，只是为了让被指去找那个屏幕的管理员别再找了。

由此带来的后果落在 SLA 一侧：截止时间按**日历小时**走。现在每一张工单都会被算出一个截止时间 —— `src/objects/case.hook.ts` 拿工单的优先级去和其账户的**客户层级**对查，再把相应的实际小时数加到当前时钟上 —— 所以一个周五下午 4 点建的 Critical 工单，截止时间就是同一个周五晚上 8 点；一个在长假前建的 Low 工单，那一周就这么在假期里跑完。夜间、周末与节假日在每个优先级上都一律照算。参见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)。

### 3. 电子邮件设置

**设置 → 邮件**：

- [ ] 工单的入站邮件转发（例如 `support@yourdomain.com`）
- [ ] 出站邮件签名模板
- [ ] 用于发件人身份验证的 DKIM / SPF

## ✅ 第 2 天 —— 人员

### 4. 用户邀请

**设置 → 用户**：

- [ ] 导入或邀请所有用户
- [ ] 为每个用户分配一个 [权限档案](/zh-Hans/docs/administration/profiles)
- [ ] 为每个用户分配岗位 —— 一个用户可以持有多个
- [ ] 为每个用户设置一名经理（驱动审批路由）

### 5. 岗位

**设置 → 用户**，以及[共享与安全](/zh-Hans/docs/administration/sharing-and-security)列出的 12 个岗位：

- [ ] 把你的组织映射到内置岗位上。岗位是**扁平的** —— 它们分发访问权限，不会叠成一条汇报线，一个岗位也不会向另一个岗位上卷
- [ ] 每新增一个岗位，就为它补上点名该岗位的共享规则（或权限集绑定）—— 没有任何规则点名的岗位什么也授予不了

### 6. 权限档案与权限

**设置 → 权限集** —— 本清单里所说的*权限档案*就是权限集，设置中没有叫*权限档案*的页面：

- [ ] 审查六种内置权限档案（参见 [权限档案](/zh-Hans/docs/administration/profiles)）
- [ ] 如有需要，克隆并自定义（例如一个删除权限有限的 *初级销售代表* 权限档案）

## ✅ 第 3 天 —— 数据基础

### 7. 客户与联系人所有权

- [ ] 为客户和联系人决定组织范围默认值（私有 vs 公开读取 vs 公开读/写）—— 参见 [共享与安全](/zh-Hans/docs/administration/sharing-and-security)
- [ ] 如果你以小组而非单个代表的方式销售，配置客户团队

### 8. 潜在客户路由 —— 没有需要配置的东西

**不存在“设置 → 潜在客户设置”这个屏幕**，也没有任何路由规则可写。一条无所有者的线索 —— 网页表单、CSV 导入、API 采集 —— 会在插入时由 `src/objects/lead.hook.ts` 分配：交给持有 `sales_rep` 岗位的人中**未结线索最少**的那一位。这是一个自平衡的轮询，而不是按区域、行业或来源匹配的规则；没有区域路由，没有队列，也没有发给提交者的自动回复邮件。如果没有人持有 `sales_rep`，这个钩子什么也不做，线索就一直无主，直到有人认领。

- [ ] 把 `sales_rep` 岗位分配给每一位应当接收线索的销售代表 —— 这个人员池*就是*路由表
- [ ] 在 **Studio → Automation → Flows** 中查看接下来 `lead_assignment` 流程做了什么（按评级设置跟进日期，并提醒新的所有者）

### 9. 产品目录

- [ ] 导入 [产品](/zh-Hans/docs/revenue/products) —— 至少：代码、名称、标价
- [ ] 设置产品经理（每条产品线的联系人）
- [ ] 上传数据表 —— 产品记录上的一个 PDF 文件字段，供人打开查看；没有任何知识库会摄取它

## ✅ 第 4 天 —— 流程

### 10. 商机阶段

确认 7 阶段默认管道与你的销售流程相符。各阶段及其概率为：

| 阶段 | 概率 |
| --- | --- |
| Prospecting | 10% |
| Qualification | 25% |
| Needs Analysis | 40% |
| Proposal | 60% |
| Negotiation | 80% |
| Closed Won | 100% |
| Closed Lost | 0% |

如果你的流程不同，那是一次源码修改，不是在某个屏上调整：**并不存在「设置 → 商机 → 阶段」这个页面**。七个阶段是 `stage` 字段自己的选项（`src/objects/_picklists.ts` 里的 `OPPORTUNITY_STAGE_OPTIONS`），概率则是 `src/objects/opportunity.hook.ts` 里的 `STAGE_PROBABILITY` 映射 —— 它在每次保存时都按阶段重新推导 **Probability** 与 **Expected Revenue**，所以手工填在商机上的概率撑不过下一次保存。改动其中任何一项都是代码改动加一次重新部署。

### 11. 工单 SLA

确认默认的 [SLA 矩阵](/zh-Hans/docs/service/sla-and-escalation)：

| 优先级 | Strategic | Enterprise | Mid-Market | SMB |
| --- | --- | --- | --- | --- |
| Critical | 4h | 4h | 4h | 4h |
| High | 6h | 8h | 8h | 8h |
| Medium | 24h | 36h | 48h | 48h |
| Low | 96h | 120h | 168h | 168h |

**每一个格子都是应用真正在守的期限。** `case_sla_defaults` 钩子（`src/objects/case.hook.ts`）在每一张工单上把 `sla_due_date` 盖成 *当前时间 + 相应的日历小时数*，每小时跑一次的 `case_sla_monitor` 会捞起其中任何一张到期日已过的。走哪一列由账户的**客户层级**决定 —— 所以确认这张矩阵，也就意味着确认你的账户确实分好了层级。层级为空的账户，或者建单人读不到的账户，一律按 **SMB** 对待。

**这里没有「首次响应目标」可确认。** 本清单曾经带着整整一列 *首次响应*（Critical 1 小时一直到 Low 1 个工作日），这四个数字在应用里哪儿都不存在；本节链过去的那一页 SLA 文档也没有首次响应目标。真正存在的是那个时间戳：**First Response Date** 在工单上第一次记录 *已经发生过* 的互动时被写入（`event_activity_bubble` 钩子，`src/objects/event.hook.ts`）。它从不与任何目标比较 —— `case_metrics` 没有声明任何首次响应度量，因此没有报表、没有仪表盘磁贴会报它，也没有任何流程会为它告警。你当然可以对客户承诺一个首次响应时长；应用只是记下它何时发生，别的什么都不做。

如果你的支持承诺不同，请自行调整 —— 这十六个数字写在 `src/objects/_case-sla.ts` 与 `src/objects/case.hook.ts` 里的一张对应表中，不在任何设置屏上，而且两处必须同步修改。

### 12. 工单路由 —— 没有需要配置的东西

**不存在“设置 → 工单设置”这个屏幕**，也没有任何路由规则可写。一张无所有者的工单 —— 最常见的来路是网页转工单（web-to-case）提交 —— 会在插入时由 `case_auto_assign`（`src/objects/_case-assignment.ts`）分配：交给持有 `service_agent` 岗位的人中**未结工单最少**的那一位，这里的“未结”指状态既不是 *Resolved* 也不是 *Closed*。这和线索那一侧是同一种自平衡轮询：比的是谁负载最轻，而不是按次序轮换，也不是按产品、区域或来源匹配的规则；没有区域路由，也没有队列。它**只在插入时运行**，而且只处理到达时就没有所有者的工单 —— 它不会在之后把工单从某个人手里拿走，也不会在客服自己新建工单时触发，因为钩子跑起来之前平台已经把创建者盖成了所有者。它也从不阻断工单进入：当人员池根本读不到时（匿名网页转工单表单就是这种情形），工单照样被记录下来，只是无主。而如果没有人持有 `service_agent`，这个钩子什么也不做，工单就一直无主，停在[工单](/zh-Hans/docs/service/cases)页面的 **未分派 — 待分诊** 页签里。那个页签正是这个钩子“什么也不做”这条路径的可见化，所以给这个岗位配上人本身就是一次行为变化：新工单不再无主到达，也不再出现在那里。**这不是升级交接**：那是另一个人员池、另一个时机 —— 它挂在转为 *Escalated* 的状态迁移上，把工单交给持有 `service_manager` 岗位的人中负载最轻的那一位（参见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)）。

- [ ] 把 `service_agent` 岗位分配给每一位应当接收工单的客服 —— 这个人员池*就是*路由表
- [ ] 在还没有人持有它的时候，盯住工单页面的 **未分派 — 待分诊** 页签：它列出的正是这个钩子没能分配掉的工单

### 13. 审批流程

- [ ] 确认折扣审批阈值（默认 $500K）—— 参见 [审批](/zh-Hans/docs/revenue/approvals)
- [ ] 确认审批人（按角色：经理 + 总监）
- [ ] 通过提交一个示例商机进行测试

## ✅ 第 5 天 —— 知识与 AI

### 14. 知识文章

HotCRM 只附带**一个**知识对象，而不是一组知识库。下面每一条都是你在**服务 → 知识库**下创建的普通记录，归入该对象定义的七个分类之一。

- [ ] 把最热门的 20 个 FAQ 写成文章，归入**故障排查**、**操作指南**或**入门指南**
- [ ] 把支持时间、SLA 承诺和数据处理说明归入**政策制度**
- [ ] 逐篇设置**受众** —— 操作手册用*仅内部*，你愿意发给客户的用*公开*
- [ ] 把它们**发布** —— Copilot 只查询已发布的文章，草稿等于不存在
- [ ] 收工前复核一遍分类和标签：匹配靠的是分类与标签而不是语义，归错的文章就是找不到的文章

没有任何叫 *销售知识*、*产品信息* 或 *竞争情报* 的东西可以填充种子内容 —— HotCRM 不附带这些库，也没有可供对战卡挂靠的竞争对手对象。Copilot 拿一篇文章能做什么、不能做什么，参见 [知识库](/zh-Hans/docs/ai-copilot/knowledge-bases)。

### 15. AI Copilot

设置里没有 *AI* 分组，也没有任何界面能把 Copilot 打开。设置里与 AI 相关的只有两处：**设置 → 配置 → AI 与 Embedder**（配置提供商、模型与 Embedder），以及 **设置 → 配置 → 功能开关** 下那个默认关闭、平台里没有任何东西读取的测试版 *AI 助手* 开关。让 Copilot 能作答的是一个配置好的提供商；它能跑哪些技能由应用本身决定，不属于安装环节。作为导航分组的 *AI* 在 **Studio → AI**（智能体 / 工具 / 技能）。

- [ ] 确认 **设置 → 配置 → AI 与 Embedder** 里选的是一个真实提供商 —— 它默认是 *Memory(回显 — 仅测试)*，只把你的输入原样回显而不作答 —— 然后点 *测试连接*
- [ ] 运行一个示例查询（*“给我 [测试客户] 的 Customer 360”*）以验证 —— 能引用真实记录作答，就说明提供商已生效
- [ ] 在 **Studio → AI → 技能** 里过一遍 Copilot 随附的技能 —— 它们都是启用的；有哪些技能由应用决定，而不是在这里挑选（参见 [技能](/zh-Hans/docs/ai-copilot/skills)）
- [ ] 不要去找 AI 脱敏规则，去看字段级安全：Copilot 以当前登录用户的身份读取，某个字段在他的权限档案里被遮罩，就永远到不了 Copilot（参见 [共享与安全](/zh-Hans/docs/administration/sharing-and-security)）

## ✅ 第 6 天 —— 仪表板与报表

- [ ] 将 **CRM 概览** 固定为所有人的主页仪表板
- [ ] 设置团队专属仪表板（销售 / 服务 / 高管）
- [ ] 为经理安排每周订阅邮件
- [ ] 审查 [标准报表](/zh-Hans/docs/analytics/reports) 并自定义筛选器

## ✅ 第 7 天 —— 上线

- [ ] 运行 **迁移检查**（所有导入的记录都有所有者和必填字段）
- [ ] 运行 **冒烟测试**：创建潜在客户 → 转化 → 商机 → 报价 → 赢单 → 合同
- [ ] 培训用户掌握他们的日常工作流（45 分钟的基于角色的会话）
- [ ] 设置一个内部 **#hotcrm-help** 频道用于答疑

## 上线后

- **第 2 周**：审查仪表板使用情况和采用指标。
- **第 1 个月**：首次回顾 —— 哪些有效，哪些无效。
- **每季度**：审查权限档案、共享规则、知识库是否有漂移。
