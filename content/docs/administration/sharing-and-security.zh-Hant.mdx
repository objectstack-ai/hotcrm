# 共用與安全

共用回答這個問題：*「這個使用者能檢視和編輯哪些記錄？」* 四個層級疊加在一起給出答案：

1. **物件權限** —— 這個使用者到底能不能碰這個物件？（參見[權限設定檔](/zh-Hant/docs/administration/profiles)。）
2. **組織範圍預設值 (OWD)** —— 記錄層級的基線（「商機是私有的」）。
3. **共用規則** —— 各種開口（「EU 團隊可以編輯 EU 客戶」）。
4. **手動共用** —— 記錄層級的「你和我一起在跟這一條」。

外加用於遮罩敏感欄位的 **欄位層級安全**。

> 第一層是閘門，不是過濾器。如果權限設定檔沒有授予這個物件，任何 OWD、共用規則或 *檢視所有* 設定都無法把記錄找回來 —— 請求在觸及共用之前就被拒絕了。

## 第 1 層 —— 組織範圍預設值

OWD 是每個物件的 *最嚴格* 設定，其他一切都在此之上放寬。

| 物件 | OWD | 原因 |
| --- | --- | --- |
| 線索 | 私有 | 代表跟自己的線索 |
| 客戶 | 私有 | 客戶歸屬很重要 |
| 聯絡人 | 由父層控制（客戶） | 聯絡人屬於它的客戶，並跟隨客戶的共用 —— 見下面的 *「由父層控制」在實務中* |
| 商機 | 私有 | 敏感的交易資料 |
| 商機明細 | 由父層控制（商機） | 產品明細是交易的一部分 |
| 報價 | 私有 | 定價屬於所有人 |
| 報價明細 | 由父層控制（報價） | 明細是報價的一部分 |
| 合約 | 私有 | 敏感的商務條款 |
| 案件 | 私有 | 專員的佇列是自己的；升級件走共用 |
| 任務 | 私有 | 個人活動項目 |
| 活動 | 私有 | 個人活動項目，與任務同類 |
| 活動參與者 | 由父層控制（活動） | 參與者屬於他們參加的那場會議，並跟隨那場會議的共用 —— 見下面的 *「由父層控制」在實務中* |
| 預測 | 私有 | 快照屬於其所有人；經理持有 *檢視所有* |
| 產品 | 公開唯讀 | 所有人都看得到目錄 |
| 行銷活動 | 公開唯讀 | 行銷建立，銷售檢視 |
| 行銷活動成員 | 由父層控制（行銷活動） | 成員關係是行銷活動的一個屬性，並跟隨它的共用 —— 見下面的 *「由父層控制」在實務中* |
| 知識文章 | 公開唯讀 | 知識庫面向全體內部使用者；由專員撰寫 |

**OWD 的取值**：私有 / 公開唯讀 / 公開讀寫 / 由父層控制。

### 「由父層控制」在實務中

對於上面五個由父層衍生的物件，沒有任何按使用者設定的東西：存取權限是 *計算* 出來的。

- **讀** —— 你看到的是那些父記錄你能看到的列，而「能看到」指的是任何一條能讓你直接開啟該父記錄的途徑：你擁有它、某條共用規則授予了它，或者有人手動共用給了你。對隨產品發布的 stack 實測（平台 17.0.0-rc.4）：一個只讀得到一個客戶的代表，只讀到 **那一個** 客戶的聯絡人；一個一張報價都讀不到的代表，一列報價明細也讀不到。那個僅透過區域規則到達該代表的客戶正是關鍵 —— 透過共用持有的父記錄，同樣算作「你能看到的父記錄」。
- **寫** —— 新增、修改或移除一列需要對父記錄有 **編輯** 權限，其解析方式與讀取相同。父記錄你無權編輯的列會被拒絕，並在錯誤訊息中點名是哪個父記錄擋下了它。

> **這一行為在平台 17.0.0-rc.4 發生了改變。** 在 17.0.0-rc.3 及更早版本上，計算出來的結果是組織範圍而不是按父記錄收窄：衍生只從父物件自身的 *列層級安全政策* 去解析可存取的父記錄，而 HotCRM 幾乎沒有寫這類政策，因此只要權限設定檔授予了該物件，「由父層控制」物件對該使用者就是可讀、也可寫的。如果你執行的是更早的版本，你拿到的就是那個行為，報價與商機的明細定價在組織範圍內可見。本倉的測試 `test/parent-derived-reach.test.ts` 在兩個方向上都釘住了目前的可達範圍（#549、#694；上游修復 objectstack-ai/objectstack#5386）。

由於存取是衍生的，子記錄本身的歸屬無關緊要 —— 報價產生流程建立的報價明細，對報價所有人來說與自己手動輸入的一樣可見。

## 第 2 層 —— 職位

**職位（position）** 是用於分發存取權限的扁平群體。HotCRM 內建十二個：

```
executive
sales_director      sales_manager      sales_rep
service_director    service_manager    service_agent
marketing_director  marketing_manager  marketing_user
na_sales_team       eu_sales_team          （區域分組）
```

職位 **在設計上是扁平的** —— 沒有階層，**什麼都不會上捲**。銷售總監不會繼承銷售經理的存取權限；每個需要某條記錄的層級都由它自己的共用規則點名。這就是下面若干規則成對出現的原因。

在 **設定 → 使用者** 中指派職位；一個使用者可以持有多個。

## 第 3 層 —— 共用規則

共用規則在 OWD 基線之上 **放開** 記錄存取。

### 兩種形式

| 類型 | 共用什麼 | 範例 |
| --- | --- | --- |
| **基於條件** | 符合某個過濾條件的所有記錄 | *「帳單國家為 DE/FR/… 的客戶」* → 共用給 EU 團隊 |
| **基於所有人** | 某個群體擁有的所有記錄 | *「SDR 擁有的記錄」* → 共用給 AE 群體 |

基於條件的規則是被真正執行的那一種：符合的記錄會實體化為真實的共用授權。

### 內建共用規則

| 規則 | 物件 | 授予 | 給誰 |
| --- | --- | --- | --- |
| Account Team Sharing | 客戶 | 編輯 | `sales_manager` —— 活躍的客戶型客戶 |
| North America Territory | 客戶 | 編輯 | `na_sales_team` —— 帳單國家為 US/CA/MX 的客戶 |
| Europe Territory | 客戶 | 編輯 | `eu_sales_team` —— 帳單國家為 UK/DE/FR/IT/ES 的客戶 |
| Opportunity Sales Team Sharing | 商機 | 讀取 | `sales_director` —— 金額 ≥ $100,000 的進行中交易 |
| Large Open Deals — Executive | 商機 | 讀取 | `executive` —— 同一批交易，上一層級 |
| Escalated Cases Sharing | 案件 | 編輯 | `service_manager` —— 未關閉的緊急案件 |
| Escalated Cases — Service Director | 案件 | 讀取 | `service_director` —— 同一批案件，上一層級 |
| Live Campaigns — Marketing Manager | 行銷活動 | 編輯 | `marketing_manager` —— 籌劃中 / 進行中的活動 |
| Live Campaigns — Marketing Director | 行銷活動 | 編輯 | `marketing_director` —— 同一批活動 |

在 **設定 → 共用設定** 中建立你自己的規則。

> **條件只能過濾普通欄位，不能過濾地址的某一部分。** 兩條區域規則比對的是客戶上的 **帳單國家** —— 一個唯讀的兩位國家代碼，由你在 **帳單地址** 中填寫的國家推導而來 —— 而不是地址本身。條件規則必須以資料庫查詢的形式執行，而查詢無法深入結構化的地址或位置值內部。因此，針對 `帳單地址 → 國家` 撰寫的規則會被**直接拒絕**，而不是被悄悄放寬成「所有客戶」：它根本不會被安裝，它指定的職位也就什麼都拿不到。介面上不會把這樣的規則標記為失效，所以當某個團隊回報記錄缺失時，請檢查規則裡引用的每個欄位是否都是該物件上的普通欄位。

### 一條規則放開的是一個物件，而不是它底下的記錄

共用規則是 **按物件** 撰寫的。放開 `Account` 只放開客戶本身 —— 掛在這個客戶底下的記錄仍各自守著自己的基線，其中只有聯絡人是從客戶衍生的：

| 已共用客戶上的相關清單 | 接收者實際看到的 |
| --- | --- |
| 聯絡人 | 這個客戶的聯絡人 —— Contact 是「由父層控制」，而共用過來的客戶就算作他們能看到的父記錄 |
| 商機 | 只有自己的交易；若持有 `sales_director` 或 `executive`，另加金額 ≥ $100,000 的未結交易 |
| 報價 | 只有自己的 |
| 合約 | 只有自己的 |
| 案件 | 只有自己的；若持有 `service_manager` 或 `service_director`，另加未關閉的緊急案件 |
| 任務 | 只有自己的 |
| 活動 | 只有自己的 |

也就是說，區域規則交出的是客戶記錄；底下的交易、報價、合約、案件、任務與會議歷史仍歸各自的所有人，使用者明明能完整讀取這個客戶，這些相關清單卻可能是空的或殘缺的。聯絡人是例外，而且是符合本意的那種例外：它跟隨客戶，所以區域共用過來的客戶，其聯絡人清單是完整的。

讓子物件跟隨客戶是一次刻意的放開，而不是一個設定細節。在子物件上以與客戶規則相符的條件另寫一條共用規則，會對 **所有** 持有該物件的使用者放開可見性，而不只是區域規則的接收者。把子物件的 OWD 改成「由父層控制」則是更精準的那把刀：自平台 17.0.0-rc.4 起，它恰好把子記錄授予那些能夠到達其父記錄的人（見上面的 *「由父層控制」在實務中*）。對報價與合約，HotCRM 今天兩者都不做；是否應該做是一項待定決策（#549）。

## 第 4 層 —— 手動共用

**手動共用** 在上述一切之上，把某一條記錄的 **讀取** 或 **讀寫** 權限授予某個使用者或群組。共用按記錄儲存。自平台 17.0.0-rc.4 起，手動共用同樣會帶上這條記錄底下由父層衍生的子記錄：共用一個客戶就交出了它的聯絡人，因為衍生會像解析其它途徑一樣把共用授權折算進去（見 *「由父層控制」在實務中*）。

HotCRM **不提供客戶團隊物件** —— 客戶上沒有團隊名單，也沒有「團隊」頁籤。上表中那條名為 *Account Team Sharing* 的規則就是一條普通的條件規則：它把活躍客戶類帳戶的編輯權授予每一位 `sales_manager`，而不是按記錄組成的小組。以小組方式作戰的組織，可以把小組建模為一個職位並為其撰寫共用規則，或者在客戶上使用手動共用。

## 這些層級如何組合

當以下條件 **全部** 成立時使用者才能看到一條記錄：其權限設定檔授予了該 **物件的讀取權限**，並且 **以下任一條** 為真：

1. 他們 **擁有** 這條記錄。
2. 其權限設定檔授予該物件的 **檢視所有**。
3. **OWD** 為公開唯讀或更寬。
4. 該物件是 **「由父層控制」**，且 **它的父記錄** 透過上述任意一條途徑對他們可見（見 *「由父層控制」在實務中*）。
5. 某條 **共用規則** 符合該記錄且命中他們的某個職位。
6. 該記錄被 **手動共用** 給了他們。

若都不成立，這條記錄只是從清單、搜尋和報表中 *消失* —— 而不是給出一條錯誤訊息。

## 歸屬與轉移

每筆記錄有且只有一位**負責人（Owner）**。它就是表單上的那個欄位、「我的……」檢視所篩選的那個欄位，也是上面每一條規則說「記錄的負責人」時所指的那個欄位——一欄，一個答案。變更負責人是真正的交接：原負責人立即失去以歸屬為依據的存取權，新負責人立即取得，且在所有位置同步生效。

正因為它會移動存取權，**修改負責人是一項獨立的權限**，與一般的編輯權限分開：

| 角色 | 可轉移的物件 |
| --- | --- |
| 系統管理員 | 全部物件 |
| 銷售經理 | 銷售簿——潛在客戶、客戶、聯絡人、商機、報價、任務、會議、預測 |
| 客服專員 | 僅任務（以便升級時把工作交給客戶負責人） |
| 銷售代表、行銷使用者 | 無——記錄是被指派給他們的 |

有三類日常操作**不算**轉移，因此不需要該權限：

- **建立記錄。** 新記錄會自動歸屬到建立者，你無需手動選擇自己。
- **儲存表單**時未變更負責人——即使表單會把該欄位一併送出。
- **自動化代你執行**——指派新潛在客戶的輪詢、夜間產生續約與跟進任務的批次作業。

沒有該權限的使用者嘗試轉移時會收到明確的拒絕提示，而不是悄無聲息地失效。需要整體移交業務簿時，請聯絡管理員或你的銷售經理。

> **從舊版本升級？** 負責人過去是一個普通欄位，任何有編輯權的人都能改——而變更它只會讓記錄在各種清單和報表裡移動，存取權**完全沒動**。現在兩者是同一個欄位。先前顯示負責人與實際存取歸屬已經產生偏離的記錄，需要一次性回填對齊；詳見發行說明中的回填說明。

### 私有商機

商機上的 `Private` 在上述一切之上生效：使用者標記為 **Private** 的交易只對其所有人（以及管理員）可見，即使是像 Sales Manager 和 Marketing User 這類本來持有組織範圍商機讀取權限的權限設定檔也看不到。用於董事會層級或涉併購敏感的交易。

## 欄位層級安全 (FLS)

FLS 控制在一條 *可見* 記錄內部，某個權限設定檔能看到和編輯 **哪些欄位** —— 例如客戶 **健康度評分** 對所有能看到該客戶的人可讀，但只有銷售經理能設定它；而 **案件內部備註** 對銷售代表完全隱藏。隨產品提供的遮罩清單見[權限設定檔](/zh-Hant/docs/administration/profiles#欄位層級安全)。

FLS 在 **所有地方** 生效 —— 清單檢視、報表、API 和 AI Copilot。被遮罩的欄位也不能用於過濾、排序或分組。

## AI Copilot 的共用

Copilot 代表使用者行動 —— 它看到的與使用者看到的完全一致，不多一分：

- 物件權限、共用和 FLS 全部自動生效。
- 管理員執行 Copilot 會比代表看到更多 —— 這是設計使然。

不存在「AI 繞過」。

## 給管理員的提示

- ✅ **先檢查物件授權。** 空白的相關清單或報錯的導覽項，幾乎總是缺少物件權限，而不是共用問題。
- ✅ **從嚴開始** —— 線索/客戶/商機用私有 OWD，然後用共用規則放開。
- ✅ **記住職位是扁平的。** 授予經理並不等於授予總監；兩者都要寫。
- ✅ **每季稽核共用規則** —— 它們會累積。
- ✅ 不要濫用 **檢視所有** —— 它是一把繞過所有共用規則的大鎚。

## 給使用者的提示

如果你認為自己應該能看到某條記錄卻看不到：

1. 查一下 **誰擁有它**。
2. 如果你是從客戶點進去的，先看 **它是哪個物件**：即使客戶本身已經共用給你，報價、合約、任務、案件與交易仍歸各自的所有人。聯絡人是唯一從不會被扣下的相關清單 —— Contact 是「由父層控制」，它跟隨客戶，所以客戶共用給你時聯絡人也一併到達（見 *「由父層控制」在實務中*）。
3. 查一下該交易是否被標記為 **Private**。
4. 詢問管理員是否應該有一條 **共用規則** 涵蓋你的職位。
