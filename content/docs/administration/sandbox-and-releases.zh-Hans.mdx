# 沙箱与发布管理

切勿直接在生产中进行配置变更。本页介绍安全的工作流：在沙箱中构建、测试、打包、提升到生产，必要时回滚。

## 什么是沙箱？

**沙箱** 是你的生产 HotCRM 租户的全保真副本 —— 相同的模式，可选地包含相同的数据 —— 在隔离环境中运行。你可以毫无后果地把它弄坏。

| 沙箱类型 | 其中包含什么 | 刷新频率 |
| --- | --- | --- |
| **仅配置** | 仅模式 + 元数据，无记录 | 按需 |
| **部分数据** | 模式 + 一小部分记录样本 | 每周 |
| **完整副本** | 模式 + 所有生产数据（已匿名化） | 每月 |

企业版套餐通常包含 **3 个沙箱**；可按需添加更多。

## 创建与刷新沙箱

1. **设置 → 沙箱管理 → 新建沙箱**。
2. 选择 **类型**（配置 / 部分 / 完整）。
3. 为它命名（例如 `dev`、`uat`、`training`）。
4. 点击 **创建** —— 通常 10–60 分钟内就绪，具体取决于大小。

要用最新的生产数据刷新现有沙箱，请点击沙箱行上的 **刷新**。⚠️ **刷新会清除沙箱中的所有更改** —— 如果你需要它们，请先打包并导出。

### 刷新时的匿名化

对于完整副本沙箱，PII 可以在刷新时匿名化：

- 电子邮件地址 → `user-{id}@example-anon.test`
- 电话号码 → 随机化但保留格式
- 姓名 → 看起来真实的假名
- 自由文本字段 → 保持原样（注意 —— 请审查敏感内容）

推荐用于由合作伙伴 / 外包人员访问的沙箱。

## 变更工作流

```
┌───────────┐   build    ┌─────────┐   test    ┌─────────┐   promote   ┌────────────┐
│ Developer ├──────────▶│   dev   ├──────────▶│   uat   ├────────────▶│ production │
└───────────┘            └─────────┘           └─────────┘             └────────────┘
                                                                              │
                                                                       rollback│
                                                                              ▼
                                                                       last working
                                                                          package
```

1. 在 `dev` 沙箱中 **构建** 变更。
2. **提升** 到 `uat` —— 业务用户在那里测试。
3. 需要 **UAT 签核** 才能继续。
4. 在变更窗口期间 **提升** 到 `production`。
5. 在生产中立即进行 **冒烟测试**。
6. 必要时 **回滚**。

## 变更包

**变更包** 将一组元数据变更（对象、字段、验证、流程、共享规则等）捕获为单个可部署的工件。

### 创建包

1. **设置 → 变更包 → 新建**。
2. 名称 + 描述。
3. 添加组件：
   - **手动** —— 从列表中挑选对象、字段、规则。
   - **按标签** —— 任何标记为 `release-2026-Q1` 的内容。
   - **自动** —— 自上次打包时间戳以来的每一项变更。
4. **验证** —— 系统检查包的一致性（例如无法解析的字段引用）。
5. **保存**。

### 部署包

1. 从源沙箱 → **部署 → 选择目标租户**。
2. **试运行** —— 将会变更什么、将会创建什么、存在什么冲突。
3. 审查变更集。
4. **部署** —— 仅配置变更通常 &lt;2 分钟。
5. **审计日志** 捕获谁在何时部署了什么。

### 哪些可以打包

| 类型 | 可打包 |
| --- | --- |
| 对象、字段、验证 | ✅ |
| 流程 | ✅ |
| 共享规则、权限档案、权限集 | ✅ |
| 页面、列表视图、仪表板 | ✅ |
| 报表、立方体 | ✅ |
| AI 技能、知识库配置 | ✅ |
| 审批流程 | ✅ |
| 电子邮件模板 | ✅ |
| **数据记录** | ❌（使用数据导入） |
| **文件** | ❌（使用文件同步 API） |
| **用户账户** | ❌（使用 SCIM） |

## 版本控制（基于 git）

对于技术团队，沙箱元数据可以 **同步到 git 仓库**：

1. **设置 → 沙箱 → Git 同步 → 连接**。
2. 授权一个 GitHub / GitLab / Bitbucket 账户。
3. 选择仓库和分支。
4. **拉取** —— 从 git 获取元数据到沙箱。
5. **推送** —— 将沙箱变更提交回 git。

这解锁了：

- 通过 PR 进行 **代码审查**。
- 分支之间的 **差异对比**。
- 每次变更的 **历史**。
- 在合并前运行 `pnpm typecheck` 等的 **CI**。

对于使用自己的包来扩展 HotCRM 的客户，这是推荐的工作流。

## 回滚

两种形式：

### 快速回滚（24 小时内）

每次部署都会创建一个 **还原点**。在部署后的 24 小时内：

1. **设置 → 变更包 → 部署历史 → [部署] → 回滚**。
2. 确认 —— 系统还原元数据变更。
3. 自部署以来创建的记录保留；元数据被还原。

### 重新部署之前的包

如果已经过去 >24 小时，请重新部署 **上一个成功的包**。同样的 UI，只需选择较旧的包版本。

⚠️ 如果你回滚模式变更，针对新模式创建的数据可能需要迁移。请始终先在 UAT 中测试回滚。

## 生产变更窗口

最佳实践：

- **非高峰窗口**（通常是周末或周五晚 7 点）用于非简单部署。
- 在重大业务事件前设置 **冻结期**（季度末、大型发布）。
- 在公司 #cm-announcements 频道 **公告**。
- 任何生产部署都要有 **2 名管理员** 在场（四眼原则）。
- 部署后立即运行 **冒烟测试清单**。

## 冒烟测试清单

每次生产部署后：

- [ ] 以测试用户身份登录。
- [ ] 创建潜在客户 → 转化 → 商机 → 报价 → 合同。
- [ ] 创建案例 → 分诊 → 解决。
- [ ] 运行主页仪表板 —— 所有图块加载。
- [ ] 通过已连接的收件箱发送一封测试邮件。
- [ ] 在真实记录上调用一个 Copilot 技能。
- [ ] 抽查变更的组件。

## 监控与提醒

- 每次提升时向 Slack/Teams 发送 **部署提醒**。
- **错误激增** 检测 —— 如果部署后错误激增，自动建议回滚。
- **性能回归** 检测 —— 如果 p95 延迟下降 >20%，发出提醒。

## 提示

- ✅ **始终** 在 `dev` 中构建、在 `uat` 中测试、部署到 `prod`。切勿跳过 uat。
- ✅ **小而频繁** 的包胜过大型的季度发布。
- ✅ **为包清晰命名** —— `2026-Q1-pipeline-revamp` 而非 `Package 47`。
- ✅ 按举措为组件 **打标签** —— 让打包变得轻而易举。
- ✅ 一旦有 >2 名管理员进行变更，就尽快 **连接到 git**。
- ✅ 每月 **刷新沙箱** —— 陈旧的沙箱会给人虚假的信心。
- ✅ 每季度 **演练回滚** —— 切勿在真实事故中第一次使用它。
