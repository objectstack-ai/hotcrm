# 會議與電話

**一場會議或一通電話都儲存為一筆活動（Event）記錄**（`crm_event`）——佔用某個人日曆上一個時段的互動，每次一列；無論它已經發生（你剛剛記錄的一通電話），還是預約在下週二。

活動記錄是*「和這個客戶之間發生過什麼，什麼時候發生的？」*這個問題的可查詢答案。它與[活動（任務）](/zh-Hant/docs/sales/activities)刻意不是同一樣東西：

| | **任務** | **活動（Event）** |
| --- | --- | --- |
| 它是什麼 | 你仍然**欠**某人的事 | **發生過**的事 |
| 錨點 | 一個截止日期 | 一個開始時間和結束時間 |
| 有參與者 | 無 | 有——而且是記錄 |
| 歸屬介面 | 你的待辦清單 | 你的日曆 |

郵件是第三種型態：它不是一個日曆時段，因此 **Send Email** 不會寫入任何活動記錄（見[郵件與日曆](/zh-Hant/docs/guides/email-and-calendar)）——但它同樣會刷新客戶的接觸時點，就像一場已舉行的會議一樣。

## 三個按鈕

每一筆**潛在客戶、聯絡人、客戶、商機和工單**都帶有同樣的三個操作：

| 操作 | 寫入的活動記錄 | 什麼時候用 |
| --- | --- | --- |
| 📞 **Log a Call**（記錄電話） | 類型*電話*、狀態**已舉行**、開始時間為*此刻* | 電話剛打完 |
| 📅 **Log a Meeting**（記錄會議） | 類型*會議*、狀態**已舉行**、開始時間為*此刻* | 會議剛開完 |
| ➕ **Schedule a Meeting**（預約會議） | 類型*會議*、狀態**已計劃**、開始時間由你填寫 | 你在為之後預約 |

你可以在記錄頁標頭、清單檢視列的 ⋮ 選單以及相關清單中找到它們。（在工單上，記錄頁標頭帶的是 **Log a Call**，與*升級*、*關閉*並列；另外兩個操作同樣註冊在工單上，可從清單檢視列的選單進入。）

### 每個表單會問什麼

**Log a Call** 和 **Log a Meeting** 都會問：

- **主題**（必填）
- **時長（分鐘）**——三個操作上都是選填
- **聯絡人參與者**——可選任意多位聯絡人
- **內部參與者**——可選任意多位同事
- **備註**——聊了什麼

**Schedule a Meeting** 額外收集 **Start Date (UTC)**、**Start Time (UTC)** 和**地點**，並把備註框改名為 **Agenda**（議程）。

> ⚠️ **預約會議的開始日期與時間按 UTC 解讀**，這也是兩個欄位標籤寫明 UTC 的原因。請先換算再填寫：UTC+8 的 15:00 會議要填 `07:00`。HotCRM 儲存的一切都是 UTC 時刻；只是這個選擇器目前還不知道你所在的時區。

### 一次點擊產生了什麼

在一個商機上記錄一通電話，寫入的是三樣東西，不是一樣：

1. **活動記錄本身**——主題、類型、狀態、開始時間、時長、地點、備註，負責人是你，並回鏈到你發起操作的那筆記錄。
2. **參與者**——每個人一列（見下文）。你會被加為**組織者**，回覆直接設為*已接受*；如果你是在聯絡人或潛在客戶上發起的，那個人也會被加為參與者。
3. **一筆時間線項目**——該記錄的活動時間線上多出一筆指向這筆活動記錄的項目，因此從時間線鑽取打開的是真實記錄，而不是一段摘要字串。

在**工單**上，第一通*已舉行*的電話或會議還會寫入工單的**首次回應時間**——客戶第一次得到回音的時刻。僅僅*預約*的會議不算回應，狀態變更也不算。

## 已計劃 vs 已舉行——讓報表保持誠實的那條分界

每筆活動記錄都帶一個狀態：

| 狀態 | 含義 |
| --- | --- |
| 🔵 **已計劃** | 已預約，尚未發生 *（新建活動的預設值）* |
| 🟢 **已舉行** | 它發生了 |
| ⚪ **已取消** | 被取消 |
| 🟠 **客戶未到** | 沒有人出現 |

**只有*已舉行*的活動記錄會刷新客戶的接觸時點。** 預約在下個季度的會議並不是一次已經發生的互動；讓一次預約重設這個時鐘，正是「風險客戶」報表學會說謊的方式——把一個其實沒人聯絡過的客戶報成剛剛接觸過。

所以有一個習慣值得養成：

> 會議結束後，打開這筆活動記錄，把**狀態改為「已舉行」**。

時鐘在*進入*「已舉行」的那一次轉變上推進——只推進一次，而不是之後每次儲存都推進。「已取消」和「客戶未到」的記錄會保留（嘗試過本身就是證據），但它們的**時長會被歸零**，因此「本週面向客戶的分鐘數」不會虛高。

## 什麼會刷新「最後互動」

有兩個欄位承載客戶接觸時點，[銷售活動儀表板](/zh-Hant/docs/analytics/dashboards)上的沉默客戶磁貼等報表都建立在它們之上：

- **客戶 → 最後活動日期**（Last Activity Date）
- **聯絡人 / 潛在客戶 → 最後聯絡時間**（Last Contacted Date）

刷新它們的恰好是這些動作：

| 你做了什麼 | 客戶 | 聯絡人 | 潛在客戶 |
| --- | --- | --- | --- |
| 一筆活動記錄變為**已舉行** | ✅ | ✅ | ✅ |
| 一筆**任務**被完成 | ✅ | ✅ | ✅ |
| 在聯絡人上 **Send Email** | ✅（該聯絡人所屬客戶） | ✅ | — |
| 一張**工單**被設為*已解決* | ✅（該工單所屬客戶） | — | — |

客戶上的時點戳會**沿關係鏈向上走**。銷售代表是在商機、聯絡人或工單上記錄電話的——幾乎從不直接記在客戶那一列上——所以活動記錄會順著關聯向上找到背後的客戶並為它蓋戳。沒有這個向上追溯，一個往來頻繁的客戶會在整個銷售週期裡看起來一片沉默。

有兩件事這張表**刻意**沒有包含：

- 處於**已計劃**的活動記錄，以及儲存之前就已經是「已舉行」的活動記錄。
- 沒有任何關聯記錄的會議。活動記錄在沒有設定關聯記錄時會給出警告，而一次沒有掛到任何客戶上的互動，也無法刷新任何客戶的時鐘。

管理員還需要知道：修改客戶的**負責人**或**類型**，會作為這次編輯的副作用為它的最後活動日期蓋戳。它並不是一次互動；如果你在稽核「沉默」，請讀活動記錄，而不是只讀這個日期。

## 參與者是記錄，不是一個文字方塊

會議室裡的每個人都是掛在這場會議下的一筆真實記錄（`crm_event_attendee`）——正因如此，*「這個季度有哪些聯絡人拒絕了兩次？」*和*「這位銷售代表真正參加過什麼？」*才成為可回答的問題。

每筆參與者記錄保存：

| 欄位 | 說明 |
| --- | --- |
| **參與者類型** | *聯絡人*、*潛在客戶*、*內部使用者* 或 *外部來賓*——說明這一列指向的是哪類人 |
| **聯絡人 / 潛在客戶 / 內部使用者** | 那個人，以指向其記錄的真實連結形式 |
| **外部參與者** | 自由文字，也是最後的手段：留給完全不在任何 CRM 物件裡的客人（客戶方的律師）。把類型選為 *外部來賓*，姓名填在這裡。不是用來貼上一串名單的地方。 |
| **回覆** | *未回覆*（預設）、*已接受*、*已拒絕*、*待定* |
| **組織者** | 召集這場會議的人 |
| **邀請時間** | 邀請被記錄的時間 |
| **參與者編號** | 自動編號 `EA-00001` |

一筆參與者記錄必須**恰好**填寫其**參與者類型**所指的那一欄，其餘留空：*聯絡人* 列要填聯絡人，*外部來賓* 列要在**外部參與者**裡寫下姓名。指向不到任何人的參與者會被拒絕；類型與被填寫的欄位不一致的也會被拒絕——一筆記錄不能一邊自稱聯絡人、一邊只寫著外部客人的姓名。

### 刪除人與刪除會議

- **刪除一個人**（聯絡人、潛在客戶或同事）→ 他的參與者記錄隨之刪除，而**會議本身保留**，主題、時間和會後紀要都在。正是這一點讓人可以被刪除：在改成這樣之前，任何一個曾被記錄為參會人的人都根本刪不掉。
- **刪除一場仍有參與者的會議** → 會被拒絕，並明確指出是哪些參與者記錄擋住了它。先刪掉參與者記錄，會議才能刪除。一場會議的參會名單是這場會議歷史記錄的一部分，絕不會被悄悄丟棄。

## 系統自動為你完成的事

- **時長 ↔ 結束時間。** 給出開始和結束，時長就由它們*測量*得出（即使你另外填了一個數字也一樣——一個和自己的時間戳互相矛盾的時長，正是把報表算成一堆廢數的原因）。給出開始和時長，結束時間就被推算出來，這正是讓一通已記錄的電話出現在日曆上的原因。
- **全天活動**不保留分鐘數，因此「全天」與「我們忘了填」始終可以區分。
- **已取消 / 客戶未到** → 時長歸零。
- **結束早於開始**會被直接拒絕。
- **沒有關聯記錄**會觸發警告——把會議關聯到那筆交易或那張工單，否則它在真正需要它的地方是看不見的。

## 到哪裡找活動記錄

側邊欄裡只有 **Activity › Events** 這一個入口；檢視這些記錄的每一種方式，都是它打開的那個頁面頂部的一個標籤頁，標籤上寫的就是檢視自己的名字：

| 標籤頁 | 顯示什麼 |
| --- | --- |
| **全部活動**（預設打開） | 你能看到的全部活動記錄，最新在前 |
| **活動日曆** | 同樣的記錄以日曆呈現，按類型著色 |
| **團隊日程** | 同樣的時間跨度，每位銷售代表一條泳道 |
| **我的日曆** | 只顯示你自己的活動記錄 |
| **📅 即將開始 · 按時間升序** | 已計劃但尚未舉行，按時間升冪 |
| **✅ 互動歷史** | 只顯示已舉行的活動記錄——真正發生過的事 |

側邊欄裡另外保留了 **My Work › My Calendar** 這一個快捷入口：它落在同一個頁面上，並已選中**我的日曆**標籤頁——你自己的這一週是打開得最頻繁的檢視。

六種活動類型——**會議**（預設）、**電話**、**演示**、**線上研討會**、**上門拜訪**、**其他**——為日曆著色，並驅動[銷售活動儀表板](/zh-Hant/docs/analytics/dashboards)上的活動構成分析。

這裡沒有按日期篩選的「過去的活動」，這是刻意的：狀態是人寫下的、不會隨時間失效，而基於日期的標記在時鐘走過那一刻就已經過時。

## 誰能看到什麼

- 活動記錄是**私有**的：銷售代表看到自己的，銷售經理看到整個團隊的，管理員看到全部。客服可以在工單上記錄並查看自己的活動記錄。
- **參與者記錄目前的表現不同。** 對它的存取本應從會議衍生，但在目前的平台上這條衍生不會按歸屬收窄，因此任何權限集授予了「活動參與者」讀取權限的使用者，都能讀到他打不開的那些會議的參與者記錄。在把這個物件授予更大範圍的人群之前請記住這一點；收窄是平台側正在推進的修復，而不是一個應用設定。

## AI assistant 如何提供幫助

因為會議現在是一筆普通記錄，assistant 的 **Live Data** 技能可以像讀任何其他物件一樣讀它——*「上個季度我們和 Acme 開了多少次會？」*、*「我的哪些客戶 60 天內沒有任何互動？」*——而且是對著即時 schema 讀的，所以你今天新增的欄位在同一段對話裡就能用上。沒有任何技能會寫入活動記錄；寫入者就是上面那三個按鈕。

## 給銷售代表的建議

- ✅ 從**商機或工單**上記錄電話，而不是從客戶上——這條關聯決定了它會出現在哪筆記錄上，而客戶上的時點戳無論如何都會替你蓋好。
- ✅ 記得回頭把會議改成**已舉行**。一個滿是「已計劃」的日曆既不能告訴經理任何事，也不推進任何客戶的時鐘。
- ✅ 把真實的參與者填進去。「客戶方有誰從來沒參加過電話會議？」只有你填了才答得出來。
- ✅ 用活動記錄上的**會後紀要**寫下達成了什麼共識——記錄表單裡的備註寫的是聊了什麼，會後紀要寫的才是下一個人需要的東西。

## 給管理員的建議

- ✅ 輔導要盯**已舉行**，而不是盯數量：沉默客戶磁貼的誠實程度，取決於這個狀態欄位。
- ✅ 關注**客戶未到**——某個客戶的爽約率上升，往往遠早於續約就已經是一個流失訊號。
- ✅ 活動是私有物件。如果某位經理反映日曆是空的，先檢查其權限集的記錄範圍，再去懷疑資料。
- ✅ 為 UTC 以外時區的團隊撰寫內部操作指引時，記得寫上開始時間按 UTC 填寫這件事。
