# 新特性

## v1.0 —— HotCRM，会自我重写的 CRM

**首次发布。** HotCRM v1 面向那些厌倦了等待 CRM 供应商在下个季度添加他们所需字段的团队。你添加字段；AI 在你下次询问时就会用上它。本次发布中有三件事让它有别于你以往用过的每一个 CRM。

### ✨ 惊艳点 #1 —— 实时模式，实时 AI

在管理控制台中添加一个字段。十秒后，向助手询问与它相关的问题。它已经知道了。无需重新训练、无需重启、无需重新部署 —— 平台在每个智能体回合都会重新读取元数据，而 Copilot 的 `describe_object` 工具一保存就会返回你的新字段。

用我们随附的脚本在 30 秒内试一试：

```bash
HOTCRM_TOKEN=... ./scripts/wow1-live-schema.sh
```

### 💬 惊艳点 #2 —— 聊天优先的记录页

打开任意客户、商机、工单或合同。Copilot 始终在浮动聊天气泡中一键可达 —— 而且它已经把实时模式**以及**这条记录纳入了上下文。问它：

- “给我这个客户的全貌。”
- “给主要联系人起草一封跟进邮件。”
- “接下来我应该采取的 3 个动作是什么？”

每个记录页底部的讨论信息流捕捉来回对话，使其成为机构记忆，而不是下个季度没人能找到的 Slack 线程。

### 🛠️ 惊艳点 #3 —— 对盒子里有什么诚实以待

我们不会假装平台能做它做不到的事情。自然语言**流程构建器**是我们设计的一项平台能力（[ADR-0010](https://github.com/objectstack-ai/framework/blob/main/docs/adr/0010-nl-to-flow-authoring.md)），它在路线图上，但不随 v1 发布。确实随附的是：每个业务对象、视图、页面、仪表盘、角色和种子记录都是一个普通的 TypeScript 文件，你可以编辑、对比和提交它 —— 而且你一保存，AI 就能看到这些编辑。

### v1.0 包含什么

- **15 个业务对象**，横跨销售 / 服务 / 营销 / 营收。
- **Sales Copilot**，具备 5 项技能：实时数据、线索资格评估、邮件起草、营收预测、客户 360°。
- **管理层仪表盘** + 9 份预构建报告。
- **精简的导航** —— 5 个核心界面（销售、服务、洞察、审批），让新用户在 30 秒内找到方向。
- **演示种子** —— Acme Corporation 是一个完整成形的客户（3 个商机、2 个工单、1 份合同、3 个叙述性任务、一份 1KB 的战略简报），因此你一登录，Copilot 就有真实素材可供总结。

准备好试试了吗？`pnpm install && pnpm demo:reset && pnpm dev`，然后打开 http://localhost:4001 并创建第一个管理员账户。

## v6.0.0 —— 最新发布

**HotCRM 6.0.0** 全线 `@objectstack/*` 包发布时运行在 **ObjectStack 18.0.0** 上（平台 18
大版本的首个正式版）。它之后的版本运行在 **ObjectStack 18.1.0** 上，应用清单声明了与之匹配的
`^18.1.0` 协议区间，因此协议大版本不同的运行时
（包括 17.x 的宿主）会在装载之初就带着结构化诊断拒绝加载，而不是在某次 schema 解析的
深处才失败。5.1.2、5.1.1 与 5.1.0 运行在 ObjectStack 18.0.0-next.3 上，5.0.0 运行在
ObjectStack 18.0.0-next.2 上，4.0.1 运行在 ObjectStack 17.7.0 上。

> **这一页不维护第二张发布表。** 逐版本的发布历史在仓库的 `CHANGELOG.md` 里，由每个
> 拉取请求补充的 `.changeset/` 条目编译而成。v1.0 与 6.0.0 之间的各个版本都记录在那里，
> 这里刻意不再重列一遍 —— 手工誊抄那份历史，正是这一节曾在应用还是 2.2.2 时就宣称
> 「v5.0」、并把它挂在一个从未发布过它的平台大版本上的原因。

### 6.0.0 改变了什么

**6.0.0 是大版本，因为升级到它需要你动手。** 在 ObjectStack 18.0.0 接管数据库之前必须先迁移
数据库，Service Manager 权限集退役，三个市场活动操作的 API 结构也变了 —— 本节末尾的检查清单
说明了该怎么做。平台从 18.0.0-next.3 升到 18.0.0（中间经过 18.0.0-next.5），全部
`@objectstack/*` 包一起升级。它仍然需要 ObjectStack 18 的宿主。

- **受邀的同事不分配权限集也能打开 CRM。** 新的权限集 **CRM User**（`crm_user`）是这个包的
  默认权限集：它在 **Marketplace** 里的包页面会建议授予所有已登录成员，点一次 **Grant** 即可。
  它让每个成员处理自己的线索、客户、商机、任务和活动，并读取产品、市场活动和知识库目录；
  它不能删除、也不能导出任何数据。在自托管的 `objectstack serve` 上，每个已登录成员一开始就持有它。
- **每张报表都有侧边栏入口**，放在新的 **报表** 分组里，位于列表最后。
- **每个岗位都写明它授予的权限集**，所以 Setup 能看出谁持有什么。Service Manager 岗位现在
  授予 **Service Agent**，Service Manager 权限集随之退役。
- **市场活动的报名按你自己的权限进行。** Enroll Members、Add to Campaign 和 Mark Responded
  以使用者本人的身份运行，因此 Sales Rep 和 Sales Manager 不再看到它们。Enroll Members
  有人被拒绝时会如实说明，并给出两个数字；对未开放的市场活动会直接拒绝。
- **Convert Lead 在提交之前就说明线索会并入哪个客户。** 只有 Convert Lead 能把线索标为
  已转化；停在已转化却什么都没转化的线索可以重新编辑。
- **合同状态按既定路线流转。** Expired 和 Terminated 是终态；续约是一份新合同。
- **商机被审批锁定期间，它的明细行也被锁定**，所以金额始终与明细行一致。
- **公开的支持表单会询问访客的姓名和邮箱**，保存在工单的 **Supplied Name** 和
  **Supplied Email** 上，客服可以据此回复。
- **关闭工单会完成它的升级跟进任务**；**Escalate Case** 和 **Close Case** 只对有权编辑工单的人显示。
- **Pipeline by Stage** 磁贴和 **Opportunity Funnel by Owner → Stage** 报表**改为横向条形图**，
  按销售顺序每个阶段一条。
- **新建表单不再要求填写应用会自动补上的值**：明细行的 Sales Price、报价的 Expiration Date，
  以及预测的 Period End 和 Snapshot Date。

另有一长串修复 —— 拒绝提示的措辞与界面一致、All Forecasts 按最新在前排序、演示客户出现在
地图上、大额成交提醒中的金额带格式、私有商机的名称不再出现在任务标题里、文档按应用实测
重新校对 —— 每条都在 `CHANGELOG.md` 里有自己的条目。

**升级到 6.0.0 前后请检查：**

- **在 ObjectStack 18.0.0 接管数据库之前先升级数据库。** 每个 5.x 部署都运行在 18.0.0 的
  预发布宿主上，而在运行 `os migrate organization-ownership` 之前，18.0.0 会拒绝在预发布版
  创建的数据库上启动。步骤见 `CHANGELOG.md` 中 18.0.0 升级那一条。
- **直接分配过 Service Manager 权限集的人**，在这个版本之后从它得不到任何权限。请改为分配
  **Service Agent**，或者把 Service Manager 岗位给他们。
- **授予 CRM User 会叠加到每个权限集上。** 生效后，Marketing User 或 Service Agent 也能
  创建和编辑自己名下的客户和商机。
- **调用 Add to Campaign 的集成** 要把市场活动放在 `params.campaignId` 里发送；旧的
  `params.crm_campaign` 会被 `400` 拒绝。Add to Campaign 和 Mark Responded 的返回结构也变了；
  两者都写在 `CHANGELOG.md` 的对应条目里。
- **另一个源上的前端必须写进 `OS_CORS_ORIGIN`**，生产环境的 `os serve` 需要 `OS_AUTH_SECRET`。
- **从 5.1.1 或更早版本升级**，下面各节的全部内容同样适用。

### 5.1.2 修复了什么

- **没有产品编号的产品以名称作为标题，它的明细行也是。** HotCRM 开始自动生成产品编号之前
  建的产品原来根本没有标题，所以从 5.1.0 起，它们的明细行一直显示记录 ID，而且没办法修好。
  从 5.1.0 升上来以后，它们会和其他明细行一样在第一次显示时补上名字。
- 5.1.1 只发布到了 staging 市场；下面「5.1.1 修复了什么」里的内容随 5.1.2 一起进入生产。

### 5.1.1 修复了什么

**5.1.1 让 5.1.0 的明细行命名在托管环境上也能用。**

- **旧明细行会自动带上产品名。** 5.1.0 之前创建的明细行原来显示记录 ID，要跑一个托管环境
  跑不了的脚本才能改过来。现在列表或记录页第一次显示这样的明细时，这个产品的所有明细会在
  后台补上名字：第一次看到的仍是 ID，再打开就是产品名。
- **给明细很多的产品改名，每一行都会跟着改。** 在托管环境上，这个更新以前会停在半路；
  现在会一直进行到每一行都换成新名字。
- **每小时的 SLA 巡检不再覆盖已升级工单的升级原因和日期。**
- **每个市场活动成员都会有加入日期**，不论是怎么加进来的。

### 5.1.0 新增了什么

**能跑 5.0.0 的 ObjectStack 18 宿主都能跑 5.1.0。** 平台从 18.0.0-next.2 升到
18.0.0-next.3，全部 `@objectstack/*` 包一起升级。

- **销售主页的列表又能显示了。** 在 18.0.0-next.3 自带的控制台上，*My Leads*、
  *My Open Deals*、*My Open Tasks* 和 *Upcoming Events* 都显示「No object named」，
  什么也加载不出来。现在它们恢复正常。页面标题也改成了侧边栏入口的名字 **销售主页**。
- **每个角色打开自己的主页。** 销售代表进入 **销售主页**，客服专员和客服经理进入
  **服务概览**；经理、管理员和市场人员和以前一样进入 **主页**。
- **明细行以产品命名。** 商机和报价的明细行现在显示为它的产品，例如
  **PRD-0009 - Premium Support**，不再显示描述或原始记录 ID。
- **线索的「相关」页签** 除了未完成任务，还显示它的日程、它所在的市场活动，以及它转化成的记录。
- **任务有了「完成」按钮**，在任务所在的行上和任务的记录页上都有。
- **线索、客户和商机列表可以隐藏列**，在 **显示** 菜单里操作。这个选择只对你自己生效，
  保存在你的列表设置里。
- **你对示例记录的修改在重启后会保留。** 示例记录只在没有它们的数据库第一次启动时添加一次，
  之后的启动不再改动它们。

另有一长串修复 —— 每个客户最多一个主联系人、审批人显示为 **最后修改人**、提高优先级会提前
SLA 截止时间、已结算的明细行不能再删除、报价总额只读、线索卡片和日历、仪表盘数字卡片
只占一行、更完整的示例知识库 —— 每条都在 `CHANGELOG.md` 里有自己的条目。

**升级到 5.1.x 之后请检查：**

- **从 5.1.1 起，5.1.0 之前创建的明细行会在第一次显示时补上名字。** 什么都不用跑。
  自托管的运维如果想一次性全部补上，仍然可以运行
  `pnpm exec tsx scripts/backfill-line-product-title.ts --url https://YOUR-ORG --email ADMIN --password PASSWORD`
  （只报告，加上 `--apply` 才写入）。
- **在 Studio 里另存过的销售主页保留旧的列表写法。** 通过 Studio 保存过自己那份销售主页的
  部署会继续使用那份副本，而这个控制台不再读取它的 `objectName` / `viewType`。删掉副本即可
  回到包里的页面，或者用 `data` 和 `type` 重新保存。
- **从 4.x 升级**，下面「5.0.0 新增了什么」里的全部内容，包括其中的升级前检查，同样适用。

### 5.0.0 新增了什么

**5.0.0 之所以是大版本，是因为它需要 ObjectStack 18 的宿主。** 平台线从 17.7.0 走到了
18.0.0-next.2，分三步，全线 `@objectstack/*` 包与应用清单声明的协议区间一起移动。

- **租户管理员不再拥有 `manage_org_presentation`。** ObjectStack 18 退役了按组织的覆盖层，
  因此租户管理员不再编写任何元数据。
- **App Launcher 与 Utility Bar 两个页面下线。** 应用里没有任何入口能到达它们。切换应用请用
  控制台自带的应用切换器。
- **Sales Home 改成三栏，并在侧边栏 Home 之下有了自己的条目。** *Ask the AI Assistant* 与
  *Upcoming Events* 两张卡片位于关键指标的右侧。
- **报价单只有一种税。** 报价单明细不再带 **税率（%）**：报价单自己的 **税额** 就是税，
  明细行的 **总计** 等于它的 **小计**。
- **升级后的工单，被转走的那位客服仍能查看。** 新增的只读字段 **升级前负责人** 记下这位客服。
- **共用的选项列表只声明一次。** 行业、线索来源、称谓、付款条款与关联对象类型不再在提供它们的
  各个对象之间各自漂移。

此外还有一长串修复，每一条都在 `CHANGELOG.md` 里有自己的条目。

**升级前请检查这几件事：**

- **先把宿主升到 ObjectStack 18，并执行平台的迁移。** 数据库还是 17.x 的组织形态时，18 的
  运行时拒绝为它提供服务，直到运维执行 `os migrate organization-ownership`（先用
  `--out plan.json` 生成计划，再 `--apply --backup-taken --plan-file plan.json`）。
  这次迁移保留已有数据，不需要清空任何东西。
- **写 `crm_quote_line_item.tax_rate` 的集成**会被以 400 `INVALID_FIELD` 拒绝。已存的税率仍留在
  数据库里，不再被读取；`os migrate apply --allow-destructive` 会删除这一列，执行之前先把税率读出来。
- **17.x 下的岗位分配没有带组织的销售经理或服务经理**不会进入工单升级的人员池。请重新分配一次。
- **指向 App Launcher 或 Utility Bar 页面的书签会失效。**
- **从 3.x 升级时**，下方「4.0.0 新增了什么」连同其中的升级前检查同样适用。

### 4.0.1 修复了什么

**4.0.1 是第一个能从应用市场安装的 4.x 版本。** 4.0.0 发布到应用市场的是一个空应用，已被撤下，
因此停留在 3.x 的部署会直接升级到 4.0.1，下方「4.0.0 新增了什么」连同其中的升级前检查都适用于
这次升级。4.0.1 还让侧边栏徽标和网站图标在托管安装上正常显示。

### 4.0.0 新增了什么

**4.0.0 之所以是大版本，是因为联系人的邮寄地址合并成了一个字段。** 原来五个独立的地址字段被移除，
已有部署要把联系人地址转换一次（见下方的升级前检查）。这个版本同时让每笔销售记下更多信息。

- **销售记录承载了更多交易信息。** 客户记下它在纸面上是谁、花多少钱、可以向它卖什么，以及
  是否已经审批通过。联系人记下采购决策圈：此人在采购决策中的角色、对我们的态度，以及我们
  对他的了解程度。线索记下潜在客户需要什么、大致值多少。商机记下它是否值得投入、客户自己的
  采购时间表，以及这笔交易背后的来龙去脉。
- **公司做出承诺的环节有了审批。** 商机推进阶段之前的立项审批，以及客户登记、线索转化、
  商机赢单/丢单结论各自的审批。线索、立项与赢丢单这三道关默认关闭，由管理员逐一开启。
- **每条通知都以收件人自己的语言送达。** 同一条提醒发给一位说中文的销售和一位说日语的经理，
  两人各自收到自己语言的版本。
- **报价单与合同跟随客户。** 销售现在能读到自己看得见的每个客户下的报价单与合同，续约合同也包括在内。
- **联系人的邮寄地址合并为一个字段**，作为一个整体显示和编辑，与客户的账单地址同一形态。
  联系人导入模板保留原来的五个地址列。
- **HotCRM 以一个应用、两个包的形式安装**：HotCRM 应用，以及承载工单与知识库的 Service 模块。
- **平台线从 17.4.0 走到了 17.7.0**，分三步，全线 `@objectstack/*` 包与应用清单声明的协议区间
  一起移动。

此外还有一长串修复，每一条都在 `CHANGELOG.md` 里有自己的条目。

**升级前请检查这几件事：**

- **在执行 `os migrate apply --allow-destructive` 之前，把联系人地址转换一次。** 升级不会搬动
  联系人旧的地址字段，而那条命令会删除它们。`CHANGELOG.md` 里邮寄地址那一条给出了两条命令。
- **读写联系人 `mailing_street` … `mailing_country` 的集成**，必须改用 `mailing_address` 及其各个部分。
- **My Cases 现在是 My Work 分组的最后一项。** 其他菜单项的位置都没有变。
- **对调用方看不见的记录发起写入，现在返回 404**，此前返回 403。
- **导入严格读取日期。** 像 `07/15/2026` 这样月份在前的单元格，现在会让该行失败，而不是被导入成另一个日期。

### 3.1.0 新增了什么

这是一个小版本：没有任何东西被改名，没有任何已存记录被重写，从 3.0.0 升级不需要执行迁移步骤。

- **「认领工单」按钮。** 把一张无人负责的工单从 **未分派 — 待分诊** 里领走，这件事一直是能做的
  —— 客服把它移到某个处理中的状态，认领接缝就会把操作者盖成负责人 —— 但界面上没有任何地方
  说过这一点。现在工单记录页头部和待分诊列表的行菜单里都有了这个动作：它问你要认领到哪个
  工作状态（默认「处理中」），然后把工单移过去。它**刻意不写归属列**；认领接缝仍然是那一列
  唯一的写入者。
- **平台线从 17.1.0 走到了 17.4.0**，分三步，全线 `@objectstack/*` 包与应用清单声明的协议区间
  一起移动。作者在 `src/` 里写的东西没有任何形态变化。
- **一套 SaaS / 多组织组合**，面向用一套 HotCRM 部署承载多个组织的运营方。
- **知识库的「复核队列」页签被移除。** 它返回的是全部已发布文章，只是按最久未复核在前排序；
  随着知识库变大，它会退化成「全部文章，换个排序」。`last_reviewed_at` 原封不动 —— 被移除的
  只是按它排序的那个页签。
- **产品目录的「默认税率（%）」被移除。** `crm_product.tax_rate` 只能通过 REST API 设置，而且
  没有任何一处合计读它。税额在真正参与计算的地方保持不变：报价单明细自己的税率，以及报价单
  上的税额。（后来的版本又退役了明细行自己的税率，报价单上的税额成为唯一的税。）

此外还有一长串修复，每一条都在 `CHANGELOG.md` 里有自己的条目。

**升级前唯一需要检查的一件事：** 有没有集成在通过 REST API 写 `crm_product.tax_rate`。该字段
已经不存在，所以这类写入会被拒绝，而不是被忽略。这个版本里没有其他任何东西移除或改名了
客户端可以寻址的对象。

### 从 2.x 升级 —— 负责人现在是同一个字段

**3.0.0 之所以是大版本，是因为改负责人现在真的会转移访问权。** 在此之前，每个业务对象带着*两个*
负责人：表单、视图和报表上你看得见的 **负责人**，以及平台用来做每一次访问判断的另一个隐藏列。
两者之间没有任何东西保持同步——改负责人会让记录在所有列表和报表里换人，却**完全不转移访问权**：
原负责人仍然看得见，新负责人始终拿不到。

HotCRM 现在只有一个负责人：平台的归属列。

对已有部署意味着什么：

- **转移负责人与编辑权限分开授权。** 因为它真的会转移访问权，改负责人现在是一项独立权限，
  而不是"能编辑这条记录"的附带效果。
- **执行一次回填。** 在 2.x 下有人改过负责人的部署，两个列已经不一致；`pnpm backfill:owner`
  会把它们对齐。该命令不会清空已有负责人，可以重复执行——它需要管理员账号，因为它执行的
  就是一次批量转移。如果从来没有人改过负责人，两列本就一致，回填会报告零处分歧。

完整条目（含按角色划分的转移权限表）见 `CHANGELOG.md` 的 `Major Changes` 一节。
