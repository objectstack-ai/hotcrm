# 工單

**工單**是一張客戶支援單據。每個客戶報告的問題、疑問或功能請求都以工單的形式存在，以便團隊能夠一致地路由、處理和解決它。

## 7 種工單狀態

| 狀態 | 含義 |
| --- | --- |
| ⚪ **New** | 剛收到，尚未分配給客服 *(預設)* |
| 🟠 **In Progress** | 客服正在積極處理 |
| 🟡 **Waiting on Customer** | 等待客戶回覆 |
| 🔵 **Waiting on Support** | 等待另一團隊（工程、財務等） |
| 🔴 **Escalated** | 上交給資深客服或管理層 |
| 🟢 **Resolved** | 修復已交付，等待客戶確認 |
| 🟢 **Closed** | 工單已完成 |

一個典型的快速解決工單：**New → In Progress → Resolved → Closed**。
一個典型的卡住工單：**New → In Progress → Waiting on Customer → In Progress → Resolved → Closed**。

## 4 個優先順序級別

| 優先順序 | 典型 SLA 目標 | 使用場景 |
| --- | --- | --- |
| 🔵 **Low** | 7 個工作日 | 外觀問題、低影響的疑問 *(預設)* |
| 🟠 **Medium** | 2 個工作日 | 標準問題，工作繼續 |
| 🔴 **High** | 8 小時 | 影響顯著，客戶不滿 |
| 🔴 **Critical** | 4 小時 | 生產中斷，需要立即回應 |

當工單被設為 **Critical** 時，支援經理會收到郵件通知。當某個客戶帳戶的工單被設為 **High** 時，工單會自動升級。

## 工單類型

| 類型 | 用於 |
| --- | --- |
| **Question** | 操作類諮詢 |
| **Problem** | 某項功能無法使用 |
| **Feature Request** | 客戶請求新功能 |
| **Bug** | 已確認的軟體缺陷 |

## 工單來源

工單的來源：**Email · Phone · Web · Chat · Social Media**。

這驅動報表（哪些渠道產生的工單量最大），並在工單從來訪渠道建立時自動填充（例如，郵件轉工單整合會將來源設為 Email）。

## 工單記錄儲存的內容

詳情介面分為 6 個區塊：

| 區塊 | 欄位 |
| --- | --- |
| **Case Information** | 工單編號、主題、描述、帳戶、聯絡人 |
| **Origin & Routing** | 來源、所有者、父工單 |
| **SLA & Priority** | 狀態、優先順序、類型、首次回應時間、SLA 截止日期、違約標記 |
| **Resolution** | 關閉日期、解決方案、客戶簽名 |
| **Escalation** *(預設折疊)* | 升級標記、升級日期、升級原因 |
| **System** *(預設折疊)* | 審計追蹤、時間戳 |

## 自動發生的事

- **首次回應時間**——客服第一次評論或回覆時標記。
- **關閉標記**——狀態變為 *Closed* 時自動設定。
- **關閉日期**——狀態變為 *Closed* 時標記為 NOW。
- **解決時間（小時）**——按 *Created date* 與 *Closed date* 之間的差值計算。
- **SLA 截止日期**——工單建立時根據優先順序計算。
- **SLA 違約標記**——如果解決時間超過 SLA 目標，則翻轉為 true。
- **帳戶的最後活動日期**——工單更新時刷新為今天。

## 內建規則

- **已關閉工單必須有解決方案**——解決方案欄位為空時無法關閉工單。
- **升級工單必須有升級原因**——解釋為何引入了資深客服。
- **狀態推進受強制約束**——你不能從 *New* 直接跳到 *Resolved* 而不經過 *In Progress*。

## 工作流自動化

- **緊急時通知**——當優先順序被設為 Critical 時，工單升級流程的 `notify` 節點發出站內訊息 + 郵件，只發給**工單負責人一人**：收件人列表只有 `{caseRecord.owner_id}` 這一項。本應用中不存在 `support_manager@example.com` 這個收件人。
- **升級時通知**——當狀態變更為 *Escalated* 時，不會發出任何郵件：`escalation_team@example.com` 在本應用中根本不存在，也不存在「升級團隊」這樣一個收件目標。狀態轉為已升級真正觸發的是 `case_status_side_effects` 鉤子，它開出的是一條**次日到期、優先順序為緊急、歸帳戶負責人的跟進任務**——且僅限有關聯帳戶的工單，因為該任務是掛在那個帳戶上的。
- **計算解決時間**——關閉時自動進行。
- **自動設定關閉日期和標記**——狀態變更時。

## 工單升級

[工單升級流程](/zh-Hant/docs/service/sla-and-escalation#case-escalation)在以下情況下自動執行：

- 優先順序為 **Critical**，或
- 優先順序為 **High** 且帳戶為 **Customer**（非潛在客戶）

它會執行：

1. **重新分配**工單給客服的經理。
2. **標記**為已升級，標記升級日期。
3. **設定狀態**為 *Escalated*。
4. **建立一個跟進任務**給原客服，明天到期。
5. **透過郵件通知**客服、經理和支援團隊。

完整機制參見 [SLA 與升級](/zh-Hant/docs/service/sla-and-escalation)。

## 共享——誰可以看到哪個工單

- 預設情況下，工單是**私有的**——只有所有者和角色層級中的上級經理可見。
- **緊急未結工單**會自動共享（讀/寫）給所有服務經理及其下屬。緊急問題會獲得全團隊可見性。

## 欄位級安全

- **SLA 違約標記**和**解決時間**對客服是**唯讀的**——這些是自動計算的，無法手動篡改。

## 標準列表檢視

- **My Open Cases**——你尚未關閉的工單。
- **Critical Cases**——優先順序 = Critical，所有所有者。
- **Cases Due Today**——SLA 截止日期是今天。
- **Breached SLA**——SLA 違約標記為 true。
- **Recently Closed**——過去 7 天內關閉的。
- **By Account**——按客戶分組。
- **Service Board**——按狀態分組的看板。

## 工單詳情佈局

打開一個工單時，你會看到：

- **頁首**——工單編號、主題、狀態徽章、優先順序徽章、SLA 倒數計時。
- **狀態路徑**——一個 Salesforce 風格的水平流程，顯示 New → In Progress → Waiting on Customer → Escalated → Resolved → Closed，讓客服一眼就能看出工單的進展和下一站。
- **客戶面板**——帳戶、主要聯絡人、合約等級、本月未結工單。
- **三個標籤頁：**
  - **Details**——完整的工單描述和解決方案、所有元資料欄位。
  - **Related**——子任務、附件、關聯商機、里程碑。
  - **Activity**——統一的時間線（下文詳述）。
- **AI 參考欄**——Service Copilot 的建議。

### 活動時間線

Activity 標籤頁是工單上發生過什麼的唯一可信來源。它將四個資料流合併為一個按時間排序的資訊流：

| 資料流 | 來自哪裡 | 你會看到什麼 |
|--------|---------------------|------------------|
| **評論** | 隊友或客戶在工單上發布 | 主題式討論、@提及、內部/外部可見性 |
| **已記錄通話** | "Log a Call" 操作——儲存為類型為 *completed* 的 `sys_activity` | 通話主題、時長、結果、記錄人 |
| **外發郵件** | "Send Email" 操作——透過 `sys_email` 排隊 | 主題、收件人、投遞狀態（queued / sent / bounced） |
| **欄位變更** | 工單上每個被追蹤欄位的每次變更 | 改了什麼、誰改的、何時、變更前 → 變更後 |

你無需配置任何這些內容——每個 CRM 物件都自帶 `trackHistory: true`，平台的 feeds 引擎會自動將評論、活動和審計日誌接入同一時間線。

> 提示——如果你只想看討論，使用 Activity 標籤頁頂部的篩選下拉選單；你也可以從那裡訂閱該工單，這樣任何未來的發布都會在鈴鐺中提醒你。

## AI Copilot 如何提供幫助

[服務技能](/zh-Hant/docs/ai-copilot/service-copilot) 會在任何工單上自動啟動。你可以問：

- *"分流這個工單"*——工單分流技能根據主題和描述推薦優先順序。
- *"建議一個解決方案"*——沒有哪個技能能端到端做完這件事。**工單分流**只宣告了 `describe_object` 與 `get_record` 兩個工具，完全沒有檢索類工具，因此它什麼都不檢索。請向 **Customer 360°** 要按工單分類或標籤匹配出來的已發布[知識文章](/zh-Hant/docs/service/knowledge-base)，再向**郵件撰寫**要客戶回覆——草稿的依據是聯絡人與帳戶記錄，而不是那些文章，需要援引哪一篇請自己貼進去。
- *"Customer 360"*——拉取完整的帳戶上下文（未結商機、過往工單、合約等級）。

如果 Copilot 判斷優先順序為 *Critical*，它還會建議立即升級並起草內部通知訊息。

## 給服務客服的提示

- ✅ **及時分流來訪工單**——*New* 工單的等待時間不應超過首次回應 SLA。
- ✅ **當你被阻塞時使用 "Waiting on Customer"**——在某些配置中它會停止 SLA 計時。
- ✅ **始終寫下解決方案**——這是強制的，但也會為未來的工單提供知識庫素材。
- ✅ **關聯一個任務**——當工單需要未來跟進時（例如"7 天後驗證修復是否有效"）。
- ❌ 不要在未確認修復有效之前關閉工單。

## 給服務經理的提示

- ✅ 每天關注 **Breached SLA** 檢視——每個紅色徽章都代表一次客戶信任事件。
- ✅ 使用 **Service Board** 看板進行每日站會。
- ✅ 輔導那些 **Resolution Time** 趨勢上升的客服——客服排行榜上有相應的欄。

## 給管理員的提示

- 每個優先順序的 SLA 目標儲存在工單物件的自動化中。要更改它們，請編輯工單自動化——參見 [管理 › 自動化](/zh-Hant/docs/administration/automation)。
- `escalation_team@example.com` 和 `support_manager@example.com` 都沒有在任何地方設定過——這兩個地址在本應用中根本不存在。真實存在的收件人列表只有一處：工單升級流程 `notify` 節點的 `recipients: ['{caseRecord.owner_id}']`，即工單負責人一人；它在 `src/flows/case-escalation.flow.ts` 裡改，不是 Setup 介面上的設定項。
- 郵件轉工單接入（從來訪郵件自動建立工單）需要郵件外掛——參見 [定制 › 擴展物件](/zh-Hant/docs/customization/extending-objects)。
