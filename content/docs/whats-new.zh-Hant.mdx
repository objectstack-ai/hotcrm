# 新功能

本應用未隨附繁體中文語言包，因此本頁出現的介面名詞依固定順序取用：zh-CN 語言包已收錄者，採其用詞的繁體寫法；未收錄者，保留產品內的英文原名，不另造譯名。

## v1.0 —— HotCRM，會自我重寫的 CRM

**首次發行。** HotCRM v1 面向那些厭倦了等待 CRM 供應商在下個季度新增他們所需欄位的團隊。你新增欄位；AI 在你下次詢問時就會用上它。本次發行中有三件事讓它有別於你以往用過的每一個 CRM。

### ✨ 驚艷點 #1 —— 即時結構描述，即時 AI

在管理主控台中新增一個欄位。十秒後，向助手詢問與它相關的問題。它已經知道了。無需重新訓練、無需重新啟動、無需重新部署 —— 平台在每個智慧代理回合都會重新讀取中繼資料，而 Copilot 的 `describe_object` 工具一儲存就會傳回你的新欄位。

用我們隨附的指令稿在 30 秒內試一試：

```bash
HOTCRM_TOKEN=... ./scripts/wow1-live-schema.sh
```

### 💬 驚艷點 #2 —— 聊天優先的記錄頁

開啟任意客戶、商機、工單或合約。Copilot 始終在浮動聊天氣泡中一鍵可達 —— 而且它已經把即時結構描述**以及**這筆記錄納入了範圍。問它：

- 「給我這個客戶的全貌。」
- 「給主要聯絡人草擬一封跟進電子郵件。」
- 「接下來我應該採取的 3 個動作是什麼？」

每個記錄頁底部的討論訊息摘要捕捉來回對話，使其成為機構記憶，而不是下個季度沒人能找到的 Slack 討論串。

### 🛠️ 驚艷點 #3 —— 對盒子裡有什麼誠實以待

我們不會假裝平台能做它做不到的事情。自然語言**流程建構器**是我們設計的一項平台能力（[ADR-0010](https://github.com/objectstack-ai/framework/blob/main/docs/adr/0010-nl-to-flow-authoring.md)），它在路線圖上，但不隨 v1 發行。確實隨附的是：每個業務物件、檢視、頁面、儀表板、角色和種子記錄都是一個普通的 TypeScript 檔案，你可以編輯、比對和提交它 —— 而且你一儲存，AI 就能看到這些編輯。

### v1.0 包含什麼

- **15 個業務物件**，橫跨銷售 / 服務 / 行銷 / 營收。
- **Sales Copilot**，具備 5 項技能：即時資料、潛在客戶資格評估、電子郵件草擬、營收預測、客戶 360°。
- **管理層儀表板** + 9 份預先建置的報告。
- **精簡的導覽** —— 5 個核心介面（銷售、服務、洞察、簽核），讓新使用者在 30 秒內找到方向。
- **示範種子** —— Acme Corporation 是一個完整成形的客戶（3 個商機、2 個工單、1 份合約、3 個敘述性任務、一份 1KB 的策略簡報），因此你一登入，Copilot 就有真實素材可供總結。

準備好試試了嗎？`pnpm install && pnpm demo:reset && pnpm dev`，然後開啟 http://localhost:4001 並建立第一個管理員帳戶。

## v6.5.0 —— 最新發行

**HotCRM 6.5.0** 全線 `@objectstack/*` 套件執行在 **ObjectStack 18.5.0** 上，應用清單宣告了與之相符的 `^18.5.0` 協定區間，因此協定大版本不同的執行時（包括 17.x 的宿主）會在
載入之初就帶著結構化診斷拒絕載入，而不是在某次 schema 解析的深處才失敗。6.3.0、6.2.1 與 6.2.0 執行在
ObjectStack 18.4.0 上；6.1.2、6.1.1 與 6.1.0 執行在
ObjectStack 18.3.0 上，6.0.0 執行在
ObjectStack 18.0.0 上，5.1.2、5.1.1 與 5.1.0 執行在 ObjectStack 18.0.0-next.3 上，5.0.0 執行在
ObjectStack 18.0.0-next.2 上，4.0.1 執行在 ObjectStack 17.7.0 上。

**停在 6.4.0 的環境只需閱讀「6.5.0 改變了什麼」。** 6.4.0 是 6.2.0 之後第一個發行的版本；6.2.1 和 6.3.0 在儲存庫裡切出了版本，但沒有發行，
所以仍停在 6.2.0 的環境還要閱讀下面的「6.4.0 改變了什麼」「6.3.0 改變了什麼」和「6.2.1 改變了什麼」，以及它們要檢查的事項。

> **這一頁不維護第二張發行表。** 逐版本的發行歷史在儲存庫的 `CHANGELOG.md` 裡，由每個
> 拉取請求補上的 `.changeset/` 條目編譯而成。v1.0 與 6.5.0 之間的各個版本都記錄在那裡，
> 這裡刻意不再重列一遍 —— 手工謄抄那份歷史，正是這一節曾在應用還是 2.2.2 時就宣稱
> 「v5.0」、並把它掛在一個從未發行過它的平台大版本上的原因。

### 6.5.0 改變了什麼

- **每個專案都有計畫。** **項目任務**組成任務樹，帶計畫起訖日期和工時、負責人、里程碑和前置任務，專案頁面把它們畫成**甘特圖**。
  應用新增**項目計劃**、**任務樹**和**我的項目任務**。工時記錄可以關聯任務，任務的**實際工時**隨之累計。專案的**完成百分比**改為按任務計算，
  以計畫工時加權。專案經理編寫計畫，團隊成員和財務唯讀。
- **一週的工時在一處錄入。** 工時記錄現在帶**項目**，會自動找到這個人在該專案、該週的工時單，沒有就新建一張草稿。
  **我的本週**、**我的工時**和**提交本週**（可批次**提交**）取代了手動建工時單。每個專案仍各有自己的工時單和審批。
- **預算分版本。** **項目預算**帶**預算明細**，提交後鎖定。第 1 版隨專案一起審批；追加預算交給專案總監或專案管理辦公室審批，
  使基線提高 10% 及以上時還要財務審批。獲批的版本成為**基線**，專案的**批准預算**改為基線合計，唯讀。
- **訂單與回款的示範資料**、合約生效和報價接受必須有客戶簽字件、多付的發票按已付清計算、管理層唯讀權限集、在地化的規則提示，以及許多小修正。
  完整清單見 `CHANGELOG.md`。

**升級到 6.5.0 前後要檢查的：**

- **平台不變。** 6.5.0 仍執行在 ObjectStack 18.5.0 上。
- **6.5.0 之前儲存的專案保留原來手填的核准預算**，直到有預算版本獲批。`scripts/backfill-project-budget-baseline.ts` 可以把它轉成第 1 版；
  不加 `--apply` 時只輸出報告，升級過程不會執行它。
- **示範資料還不能隨應用市集安裝下發**（objectstack#34336）：訂單與回款、專案交付的示範記錄只在全新啟動時載入。

### 6.4.0 改變了什麼

- **專案交付：新模組，自帶應用。** HotCRM 現在發行第六個套件 `app.objectstack.hotcrm.psa`，以及 **Project Delivery**（專案交付）應用。
  **Project**（售前、交付或內部）掛在客戶下，可以關聯商機和合約。人員以 **Project Member** 的身分按 **Rate Card**（成本費率與計費費率）
  安排到專案上，在 **Timesheet** 上記工時，用 **Expense** 報銷支出。核准後的工時和費用會帶動專案的成本、預算使用率和毛利，這些數字都不用手填。
- **專案審批與成本控制。** 專案要有 **Approved Budget** 並通過審批才能進入進行中：Project Director 或 PMO 審批，預算達到 100,000 時還要 Finance Controller 審批。
  工時單交給專案經理審批，2,000 及以上的費用還要財務審批。**Budget Status** 在達到核准預算的 80% 時變為預警，達到 100% 時變為超支，
  跨過時會通知專案經理和財務。勾選 **Lock Time and Expenses** 後，這個專案不再接受新的提交。
- **Projects Overview 與 Project Delivery Manual。** 儀表板顯示預算、成本、毛利、按實際工作週統計的已核准工時，以及每個人的可計費占比，只統計看的人能讀到的專案。
  說明下的手冊解釋畫面上看不到的規則。
- **專案交付裡誰能看到什麼。** 五個新職位（Project Director、PMO、Project Manager、Project Team Member、Finance Controller）對應三個權限集。
  專案成員能讀專案的客戶，讀不到商機，也看不到成本費率和毛利。銷售經理能讀所有專案。
- **業務代表維護回款計劃，財務輸入發票和回款。** 回款節點、發票和回款現在只要求能讀所屬合約。業務代表可以維護任何自己能讀的合約的回款計劃，
  應收會計可以輸入和匯入發票與回款。讀不到合約的人，三樣都寫不了。6.3.0 發行時留下的這個缺口就此補上。
- **ObjectStack 18.5.0。** 平台升級本身不改 HotCRM 的中繼資料；上面的回款寫入和按週工時正是它帶來的。

**升級到 6.4.0 前後要檢查的：**

- **先把宿主升級到 ObjectStack 18.5.0**，並按平台的 18.5.0 升級清單逐項處理。
- **給交付角色指派職位。** 在 **Setup → People & Organization → Position Holders** 中指派 Project Director、PMO、Project Manager、Project Team Member 和 Finance Controller，
  再用一位專案經理登入，確認啟動器裡有 Project Delivery 應用。
- **財務現在可以儲存發票和回款了。** 下面 6.3.0 裡「由管理員輸入」的說明不再適用。用應收會計登入，在一份合約上儲存一張發票試試。
- **不做專案交付的租戶停用這個模組。** 停用 `app.objectstack.hotcrm.psa` 後，應用和它的物件會一起消失。

### 6.3.0 改變了什麼

- **訂單與回款：合約的回款計劃、發票和回款。** 合約下新增三個物件。**回款節點**組成回款計劃：什麼時候該收多少，
  其中多少已開票、已回款、還未回款。**發票**和**回款**由財務針對它記錄，可以手動輸入，也可以從 ERP 匯入；同一個
  檔案匯入兩次只會更新原有紀錄，不會重複。業務看到**逾期發票**和**本月計劃回款**兩個清單，並在合約和客戶頁面的
  分頁裡看到回款計劃、發票和回款。新增的**應收會計**職位（`crm_ar_accountant`）和權限集（`ar_accountant`）
  承載財務的權限。
- **合約和客戶上的應收彙總。** 合約的**合約金額**區段顯示**計劃回款**、**已開票**、**已回款**和**應收餘額**；客戶的
  **財務資訊**區段顯示它所有合約的**已開票**、**已回款**和**應收餘額**。**已開票**只統計已開立的發票，**應收餘額**
  是已開立發票上仍未付的金額，所以尚未對應到發票的預收款只計入**已回款**，不影響餘額。
- **「訂單與回款」成為財務自己的應用。** **Order to Cash** 應用（訂單與回款）包含發票、回款和回款計劃、兩個跟進
  清單、它們所屬的合約與客戶，以及《訂單與回款手冊》。應收會計的啟動器只提供這個應用；銷售經理和管理員四個應用
  都看得到；銷售代表、服務和行銷人員看不到它。Sales 應用保留**回款計劃**群組，放銷售代表和銷售經理維護的回款節點。
  停用這個模組的租戶，應用、物件和彙總會一起消失。

**升級到 6.3.0 前後要檢查的：**

- **財務暫時還不能儲存發票和回款。** 平台儲存發票或回款前，要求對所屬合約有編輯權限，而應收會計職位只能檢視合約。
  在平台發行解除這一限制之前（[objectstack#33250](https://github.com/objectstack-ai/objectstack/issues/33250)），
  發票和回款由管理員輸入和匯入，回款計劃由銷售經理或管理員建立。
- **升級前已有的合約和客戶，彙總顯示為空**，直到在它們下面寫入回款節點、發票或回款。彙總在寫入子紀錄時重新計算，
  而平台的補算工具目前還不能在 HotCRM 上執行（[objectstack#33608](https://github.com/objectstack-ai/objectstack/issues/33608)）。
  彙總為空表示這筆紀錄下還沒有任何紀錄。
- **給財務指派職位。** 把**應收會計**指派給記錄發票和回款的人，再用其中一人登入，確認啟動器裡有 Order to Cash 應用。

### 6.2.1 改變了什麼

- **職位改名後，任職人保持原來的職位。** 6.2.0 給十二個職位加上 `crm_` 前綴時，沒有告訴平台它們還是原來的職位，
  所以升級前已擔任職位的人，都悄無聲息地失去了職位給他們的權限。現在每個職位都寫明它原來的名字，6.2.1 第一次
  啟動時，平台以系統身分把每個組織裡擔任舊名職位的人都移到新名字下：不需要執行任何東西，託管環境和自架伺服器都
  一樣。已經升級到 6.2.0 的組織也按同樣的方式找回任職人。需要密碼的 `scripts/migrate-position-holders.ts` 已刪除。

**升級到 6.2.1 前後要檢查的：** 遷移發生在**啟動時**。在執行中安裝升級的環境，要到下一次重新啟動才遷移職位任職人，
所以升級後請重新啟動一次（在不重新啟動的安裝中遷移任職人屬於平台改動，記錄在
[objectstack#33238](https://github.com/objectstack-ai/objectstack/issues/33238)）。然後開啟
**Setup → People & Organization → Position Holders**，確認任職人都列在 `crm_` 名字下；再以業務經理身分登入，
確認能看到之前看到的客戶、商機和銷售預測。你在 Setup 裡按舊職位名新增的共享規則、佇列成員或記錄共享保留舊名字，
請把它改指向改名後的職位。從 6.1.2 或更早版本升上來時，「6.2.0 改變了什麼」下的檢查同樣適用。

### 6.2.0 改變了什麼

- **三個應用：Sales、Service 和 Marketing。** 所有角色共用的那一長串選單按工作領域拆開。**Sales**（原來的
  *HotCRM* 應用）保留潛在客戶、客戶、商機、報價單、合約、活動、洞察和銷售報表。**Service** 開啟在 Service Overview，
  包含工單、知識庫、客戶和工單報表，**Help** 下是 Service Manual。**Marketing** 開啟在 Campaigns，包含受眾，**Help** 下是
  Marketing Manual；它隨行銷模組一起出現和消失。每個角色的啟動器只列出工作需要的應用：業務代表看到 Sales，客服人員看到
  Service，行銷人員看到 Sales 和 Marketing，業務經理和管理員三個都看到。在應用市集上，每個應用歸在擁有它的套件下，
  停用一個模組會把它的應用一起帶走。
- **中文組織拿到中文示範資料。** 每套範例資料都有英文和簡體中文兩份，組織按自己的語言收到其中一份：同樣的客戶、
  商機、工單和行銷活動，金額和日期都相同，所以每個儀表板在兩種語言下讀數一致。
- **中日韓姓名姓在前。** 姓氏用中日韓文字書寫的聯絡人或潛在客戶，標題顯示為 張偉，而不是「偉 張」，清單、查找、
  頁首和搜尋都一致。其他姓名仍按「名 姓」顯示。
- **職位加上 `crm_` 前綴。** 十二個職位改名（`sales_rep` → `crm_sales_rep`），因為從 ObjectStack 18.4.0 起，
  職位名在一個環境裡由所有應用共用。顯示名不變。從 6.2.1 起，每個職位都寫明它原來的名字，升級後第一次啟動時，
  平台會把原來擔任它的人移到新名字下。6.2.0 本身不會：在 6.2.0 上，按舊名做的職位指派不授予任何權限（見下面的檢查）。
- **ObjectStack 18.4.0。** 一個人關聯的記錄必須是他能開啟的；List Price by Category 圖表移到獨立的
  **Product Catalog** 儀表板；銷售預測的標題隨負責人改名而更新；Send Email 從部署設定的寄件地址寄出，回覆地址是
  業務代表本人。每一項在 `CHANGELOG.md` 裡都有完整條目。

**升級到 6.2.0 前後要檢查的：** 先把宿主升級到 ObjectStack 18.4.0；使用 PostgreSQL 或 MySQL 時，同時執行
`os migrate apply`。請安裝 6.2.1 而不是 6.2.0：它第一次啟動時就把每個組織裡的職位任職人移到 `crm_` 名字下，
不需要執行任何東西。遷移發生在啟動時，所以在執行中安裝升級的環境，要到下一次重新啟動才遷移；在那之前，舊的職位指派
不授予任何權限。遷移之後，**Setup → People & Organization → Position Holders** 裡的任職人都列在新名字下。你在 Setup 裡按舊職位名新增的
共享規則、佇列成員或記錄共享保留舊名字，請把它改指向改名後的職位。然後以業務代表身分登入，啟動器上能看到 Sales 應用；以管理員身分
登入，能看到全部三個應用。從 6.1.1 或 6.0.0 升上來時，前面各節的檢查同樣適用。

### 6.1.2 改變了什麼

- **服務人員有了自己的手冊。** **Help** 下新增 **Service Manual**（服務手冊）：工單與 SLA、知識庫，以及新工單如何分派。

- **Pipeline by Stage** 磁貼和 **Opportunity Funnel by Owner → Stage** 報表**改為橫向長條圖**，
  依銷售順序每個階段一條。

- **寫入 `crm_quote_line_item.tax_rate` 的整合**會被以 400 `INVALID_FIELD` 拒絕。已存的稅率仍留在
  資料庫裡，不再被讀取；`os migrate apply --allow-destructive` 會刪除這一欄，執行之前先把稅率讀出來。
- **17.x 下的職位分配沒有帶組織的銷售經理或服務經理**不會進入工單升級的人員池。請重新分配一次。
- **指向 App Launcher 或 Utility Bar 頁面的書籤會失效。**
- **從 3.x 升級時**，下方「4.0.0 新增了什麼」連同其中的升級前檢查同樣適用。

### 4.0.1 修復了什麼

**4.0.1 是第一個能從應用市集安裝的 4.x 版本。** 4.0.0 發行到應用市集的是一個空應用，已被撤下，
因此停留在 3.x 的部署會直接升級到 4.0.1，下方「4.0.0 新增了什麼」連同其中的升級前檢查都適用於
這次升級。4.0.1 也讓側邊欄標誌與網站圖示在託管安裝上正常顯示。

### 4.0.0 新增了什麼

**4.0.0 之所以是大版本，是因為聯絡人的郵寄地址合併成了一個欄位。** 原來五個獨立的地址欄位被移除，
既有部署要把聯絡人地址轉換一次（見下方的升級前檢查）。這個版本同時讓每筆銷售記下更多資訊。

- **銷售記錄承載了更多交易資訊。** 客戶記下它在書面上是誰、花多少錢、可以向它賣什麼，以及
  是否已經審批通過。聯絡人記下採購決策圈：此人在採購決策中的角色、對我們的態度，以及我們
  對他的了解程度。潛在客戶記下對方需要什麼、大致值多少。商機記下它是否值得投入、客戶自己的
  採購時間表，以及這筆交易背後的來龍去脈。
- **公司做出承諾的環節有了審批。** 商機推進階段之前的立項審批，以及客戶登記、潛在客戶轉換、
  商機贏單／丟單結論各自的審批。潛在客戶、立項與贏丟單這三道關預設關閉，由管理員逐一開啟。
- **每則通知都以收件人自己的語言送達。** 同一則提醒發給一位說中文的業務和一位說日語的經理，
  兩人各自收到自己語言的版本。
- **報價單與合約跟隨客戶。** 業務現在能讀到自己看得見的每個客戶底下的報價單與合約，續約合約也包括在內。
- **聯絡人的郵寄地址合併為一個欄位**，作為一個整體顯示和編輯，與客戶的帳單地址同一形態。
  聯絡人匯入範本保留原來的五個地址欄。
- **HotCRM 以一個應用、兩個套件的形式安裝**：HotCRM 應用，以及承載工單與知識庫的 Service 模組。
- **平台線從 17.4.0 走到了 17.7.0**，分三步，全線 `@objectstack/*` 套件與應用清單宣告的協定
  區間一起移動。

此外還有一長串修復，每一條都在 `CHANGELOG.md` 裡有自己的條目。

**升級前請檢查這幾件事：**

- **在執行 `os migrate apply --allow-destructive` 之前，把聯絡人地址轉換一次。** 升級不會搬動
  聯絡人舊的地址欄位，而那條命令會刪除它們。`CHANGELOG.md` 裡郵寄地址那一條給出了兩條命令。
- **讀寫聯絡人 `mailing_street` … `mailing_country` 的整合**，必須改用 `mailing_address` 及其各個部分。
- **My Cases 現在是 My Work 群組的最後一項。** 其他選單項的位置都沒有變。
- **對呼叫方看不見的記錄發起寫入，現在回傳 404**，此前回傳 403。
- **匯入嚴格讀取日期。** 像 `07/15/2026` 這樣月份在前的儲存格，現在會讓該列失敗，而不是被匯入成另一個日期。

### 3.1.0 新增了什麼

這是一個小版本：沒有任何東西被改名，沒有任何已存記錄被重寫，從 3.0.0 升級不需要執行遷移步驟。

- **「認領工單」按鈕。** 把一張無人負責的工單從 **未分派 — 待分診** 裡領走，這件事一直是能做的
  —— 客服把它轉到某個處理中的狀態，認領接縫就會把操作者蓋成負責人 —— 但介面上沒有任何地方
  說過這一點。現在工單記錄頁頭部和待分診清單的列選單裡都有了這個動作：它問你要認領到哪個
  工作狀態（預設「處理中」），然後把工單移過去。它**刻意不寫歸屬欄**；認領接縫仍然是那一欄
  唯一的寫入者。
- **平台線從 17.1.0 走到了 17.4.0**，分三步，全線 `@objectstack/*` 套件與應用清單宣告的協定
  區間一起移動。作者在 `src/` 裡寫的東西沒有任何形態變化。
- **一套 SaaS / 多組織組合**，面向用一套 HotCRM 部署承載多個組織的營運方。
- **知識庫的「複核佇列」頁籤被移除。** 它回傳的是全部已發佈文章，只是按最久未複核在前排序；
  隨著知識庫變大，它會退化成「全部文章，換個排序」。`last_reviewed_at` 原封不動 —— 被移除的
  只是按它排序的那個頁籤。
- **產品目錄的「預設稅率（%）」被移除。** `crm_product.tax_rate` 只能透過 REST API 設定，而且
  沒有任何一處合計讀它。稅額在真正參與計算的地方保持不變：報價單明細自己的稅率，以及報價單
  上的稅額。（後來的版本又退役了明細行自己的稅率，報價單上的稅額成為唯一的稅。）

此外還有一長串修復，每一條都在 `CHANGELOG.md` 裡有自己的條目。

**升級前唯一需要檢查的一件事：** 有沒有整合在透過 REST API 寫 `crm_product.tax_rate`。該欄位
已經不存在，所以這類寫入會被拒絕，而不是被忽略。這個版本裡沒有其他任何東西移除或改名了
客戶端可以定址的物件。

### 從 2.x 升級 —— 負責人現在是同一個欄位

**3.0.0 之所以是大版本，是因為改負責人現在真的會轉移存取權。** 在此之前，每個業務物件帶著*兩個*
負責人：表單、檢視和報表上你看得見的 **負責人**，以及平台用來做每一次存取判斷的另一個隱藏欄。
兩者之間沒有任何東西保持同步——改負責人會讓記錄在所有清單和報表裡換人，卻**完全不轉移存取權**：
原負責人仍然看得見，新負責人始終拿不到。

HotCRM 現在只有一個負責人：平台的歸屬欄。

對既有部署意味著什麼：

- **轉移負責人與編輯權限分開授權。** 因為它真的會轉移存取權，改負責人現在是一項獨立權限，
  而不是「能編輯這筆記錄」的附帶效果。
- **執行一次回填。** 在 2.x 下有人改過負責人的部署，兩個欄已經不一致；`pnpm backfill:owner`
  會把它們對齊。該命令不會清空既有負責人，可以重複執行——它需要管理員帳號，因為它執行的
  就是一次批次轉移。如果從來沒有人改過負責人，兩欄本就一致，回填會報告零處分歧。

完整條目（含按角色劃分的轉移權限表）見 `CHANGELOG.md` 的 `Major Changes` 一節。
