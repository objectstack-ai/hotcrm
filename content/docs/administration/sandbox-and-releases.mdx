# Sandbox & Release Management

Never make config changes directly in production. This page covers the safe workflow: build in a sandbox, test, package, promote to production, rollback if needed.

**None of the screens named below exist.** Setup ships no *Sandbox Management*, no *Change Packages* and no *Git Sync* entry — its navigation is Overview, Apps, People & Organization, Access Control, Approvals, Configuration, Diagnostics, Integrations and Advanced, and nothing under them provisions a tenant or assembles a change set. What follows is the intended shape of release management, kept because the discipline it teaches is the right one. What HotCRM does today: its metadata is TypeScript under `src/`, reviewed in git and shipped with the app; installed packages are listed at **Setup → Packages**.

## What's a sandbox?

A **sandbox** is a full-fidelity copy of your production tenant — same schema, optionally same data — running in isolation, so you can break it without consequence. That is the concept, and it is a real one in ObjectStack. It is just not a thing this tenant contains.

| Sandbox type | What's in it | Refresh frequency |
| --- | --- | --- |
| **Config only** *(not shipped)* | Schema + metadata only, no records | On demand *(unsourced)* |
| **Partial data** *(not shipped)* | Schema + a small sample of records | Weekly *(unsourced)* |
| **Full copy** *(not shipped)* | Schema + all production data (anonymised) | Monthly *(unsourced)* |

*Not shipped, and not this shape anywhere.* There is no `sys_sandbox` object, and no `sandboxType` key or config/partial/full taxonomy exists in any installed package. The real thing this table is reaching for is the ObjectStack **Cloud** *environment*, declared in `@objectstack/spec/cloud` as `EnvironmentSchema` — one row per logical runtime of an organization's data, with its own database, credentials and members. Its `type` is a seven-member enum:

```
production | sandbox | development | test | staging | preview | trial
```

So `sandbox` is a real value — but it is an **environment posture**, not a data-fidelity tier, and the three refresh cadences above correspond to nothing. Environments live in the control plane and are addressed over `/api/v1/cloud/environments/…`, not from a page inside this tenant.

Enterprise plans typically include **3 sandboxes**; add more as needed. **Not shipped.** No sandbox-count entitlement exists anywhere — no `sandboxLimit`, `maxSandboxes` or `sandboxQuota` in any installed package. The Cloud `EnvironmentSchema` does carry a `plan` field (`free | starter | pro | enterprise | custom`), but the only quota hanging off it is `storageLimitMb`; nothing counts environments. Whatever your commercial plan says, it is not describing a capability this app can show you.

## Creating & refreshing a sandbox

The intended flow: a *Sandbox Management* screen where you pick a **type** (config / partial / full), name it (`dev`, `uat`, `training`) and click **Create**, with a **Refresh** on each row that pulls the latest production data down again — wiping whatever was in the sandbox.

There is no such screen. Provisioning an environment is a control-plane concern of ObjectStack Cloud, not a page inside this tenant's Setup; the only cloud entry Setup ships is **Setup → Cloud Connection**.

Worth knowing, because it is the one environment axis this app really can express: seed data declared in `objectstack.config.ts` is **per-environment**. Each `data[]` entry takes an `env` list, and the vocabulary is exactly three values:

```
data: [{ object: 'crm_account', env: ['prod', 'dev', 'test'], records: [...] }]
      env: ['sandbox'] → REJECTED — Invalid option: expected one of "prod"|"dev"|"test"
      env: ['uat']     → REJECTED — same
```

That is why the names in the intended flow above matter: `uat` and `training` are not spellings the platform knows, and neither is `sandbox` on this axis.

### Anonymisation on refresh *(not shipped)*

The intended behaviour: for full-copy sandboxes, PII is anonymised as the data is pulled down —

- Email addresses → `user-{id}@example-anon.test`
- Phone numbers → randomised but format-preserved
- Names → realistic-looking fake names
- Free-text fields → kept as-is (caveat — review for sensitive content)

— which would make a sandbox safe to hand to partners or contractors.

None of it exists. There is no anonymisation, pseudonymisation or fake-data generator in any installed package: zero hits for `anonymi[sz]`, `pseudonymi[sz]` or `fakeName` across the 1,158 non-map distribution files of the 51 installed `@objectstack/*` packages. There is no refresh to hang it on either, since there is no sandbox to refresh.

The one adjacent mechanism that *is* real, and is a different thing: `publicSharing.redactFields` on an object **drops** named fields from a record exposed through a public share link. It hides fields from one shared view; it does not transform values, does not produce fake ones, and has nothing to do with copying a tenant. Do not read it as anonymisation.

## The change workflow

```
┌───────────┐   build    ┌─────────┐   test    ┌─────────┐   promote   ┌────────────┐
│ Developer ├──────────▶│   dev   ├──────────▶│   uat   ├────────────▶│ production │
└───────────┘            └─────────┘           └─────────┘             └────────────┘
                                                                              │
                                                                       rollback│
                                                                              ▼
                                                                       last working
                                                                          package
```

1. **Build** the change in the `dev` sandbox.
2. **Promote** to `uat` — business users test there.
3. **UAT sign-off** required to proceed.
4. **Promote** to `production` during the change window.
5. **Smoke test** in production immediately.
6. **Rollback** if needed.

*Sound discipline, no in-app mechanism.* Nothing here is enforced or even visible to HotCRM: there is no promotion, no sign-off gate and no environment ladder inside the tenant. For this app the ladder is your git branches and your deployment pipeline, and every step above is something a human or CI does. Keep the discipline; do not look for a button.

## Change packages

A **change package** captures a set of metadata changes (objects, fields, validations, flows, sharing rules, etc.) as a single deployable artefact.

That artefact is real, and this is the one place the page's mental model is close to the truth — the unit is just produced by a build, not assembled by hand. `objectstack compile` emits a compiled `ObjectStackDefinitionSchema`, which the Cloud control plane wraps in an **Environment Artifact** (`EnvironmentArtifactSchema` — `environmentId`, `commitId`, SHA-256 `checksum`, plus the compiled definition) and serves to the runtime at boot. It is immutable and content-addressable. Separately, `ChangeSetSchema` in `@objectstack/spec/system` is the real *migration* unit: a named, ordered list of `add_field` / `rename_object` / `delete_object` / `execute_sql` operations with declared dependencies, recorded in `sys_migration` and `sys_migration_journal`.

### Creating a package

The intended flow: a *Change Packages → New* screen taking a name and description, components added by hand / by tag / automatically since the last package, then **Validate** for consistency and **Save**.

There is no such screen. A package here is the platform's own unit — listed at **Setup → Packages** and **Studio → Packages** — and HotCRM's own metadata is packaged from source at build time, never assembled in the UI.

### Deploying a package

The intended flow was a five-step wizard. Measured, one step of it is real, two describe the build, and two are not shipped:

1. From source sandbox → **Deploy → pick target tenant**. *(not shipped)* — no deploy screen, no tenant picker, and no source sandbox to deploy from.
2. **Dry-run** — what will change, what will be created, what conflicts exist. **Real, as a CLI command.** `os migrate plan` is documented in `@objectstack/cli` as a "dry-run diff of metadata vs the physical database, categorised safe / needs-confirm / destructive", and "never mutates the schema" — enforced rather than documented, since the stack boots with DDL deferred and the artifact seed suppressed. This app depends on `@objectstack/cli`, so the command is available to you today.
3. Review the change set. **Real** — that is `os migrate plan`'s output, read in a terminal rather than a review screen.
4. **Deploy** — typically &lt;2 min for config-only changes. *(unsourced)* — the figure is not measured by anything. Nothing in the app or the installed packages times a deployment, and for HotCRM "deploy" means your own pipeline shipping a new build, whose duration is a property of that pipeline.
5. **Audit log** captures who deployed what, when. *(not shipped for deployments.)* `sys_audit_log` is real and records data and metadata activity, but no deployment event is written to it — there is no deployment inside the tenant to record.

### What can be packaged

The honest answer is not a nine-yes/three-no table but the key set of the compiled artifact. `ObjectStackDefinitionSchema` accepts exactly **42** top-level keys:

```
manifest datasources datasourceMapping translations i18n objects
objectExtensions apps views pages dashboards reports datasets actions
themes flows jobs emailTemplates docs books positions permissions
capabilities sharingRules apis webhooks api server agents tools skills
hooks functions mappings analyticsCubes connectors data plugins requires
tiers devPlugins runtimeModule
```

Measured against the old table, row by row:

| Old row | Verdict |
| --- | --- |
| Objects, fields, validations | ✅ `objects` (fields and validations are declared inside an object) |
| Flows | ✅ `flows` |
| Sharing rules, profiles, permission sets | ✅ `sharingRules` + `permissions` — but there is no `profiles` key; profiles are permission sets |
| Pages, list views, dashboards | ✅ `pages`, `views`, `dashboards` |
| Reports, datasets | ✅ `reports`, `datasets` |
| AI skills, knowledge base configs | ⚠️ `skills` is a key; **there is no knowledge-base-config key** — knowledge articles are ordinary records |
| Approval processes | ⚠️ **No such key.** The standalone `approvals` stack field was removed in ObjectStack 7.4; approvals are `flows` carrying `approval` nodes (ADR-0019), so they package as flows |
| Email templates | ✅ `emailTemplates` is a key — though this app authors none |
| **Data records** | ❌ → **✅ WRONG, and this one is worth correcting.** `data` is a top-level artifact key, and HotCRM ships 21 seed families through it. Records package fine, per environment (`env: ['prod','dev','test']`) and with an upsert `mode` and `externalId` |
| **Files** | ✅ ❌ correct — no file key, and **no file sync API exists** to use instead; the suggestion points at nothing |
| **User accounts** | ✅ ❌ correct — no user key. SCIM is real as a platform surface (`sys_scim_provider`), but ships no screen in this tenant |

⚠️ Unknown top-level keys are **stripped, not rejected** — `ObjectStackDefinitionSchema` parses a stack containing `approvalProcesses` successfully and silently drops it. So a key that is not in the 42 above does not fail your build; it just never reaches the artifact.

## Version control (git-backed)

There is no *Git Sync* entry to connect — and for HotCRM there is nothing for one to do. The metadata **is** the git repo: every object, field, validation, flow, view and sharing rule is TypeScript under `src/`. So the things a sync page would unlock are already how the app is built:

- **Code review** via PRs.
- **Diffs** between branches.
- **History** of every change.
- **CI** running `pnpm typecheck` etc. before merge.

Point your team at the repository, not at Setup.

## Rollback

Two flavours:

### Quick rollback (within 24 h)

The intended flow: every deployment leaves a **restore point**, and a *Deployment History* list lets you roll one back within 24 h — reverting the metadata while leaving records created since the deploy in place.

No deployment history is recorded and there is no rollback button. Rolling back means deploying the previous version of the app again, from the same source that produced the current one.

### Re-deploy previous package *(not shipped in this tenant)*

If more than 24 h has passed, re-deploy the **previous successful package** — same UI, just pick the older package version. There is no such UI and no package version list here: HotCRM's version is its build (`manifest.version`, `2.2.2`), and the previous one is a git tag.

Two real mechanisms sit behind this, both outside the tenant. In the Cloud control plane, `RollbackEnvironmentPackageRequestSchema` rolls a **package installation** back to a named `targetPackageVersionId`. In the metadata store, `sys_metadata_commit` groups an authoring turn's changes and is the handle for `revertCommit` / `rollbackToPackageCommit` — append-only, so a revert is recorded as a new commit rather than erasing the old one. Neither is a button on this page, and neither applies to an app whose metadata ships from source.

⚠️ Data created against the new schema may need migration if you roll back schema changes. Always test rollback before you need it — and note that `os migrate plan` will categorise a destructive change for you before you run it.

## Production change windows

Best practice, and entirely a human process — nothing below is enforced by the app:

- **Off-peak window** (typically weekends or 7 PM Friday) for non-trivial deploys.
- **Freeze period** before major business events (quarter end, big launches).
- **Announce** in the company #cm-announcements channel.
- **2 admins** present for any production deploy (4-eyes principle).
- **Smoke test checklist** runs immediately after.

## Smoke test checklist

After every production deploy — every step below exercises something HotCRM really ships, except where noted:

- [ ] Log in as test user.
- [ ] Create a lead → convert → opportunity → quote → contract.
- [ ] Create a case → triage → resolve.
- [ ] Run the home dashboard — all tiles load.
- [ ] Send a test email with **Send Email** on a contact. (The original step said "through a connected inbox" — there is no inbox connector; see [Email & Calendar](/docs/guides/email-and-calendar).)
- [ ] Invoke a Copilot skill on a real record.
- [ ] Spot-check the changed components.

## Monitoring & alerts

All three of the alerts this section promised are absent, and the third is the one to read carefully:

- **Deployment alerts** to Slack/Teams on every promotion. *(not shipped.)* Two things are missing, not one. There is no deployment event in this tenant to alert on; and no Slack or Teams connector is installed — `connector_action` is a platform built-in flow node, but the platform ships it with an **empty** connector registry, concrete connectors (`@objectstack/connector-slack`, `@objectstack/connector-rest`, …) arrive as separate plugins, and this app installs none and registers none. A flow's `http` node can post to any URL, so you could build the alert yourself — there is simply nothing here that does.
- **Error spike** detection — if errors spike post-deploy, automatic rollback recommendation. *(not shipped.)* Zero hits for `errorSpike` or `rollbackRecommend` anywhere in the installed tree, and no alert-rule, threshold or anomaly-detection surface of any kind. The phrase "automatic rollback on failure" *does* occur in `@objectstack/spec/kernel` — it is a **plugin auto-update** setting (`rollback.automatic`, `keepVersions: 3`), about a plugin version failing to install, and is unrelated to deploying this app.
- **Performance regression** detection — if p95 latency degrades more than 20%, alert. *(not shipped as a detector.)* `p95` is real vocabulary — a member of `MetricAggregationType` alongside `p50`/`p90`/`p99` — so a p95 can be *computed*. What does not exist is anything that compares one against a baseline and raises an alert: no regression detector, no threshold rule, and `@objectstack/observability` is not a dependency of this app or wired in `objectstack.config.ts`.

> **The two claims this page cannot settle.** Whether the ObjectStack **Cloud** control

> rates or p95 latency for the environments it hosts, are properties of that hosted

> The statements above are scoped to what HotCRM and the installed tree do: they say

## Tips

- ✅ **Small, frequent** releases beat big quarterly ones — that discipline survives the absence of every screen above.
- ✅ **Name releases clearly** — `2026-Q1-pipeline-revamp` not `Package 47`. For this app the name is a git tag and a `manifest.version` bump.
- ✅ **Run `os migrate plan`** before shipping a schema change. It is the one piece of the intended deploy wizard you really have, and it tells you which changes are destructive.
- ✅ **Review in git.** The metadata is the repo, so PR review *is* the change-control process — there is no second one to connect to.
- ✅ **Practice rollback** — for HotCRM that means re-deploying the previous tag, so make sure someone has actually done it once.
- ⛔ Do not plan around sandboxes, change packages, deploy alerts or automatic rollback. Every one of them is marked *(not shipped)* above, and building a process on them means building on nothing.
