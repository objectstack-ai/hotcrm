# 沙箱與發布管理

切勿直接在生產中進行設定變更。本頁介紹安全的工作流：在沙箱中建構、測試、打包、提升到生產，必要時回滾。

## 什麼是沙箱？

**沙箱** 是你的生產 HotCRM 租戶的全保真副本 —— 相同的模式，可選地包含相同的資料 —— 在隔離環境中執行。你可以毫無後果地把它弄壞。

| 沙箱類型 | 其中包含什麼 | 重新整理頻率 |
| --- | --- | --- |
| **僅設定** | 僅模式 + 中繼資料，無記錄 | 按需 |
| **部分資料** | 模式 + 一小部分記錄樣本 | 每週 |
| **完整副本** | 模式 + 所有生產資料（已匿名化） | 每月 |

企業版套餐通常包含 **3 個沙箱**；可按需新增更多。

## 建立與重新整理沙箱

1. **設定 → 沙箱管理 → 新增沙箱**。
2. 選擇 **類型**（設定 / 部分 / 完整）。
3. 為它命名（例如 `dev`、`uat`、`training`）。
4. 點擊 **建立** —— 通常 10–60 分鐘內就緒，具體取決於大小。

要用最新的生產資料重新整理現有沙箱，請點擊沙箱行上的 **重新整理**。⚠️ **重新整理會清除沙箱中的所有變更** —— 如果你需要它們，請先打包並匯出。

### 重新整理時的匿名化

對於完整副本沙箱，PII 可以在重新整理時匿名化：

- 電子郵件地址 → `user-{id}@example-anon.test`
- 電話號碼 → 隨機化但保留格式
- 姓名 → 看起來真實的假名
- 自由文字欄位 → 保持原樣（注意 —— 請審查敏感內容）

推薦用於由合作夥伴 / 外包人員存取的沙箱。

## 變更工作流

```
┌───────────┐   build    ┌─────────┐   test    ┌─────────┐   promote   ┌────────────┐
│ Developer ├──────────▶│   dev   ├──────────▶│   uat   ├────────────▶│ production │
└───────────┘            └─────────┘           └─────────┘             └────────────┘
                                                                              │
                                                                       rollback│
                                                                              ▼
                                                                       last working
                                                                          package
```

1. 在 `dev` 沙箱中 **建構** 變更。
2. **提升** 到 `uat` —— 業務使用者在那裡測試。
3. 需要 **UAT 簽核** 才能繼續。
4. 在變更視窗期間 **提升** 到 `production`。
5. 在生產中立即進行 **冒煙測試**。
6. 必要時 **回滾**。

## 變更包

**變更包** 將一組中繼資料變更（物件、欄位、驗證、工作流、共用規則等）捕獲為單個可部署的成品。

### 建立包

1. **設定 → 變更包 → 新增**。
2. 名稱 + 描述。
3. 新增元件：
   - **手動** —— 從清單中挑選物件、欄位、規則。
   - **按標籤** —— 任何標記為 `release-2026-Q1` 的內容。
   - **自動** —— 自上次打包時間戳以來的每一項變更。
4. **驗證** —— 系統檢查包的一致性（例如無法解析的欄位引用）。
5. **儲存**。

### 部署包

1. 從源沙箱 → **部署 → 選擇目標租戶**。
2. **試執行** —— 將會變更什麼、將會建立什麼、存在什麼衝突。
3. 審查變更集。
4. **部署** —— 僅設定變更通常 &lt;2 分鐘。
5. **稽核日誌** 捕獲誰在何時部署了什麼。

### 哪些可以打包

| 類型 | 可打包 |
| --- | --- |
| 物件、欄位、驗證 | ✅ |
| 工作流、流程 | ✅ |
| 共用規則、權限設定檔、權限集 | ✅ |
| 頁面、清單檢視、儀表板 | ✅ |
| 報表、立方體 | ✅ |
| AI 技能、知識庫設定 | ✅ |
| 審批流程 | ✅ |
| 電子郵件範本 | ✅ |
| **資料記錄** | ❌（使用資料匯入） |
| **檔案** | ❌（使用檔案同步 API） |
| **使用者帳戶** | ❌（使用 SCIM） |

## 版本控制（基於 git）

對於技術團隊，沙箱中繼資料可以 **同步到 git 儲存庫**：

1. **設定 → 沙箱 → Git 同步 → 連接**。
2. 授權一個 GitHub / GitLab / Bitbucket 帳戶。
3. 選擇儲存庫和分支。
4. **拉取** —— 從 git 取得中繼資料到沙箱。
5. **推送** —— 將沙箱變更提交回 git。

這解鎖了：

- 透過 PR 進行 **程式碼審查**。
- 分支之間的 **差異對比**。
- 每次變更的 **歷史**。
- 在合併前執行 `pnpm typecheck` 等的 **CI**。

對於使用自己的包來擴充 HotCRM 的客戶，這是推薦的工作流。

## 回滾

兩種形式：

### 快速回滾（24 小時內）

每次部署都會建立一個 **還原點**。在部署後的 24 小時內：

1. **設定 → 變更包 → 部署歷史 → [部署] → 回滾**。
2. 確認 —— 系統還原中繼資料變更。
3. 自部署以來建立的記錄保留；中繼資料被還原。

### 重新部署之前的包

如果已經過去 >24 小時，請重新部署 **上一個成功的包**。同樣的 UI，只需選擇較舊的包版本。

⚠️ 如果你回滾模式變更，針對新模式建立的資料可能需要遷移。請始終先在 UAT 中測試回滾。

## 生產變更視窗

最佳實踐：

- **非高峰視窗**（通常是週末或週五晚 7 點）用於非簡單部署。
- 在重大業務事件前設置 **凍結期**（季度末、大型發布）。
- 在公司 #cm-announcements 頻道 **公告**。
- 任何生產部署都要有 **2 名管理員** 在場（四眼原則）。
- 部署後立即執行 **冒煙測試清單**。

## 冒煙測試清單

每次生產部署後：

- [ ] 以測試使用者身份登入。
- [ ] 建立潛在客戶 → 轉換 → 商機 → 報價 → 合約。
- [ ] 建立案例 → 分診 → 解決。
- [ ] 執行主頁儀表板 —— 所有圖塊載入。
- [ ] 透過已連接的收件匣傳送一封測試郵件。
- [ ] 在真實記錄上呼叫一個 Copilot 技能。
- [ ] 抽查變更的元件。

## 監控與提醒

- 每次提升時向 Slack/Teams 傳送 **部署提醒**。
- **錯誤激增** 偵測 —— 如果部署後錯誤激增，自動建議回滾。
- **效能回歸** 偵測 —— 如果 p95 延遲下降 >20%，發出提醒。

## 提示

- ✅ **始終** 在 `dev` 中建構、在 `uat` 中測試、部署到 `prod`。切勿跳過 uat。
- ✅ **小而頻繁** 的包勝過大型的季度發布。
- ✅ **為包清晰命名** —— `2026-Q1-pipeline-revamp` 而非 `Package 47`。
- ✅ 按舉措為元件 **打標籤** —— 讓打包變得輕而易舉。
- ✅ 一旦有 >2 名管理員進行變更，就盡快 **連接到 git**。
- ✅ 每月 **重新整理沙箱** —— 陳舊的沙箱會給人虛假的信心。
- ✅ 每季度 **演練回滾** —— 切勿在真實事故中第一次使用它。
