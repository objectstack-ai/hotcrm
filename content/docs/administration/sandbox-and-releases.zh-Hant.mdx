# 沙箱與發布管理

切勿直接在生產中進行設定變更。本頁介紹安全的工作流：在沙箱中建構、測試、打包、提升到生產，必要時回滾。

**下文點名的這些畫面，一個也不存在。** Setup 裡沒有 *Sandbox Management*，沒有 *Change Packages*，也沒有 *Git Sync* 入口 —— 它的導覽是 Overview、Apps、People & Organization、Access Control、Approvals、Configuration、Diagnostics、Integrations、Advanced，而這些分組底下沒有任何東西能開出一個租戶或攢出一個變更集。下面寫的是發布管理*應有*的形態，之所以保留，是因為它講的紀律是對的。HotCRM 今天真正的做法是：它的中繼資料就是 `src/` 下的 TypeScript，在 git 裡審查，隨應用一起發布；已安裝的套件列在 **Setup → Packages**。（平台未附繁體中文語言包，主控台介面會回退為簡體中文，因此本頁的導覽路徑一律以英文標示，以免簡繁混用。）

> **下面每一條斷言都被實測過，而且大多數沒能存活。** 本頁逐條對照應用自身的中繼資料
> （`src/`、`objectstack.config.ts`）與已安裝的 `@objectstack/*` 套件（spec 17.0.0-rc.6）
> 進行了核對。標註 *（未落地）* 的標題與表格列表示該能力並不存在 —— 沒有物件、沒有
> schema 鍵、沒有 API。標註 *（無來源）* 的列保留了一個數字，但應用與平台都沒有任何東西
> 在執行它。凡是真實能力以**另一種形態**存在的地方，都點名了真正的那一個。有兩條斷言
> 完全無法從這棵樹上判定，就地說明。沒有任何內容被刪除 —— 對下一位讀者而言，被刪掉的
> 斷言和錯誤的斷言看起來一模一樣。

## 什麼是沙箱？

**沙箱** 是你的生產租戶的全保真副本 —— 相同的模式，可選地包含相同的資料 —— 在隔離環境中執行，可以毫無後果地把它弄壞。這個概念是成立的，在 ObjectStack 裡也確實存在。它只是不在本租戶裡面。

| 沙箱類型 | 其中包含什麼 | 重新整理頻率 |
| --- | --- | --- |
| **僅設定** *（未落地）* | 僅模式 + 中繼資料，無記錄 | 按需 *（無來源）* |
| **部分資料** *（未落地）* | 模式 + 一小部分記錄樣本 | 每週 *（無來源）* |
| **完整副本** *（未落地）* | 模式 + 所有生產資料（已匿名化） | 每月 *（無來源）* |

*未落地，而且在任何地方都不是這個形狀。* 不存在 `sys_sandbox` 物件，任何已安裝套件裡都沒有 `sandboxType` 鍵，也沒有「設定 / 部分 / 完整」這套分類。這張表真正想描述的東西是 ObjectStack **Cloud** 的*環境*，宣告在 `@objectstack/spec/cloud` 的 `EnvironmentSchema` —— 一個組織的一個邏輯執行期對應一列，各自帶有資料庫、憑證與成員。它的 `type` 是一個七元列舉：

```
production | sandbox | development | test | staging | preview | trial
```

所以 `sandbox` 確實是一個真實取值 —— 但它是一種**環境姿態**，不是資料保真度層級，而上面那三種重新整理頻率沒有任何對應物。環境活在控制面，透過 `/api/v1/cloud/environments/…` 定址，而不是本租戶內部的某一頁。

企業版套餐通常包含 **3 個沙箱**；可按需新增更多。**未落地。** 任何地方都不存在沙箱數量權益 —— 已安裝的套件裡沒有 `sandboxLimit`、`maxSandboxes` 或 `sandboxQuota`。Cloud 的 `EnvironmentSchema` 確實帶有 `plan` 欄位（`free | starter | pro | enterprise | custom`），但掛在它上面的配額只有 `storageLimitMb`；沒有任何東西在數環境個數。無論你的商業套餐怎麼寫，它描述的都不是這個應用能展示給你的能力。

## 建立與重新整理沙箱

設計意圖是這樣的：有一個*沙箱管理*畫面，在那裡選擇**類型**（設定 / 部分 / 完整）、命名（`dev`、`uat`、`training`）並點擊**建立**；每一行上還有一個**重新整理**，把最新的生產資料重新拉下來 —— 同時清掉沙箱裡原有的一切。

並沒有這樣一個畫面。開出一個環境是 ObjectStack Cloud 控制面的事，不是本租戶設定裡的某一頁；設定裡唯一與雲相關的入口是 **Setup → Cloud Connection**。

有一件事值得知道，因為它是這個應用真正能表達的唯一一條環境軸：在 `objectstack.config.ts` 裡宣告的種子資料是**按環境區分**的。每個 `data[]` 條目接受一個 `env` 清單，而這套詞彙恰好只有三個取值：

```
data: [{ object: 'crm_account', env: ['prod', 'dev', 'test'], records: [...] }]
      env: ['sandbox'] → 被拒絕 —— Invalid option: expected one of "prod"|"dev"|"test"
      env: ['uat']     → 同樣被拒絕
```

這也正是上面那套命名值得一提的原因：`uat` 與 `training` 不是平台認得的寫法，在這條軸上 `sandbox` 也不是。

### 重新整理時的匿名化 *（未落地）*

設計意圖是這樣的：對於完整副本沙箱，PII 會在資料拉下來的同時被匿名化 ——

- 電子郵件地址 → `user-{id}@example-anon.test`
- 電話號碼 → 隨機化但保留格式
- 姓名 → 看起來真實的假名
- 自由文字欄位 → 保持原樣（注意 —— 請審查敏感內容）

—— 這樣沙箱就可以放心交給合作夥伴或外包人員。

這些都不存在。任何已安裝的套件裡都沒有匿名化、假名化或假資料產生器：在 51 個已安裝 `@objectstack/*` 套件的 1,158 個非 map 發布檔案中，`anonymi[sz]`、`pseudonymi[sz]` 與 `fakeName` 的命中數都是零。也沒有可以掛載它的「重新整理」動作，因為根本沒有沙箱可重新整理。

有一個相鄰機制確實是真的，而且是另一回事：物件上的 `publicSharing.redactFields` 會把點名的欄位從透過公開分享連結暴露出去的記錄中**去掉**。它是在某一個分享檢視裡隱藏欄位；它不轉換取值，不產生假值，和複製一個租戶毫無關係。不要把它當成匿名化。

## 變更工作流

```
┌───────────┐   build    ┌─────────┐   test    ┌─────────┐   promote   ┌────────────┐
│ Developer ├──────────▶│   dev   ├──────────▶│   uat   ├────────────▶│ production │
└───────────┘            └─────────┘           └─────────┘             └────────────┘
                                                                              │
                                                                       rollback│
                                                                              ▼
                                                                       last working
                                                                          package
```

1. 在 `dev` 沙箱中 **建構** 變更。
2. **提升** 到 `uat` —— 業務使用者在那裡測試。
3. 需要 **UAT 簽核** 才能繼續。
4. 在變更視窗期間 **提升** 到 `production`。
5. 在生產中立即進行 **冒煙測試**。
6. 必要時 **回滾**。

*紀律是對的，但應用內沒有任何機制。* 這裡沒有一步是被強制或被 HotCRM 看見的：租戶內部沒有提升動作、沒有簽核閘門、也沒有環境階梯。對這個應用來說，階梯就是你的 git 分支和你的部署流水線，上面每一步都是人或 CI 做的事。紀律請保留；別去找按鈕。

## 變更包

**變更包** 將一組中繼資料變更（物件、欄位、驗證、流程、共享規則等）捕獲為單個可部署的工件。

這個工件是真實的，而且這是全頁中心智模型最接近事實的一處 —— 只不過該單位是建構產出的，不是手工拼裝的。`objectstack compile` 產出一份編譯後的 `ObjectStackDefinitionSchema`，Cloud 控制面把它包進一個**環境工件**（`EnvironmentArtifactSchema` —— `environmentId`、`commitId`、SHA-256 `checksum`，外加編譯後的定義），並在啟動時交給執行期。它是不可變的、內容定址的。另外，`@objectstack/spec/system` 裡的 `ChangeSetSchema` 才是真正的*遷移*單位：一份具名、有序的 `add_field` / `rename_object` / `delete_object` / `execute_sql` 操作清單，帶宣告的相依，記錄在 `sys_migration` 與 `sys_migration_journal` 中。

### 建立包

設計意圖是這樣的：一個*變更包 → 新建*的畫面，填名稱與描述，用手動 / 按標籤 / 自上次打包以來自動這三種方式新增元件，再**驗證**一致性並**儲存**。

並沒有這樣一個畫面。這裡的「包」是平台自己的單位 —— 列在 **Setup → Packages** 和 **Studio → Packages** —— 而 HotCRM 自己的中繼資料是在建構時從原始碼打包的，從不在介面裡拼裝。

### 部署包

設計意圖是一個五步精靈。實測下來，其中一步是真的，兩步描述的是建構，還有兩步沒有落地：

1. 從源沙箱 → **部署 → 選擇目標租戶**。*（未落地）* —— 沒有部署畫面、沒有租戶選擇器，也沒有可供部署的源沙箱。
2. **試執行** —— 將會變更什麼、將會建立什麼、存在什麼衝突。**真實存在，形態是一條 CLI 命令。** `os migrate plan` 在 `@objectstack/cli` 中被記述為「中繼資料與物理資料庫之間的試執行差異對比，按 安全 / 需確認 / 破壞性 分類」，並且「從不改動模式」 —— 這是被強制的而非僅僅寫在文件裡，因為該堆疊啟動時會延後 DDL 並抑制工件種子。本應用相依 `@objectstack/cli`，所以這條命令你今天就能用。
3. 審查變更集。**真實存在** —— 那就是 `os migrate plan` 的輸出，在終端機裡讀，而不是在某個審查畫面裡。
4. **部署** —— 僅設定變更通常 &lt;2 分鐘。*（無來源）* —— 這個數字沒有任何東西在測量。應用與已安裝套件裡沒有任何東西給部署計時；而對 HotCRM 來說，「部署」意味著你自己的流水線發布一個新建構，其耗時是那條流水線的屬性。
5. **稽核日誌** 捕獲誰在何時部署了什麼。*（對部署而言未落地。）* `sys_audit_log` 是真實的，會記錄資料與中繼資料活動，但沒有任何部署事件寫入其中 —— 租戶內部根本沒有部署這件事可記。

### 哪些可以打包

誠實的答案不是一張九是三否的表，而是編譯後工件的鍵集合。`ObjectStackDefinitionSchema` 恰好接受 **42** 個頂層鍵：

```
manifest datasources datasourceMapping translations i18n objects
objectExtensions apps views pages dashboards reports datasets actions
themes flows jobs emailTemplates docs books positions permissions
capabilities sharingRules apis webhooks api server agents tools skills
hooks functions mappings analyticsCubes connectors data plugins requires
tiers devPlugins runtimeModule
```

逐列對照舊表：

| 舊表列 | 判定 |
| --- | --- |
| 物件、欄位、驗證 | ✅ `objects`（欄位與驗證宣告在物件內部） |
| 流程 | ✅ `flows` |
| 共享規則、權限檔案、權限集 | ✅ `sharingRules` + `permissions` —— 但沒有 `profiles` 鍵；權限檔案就是權限集 |
| 頁面、清單檢視、儀表板 | ✅ `pages`、`views`、`dashboards` |
| 報表、dataset | ✅ `reports`、`datasets` |
| AI 技能、知識庫設定 | ⚠️ `skills` 是鍵；**不存在知識庫設定這個鍵** —— 知識文章就是普通記錄 |
| 審批流程 | ⚠️ **沒有這個鍵。** 獨立的 `approvals` 堆疊欄位在 ObjectStack 7.4 被移除；審批是帶 `approval` 節點的 `flows`（ADR-0019），因此按流程打包 |
| 電子郵件範本 | ✅ `emailTemplates` 是鍵 —— 儘管本應用一個都沒寫 |
| **資料記錄** | ❌ → **✅ 寫錯了，而且這條值得糾正。** `data` 是頂層工件鍵，HotCRM 透過它發布了 21 個種子族。記錄完全可以打包，還能按環境區分（`env: ['prod','dev','test']`），並帶 upsert `mode` 與 `externalId` |
| **檔案** | ✅ ❌ 判定正確 —— 沒有檔案鍵，而且**不存在檔案同步 API** 可用；那條建議指向的是空的 |
| **使用者帳戶** | ✅ ❌ 判定正確 —— 沒有使用者鍵。SCIM 作為平台面確實存在（`sys_scim_provider`），但在本租戶裡沒有任何畫面 |

⚠️ 未知的頂層鍵是**被丟棄，而不是被拒絕** —— `ObjectStackDefinitionSchema` 解析一個含 `approvalProcesses` 的堆疊會成功，並悄悄把它扔掉。所以不在上述 42 個之列的鍵不會讓你的建構失敗；它只是永遠到不了工件裡。

## 版本控制（基於 git）

沒有 *Git Sync* 這個入口可連 —— 而對 HotCRM 來說，它也無事可做。中繼資料**本身**就是 git 儲存庫：每一個物件、欄位、驗證、流程、檢視和共享規則都是 `src/` 下的 TypeScript。所以一個同步頁面本該解鎖的東西，本來就是這個應用的建構方式：

- 透過 PR 進行 **程式碼審查**。
- 分支之間的 **差異對比**。
- 每次變更的 **歷史**。
- 在合併前執行 `pnpm typecheck` 等的 **CI**。

把團隊指向儲存庫，而不是設定頁。

## 回滾

兩種形式：

### 快速回滾（24 小時內）

設計意圖是這樣的：每次部署都留下一個**還原點**，再由一份*部署歷史*清單讓你在 24 小時內回滾某一次 —— 還原中繼資料，同時保留部署之後新建的記錄。

並沒有任何部署歷史被記錄下來，也沒有回滾按鈕。回滾的做法是把上一個版本的應用重新部署一次 —— 從產出當前版本的同一份原始碼。

### 重新部署之前的包 *（本租戶內未落地）*

如果已經過去 >24 小時，請重新部署 **上一個成功的包** —— 同樣的 UI，只需選擇較舊的包版本。這裡沒有這樣的 UI，也沒有包版本清單：HotCRM 的版本就是它的建構（`manifest.version`，`2.2.2`），而上一個版本是一個 git tag。

這背後確實有兩套真實機制，都在租戶之外。在 Cloud 控制面，`RollbackEnvironmentPackageRequestSchema` 能把一次**套件安裝**回滾到點名的 `targetPackageVersionId`。在中繼資料儲存裡，`sys_metadata_commit` 把一次編寫回合的變更歸為一組，是 `revertCommit` / `rollbackToPackageCommit` 的把手 —— 只追加，所以一次撤銷會被記為一次新提交，而不是抹掉舊的。兩者都不是本頁上的按鈕，而且都不適用於一個中繼資料從原始碼發布的應用。

⚠️ 如果你回滾模式變更，針對新模式建立的資料可能需要遷移。請務必在真正需要之前先演練回滾 —— 另外注意，`os migrate plan` 會在你執行之前就把破壞性變更給你分好類。

## 生產變更視窗

最佳實踐，而且完全是人的流程 —— 下面沒有一條是應用強制的：

- **非高峰視窗**（通常是週末或週五晚 7 點）用於非簡單部署。
- 在重大業務事件前設置 **凍結期**（季度末、大型發布）。
- 在公司 #cm-announcements 頻道 **公告**。
- 任何生產部署都要有 **2 名管理員** 在場（四眼原則）。
- 部署後立即執行 **冒煙測試清單**。

## 冒煙測試清單

每次生產部署後 —— 除標註處外，下面每一步都會真正走通 HotCRM 已落地的東西：

- [ ] 以測試使用者身份登入。
- [ ] 建立潛在客戶 → 轉化 → 商機 → 報價 → 合約。
- [ ] 建立工單 → 分診 → 解決。
- [ ] 執行主頁儀表板 —— 所有圖塊載入。
- [ ] 在聯絡人上用 **傳送郵件** 發一封測試郵件。（原步驟寫的是「透過已連接的收件匣」—— 並不存在收件匣連接器；見[電子郵件與日曆](/docs/guides/email-and-calendar)。）
- [ ] 在真實記錄上呼叫一個 Copilot 技能。
- [ ] 抽查變更的元件。

## 監控與提醒

本節承諾的三種提醒全部不存在，其中第三條要仔細讀：

- 每次提升時向 Slack/Teams 傳送 **部署提醒**。*（未落地。）* 缺的是兩樣東西，不是一樣。本租戶裡沒有可供提醒的部署事件；而且沒有安裝任何 Slack 或 Teams 連接器 —— `connector_action` 是平台內建的流程節點，但平台交付它時連接器註冊表是**空的**，具體連接器（`@objectstack/connector-slack`、`@objectstack/connector-rest` 等）以獨立外掛形式提供，而本應用一個都沒裝、一個都沒註冊。流程的 `http` 節點可以向任意 URL 發送請求，所以這個提醒你可以自己搭 —— 只是這裡沒有任何現成的東西在做它。
- **錯誤激增** 偵測 —— 如果部署後錯誤激增，自動建議回滾。*（未落地。）* 已安裝樹中 `errorSpike` 與 `rollbackRecommend` 的命中數為零，也不存在任何形式的告警規則、閾值或異常偵測面。「automatic rollback on failure」這個說法確實出現在 `@objectstack/spec/kernel` 裡 —— 那是一個**外掛自動更新**設定（`rollback.automatic`、`keepVersions: 3`），講的是某個外掛版本安裝失敗，與部署本應用無關。
- **效能回歸** 偵測 —— 如果 p95 延遲下降 >20%，發出提醒。*（作為偵測器未落地。）* `p95` 是真實詞彙 —— `MetricAggregationType` 的成員，與 `p50`/`p90`/`p99` 並列 —— 所以 p95 是可以被*計算*出來的。不存在的是任何把它與基線做比較並發出提醒的東西：沒有回歸偵測器、沒有閾值規則，而且 `@objectstack/observability` 既不是本應用的相依，也沒有在 `objectstack.config.ts` 中接線。

> **本頁無法判定的兩條斷言。** ObjectStack **Cloud** 控制面是否會向 Slack 或 Teams
> 傳送部署通知，以及它是否會為其託管的環境監視錯誤率或 p95 延遲，都是那項託管服務的
> 屬性 —— 不是本應用中繼資料的屬性，也無法從已安裝的套件中讀出。上面的表述的作用域是
> HotCRM 與已安裝樹：它們說的是這裡沒有任何東西在做這件事。如果你跑在 Cloud 上，
