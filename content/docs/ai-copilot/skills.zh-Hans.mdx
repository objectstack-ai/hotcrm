# 技能

**技能**是平台助手可以执行的细分到点的 AI 能力——比如 *"判定此线索资格"* 或 *"撰写客户回复"*。技能是 HotCRM 对助手的全部贡献；它们按两组编写文档：[销售技能](/zh-Hans/docs/ai-copilot/sales-copilot) 和 [服务技能](/zh-Hans/docs/ai-copilot/service-copilot)。

## 为什么用技能，而非"一个大 AI"

把能力打包为技能（而不是一段大提示词）使它：

- **可预测**——每项技能都有明确定义的输入、输出和行为。
- **可审计**——管理员可以看到每项技能从哪里读取、向哪里写入。
- **可改进**——你可以优化某一项技能（例如更好的线索资格判定），而不触及其他技能。
- **感知权限**——技能继承用户的记录可见性。

## 内置技能

HotCRM 内置六项核心技能：

| 技能 | 使用者 | 它做什么 |
| --- | --- | --- |
| **🔄 实时数据** | 销售 + 服务 | 读取实时模式和实时记录——每一轮 |
| **🎯 线索资格判定** | 销售 | 按 BANT 为线索评分，推荐下一步操作 |
| **✍️ 邮件撰写** | 销售 + 服务 | 撰写感知上下文的邮件或回复 |
| **📈 收入预测** | 销售 | 按阶段汇总管道并给出一个预测区间，点名有风险的交易 |
| **🔭 Customer 360°** | 销售 + 服务 | 客户或联系人的一页式摘要 |
| **🚦 工单分流** | 服务 | 建议一个优先级，并给出判定它的那条理由 |

### 🔄 实时数据

| | |
| --- | --- |
| **输入** | 任何关于 CRM 数据的自然语言问题（"哪些客户……"、"给我展示排名前……"） |
| **读取** | 提问那一刻的 **实时** 对象元数据（`describe_object`、`list_objects`）和 **实时** 记录（`query_records`、`get_record`、`aggregate_data`）——无缓存快照 |
| **输出** | 带引用记录 ID 的直接答案 |
| **写入** | 无——只读 |
| **知识库** | 无——纯粹是元数据 + 记录 |

这是 **[Wow #1 — 实时模式](/zh-Hans/docs/ai-copilot/live-schema)** 背后的技能：在管理控制台中添加一个字段，助手在下一轮就会使用它。其他每项销售 / 服务技能都构建在实时数据之上，因此同样的实时模式特性会传递地适用——线索资格判定可以根据 10 秒前添加的自定义字段为线索评分。

### 🎯 线索资格判定

| | |
| --- | --- |
| **输入** | 一条线索记录——技能在任何 `crm_lead` 上激活 |
| **读取** | 线索本身（先 `describe_object` 读 `crm_lead`，再 `get_record`）和它的相关活动历史（`query_records`）。不读营销活动参与，也不读匹配的客户历史：技能指令里没有这两步 |
| **输出** | 0–100 的 BANT 评分、每个维度一行理由（点名它读到的字段或活动），以及唯一一条建议的下一步，并引用线索 ID。它不返回热门/温热/冷淡评级，也不返回建议状态 |
| **写入** | 它自己不写——两个结果都是它调用的真实动作。评分 ≥ 70 且你同意时调用 **转化线索**（`action_convert_lead`），其流程创建客户、联系人和可选的商机，并把线索标记为 `is_converted` / `status: converted`；否则调用 **安排跟进**（`action_schedule_followup`），其流程新建一条 `crm_task` 并回填线索的下次跟进日期。两者都不会写 `rating`——那是由人设置的 1–5 星 **线索评分** |
| **知识库** | 无。没有取知识的步骤——也不存在一个叫*销售知识*的库让它去取（参见 [知识库](/zh-Hans/docs/ai-copilot/knowledge-bases)） |

### ✍️ 邮件撰写

| | |
| --- | --- |
| **输入** | 一句目标，加上它所针对的记录——指令把文案落在联系人上，并在请求点名时带上相关的客户或商机 |
| **读取** | 联系人记录（`get_record`），以及上面那条相关的客户或商机；需要近期往来时用 `query_records` |
| **输出** | 一份主题 + 正文的草稿——主题 60 字符以内、一个明确诉求、不超过 150 词——外加第二个主题行备选，并说明两个里推荐哪一个 |
| **写入** | 无，而且它也没有途径写：联系人上的 **发送邮件** 没有开启 AI 曝光，因此运行时不会为这项技能生成任何发送工具。它只把草稿摆出来，并指向那个按钮，由人在那里审阅并发送 |
| **知识库** | 无。起草指令里没有任何一步去取文章，而这里曾点名的三个库并不存在 |

### 📈 收入预测

| | |
| --- | --- |
| **输入** | 一个关于管道健康度、预测、风险或交易滑期的问题 + 它覆盖的周期（默认：本季度） |
| **读取** | `crm_opportunity`——用 `describe_object` 拿到它当前的结构，用 `aggregate_data` 按阶段统计数量与金额合计，用 `query_records` 捞出有风险的交易（预计成交日期已过、30 天以上没有活动、阶段停留过久）。指令里没有任何一步去读字段历史；阶段停留时长直接来自记录自己的 **当前阶段天数** |
| **输出** | 按阶段展开的管道及加权价值（金额 × 概率，由它自己从读到的数据算出）、逐条点名的风险交易及其信号，以及一个以区间给出的预测——从仅承诺口径（高概率阶段）到完整加权管道——并在图表更能说明问题时用 `visualize_data` 出图。**已关闭 / 承诺 / 最佳情况 / 管道** 这几个桶不是这项技能的输出：它们是 `crm_opportunity` 的 **预测类别** 字段，以及定时的销售预测快照写入 **销售预测** 记录的那几个金额 |
| **写入** | 无——只读 |
| **知识库** | 无。方法论写在这个技能自己的指令里，不在任何库中 |

### 🔭 Customer 360°

| | |
| --- | --- |
| **输入** | 一个客户或联系人 |
| **读取** | `crm_account`，然后按这家客户过滤读取：`crm_contact`、未结的 `crm_case`（`is_closed` 为 false）、进行中的 `crm_opportunity`，以及已发布的 `crm_knowledge_article`；合计数来自 `aggregate_data`，而不是逐行相加。合同、近期活动和营销活动成员资格**不在**它读的范围里：技能带着 `query_records`，够得着 `crm_contract`、`crm_campaign`、`crm_event` 和 `crm_task`，只是指令从没让它去读（与 [服务技能](/zh-Hans/docs/ai-copilot/service-copilot) 页写实的是同一件事） |
| **输出** | 固定三段——**Account Snapshot**（客户快照）· **Active Work**（进行中的工作）· **Risks & Notes**（风险与备注），这三个小标题在技能里就是英文原文——并在行内引用记录 ID 以便深链。每条风险都要点名它的记录和引出它的信号；某个板块没有记录时如实说明为空。没有合同板块，也没有参与度板块 |
| **写入** | 无——只读 |
| **知识库** | 已发布的**知识文章**，按它刚读到的工单的分类或标签匹配——唯一会读文章的技能 |

### 🚦 工单分流

| | |
| --- | --- |
| **输入** | 一个工单——技能在 `crm_case` 上激活 |
| **读取** | 工单本身：先 `describe_object` 读 `crm_case`，再 `get_record` 取当前这条工单，加上评判标准排在最前面的客户上下文（**客户分层**、合同金额）。它没有声明任何检索类工具，因此过往工单够不着；也没有产品可读：`crm_case` 上没有任何名字的产品字段，也没有指向 `crm_product` 的 lookup |
| **输出** | 一个优先级（低 / 中 / 高 / 紧急）和驱动它的**那一条**理由，并引用工单 ID 与它读到的字段值；随后给出指向 **升级工单**（附一段可直接粘贴的 `reason`）或 **关闭工单**（附一段 `resolution` 摘要）的指引。没有分类、没有团队、没有文章清单；面向客户的回复交给 **邮件撰写** |
| **写入** | 无。它的工具只有 `describe_object` 和 `get_record`，而两个会改动工单的动作——`escalate_case` / `close_case`——都没有开启 AI 曝光，因此运行时不会为它生成任何写工具。这一行过去点名的 `category` 与 `queue`，在 `crm_case` 上根本不存在（以任何名字都不存在；工单自己的分类字段是 **类型**：咨询 / 故障 / 功能需求 / 缺陷，由人来选）。分流给出判断，按钮由坐席来点 |
| **知识库** | 无。它没有声明任何检索类工具，因此根本检索不了文章 |

## 技能如何协同工作

技能之间不会互相调用。助手为你问的这个问题挑选合适的那一项技能，一个问题跑一项技能——不会有第二项技能被串接在它后面。

唯一写进技能自身指令里的移交是工单分流的那一条：面向客户的回复，它点名交给 *邮件撰写*，而不是自己动笔。这条移交是给你的指引，所以把草稿作为下一个问题再问一次，那项技能就会接手。*工单分流* 不会调用 *Customer 360* 去判断客户是否高价值，*邮件撰写* 也不会调用它去取客户上下文——这两次调用都不存在。当你需要分流或草稿背后的客户历史时，请自己去问 *Customer 360°*：它才是带着 `query_records` 的那一项。

真正被所有技能共享的，是数据底座：每一项都通过同一套实时元数据与记录工具去读，因此实时数据的实时模式特性对它们全部成立。

## 每项技能都遵循什么

- **共享规则**——为用户 X 运行的技能只能读取对 X 可见的记录。
- **字段级安全**——受限字段会从技能输入中隐藏。
- **审计日志**——每次技能调用，连同输入和输出，都会记录以供审查。
- **确认**——线索资格判定是唯一有写入路径的技能，而且它写的是真实动作而非字段：**转化线索** 不可逆，因此会要求确认，由 AI 发起的转化会等待人工审批而不是无人值守地跑完；**安排跟进** 是增量且可撤回的，因此没有审批闸门。其余五项技能都没有声明任何写工具。

## 添加你自己的技能

管理员和开发者可以构建自定义技能——例如：

- 为即将到期的合同 *生成续约推介*。
- *评估客户健康度*，综合使用情况、NPS 和工单量。
- 当某个产品达到里程碑时 *撰写一封发布说明邮件*。

参见 [自定义 › AI 技能](/zh-Hans/docs/customization/ai-skills)，了解如何定义一项新技能、它可以使用哪些知识库，以及如何测试它。

## 给管理员的提示

- ✅ 在 AI 仪表盘中 **监控技能使用情况**——哪些技能使用最多，哪些接受率低。
- ✅ 为表现不佳的技能 **调优知识库**——大多数准确性问题都是知识问题。
- ✅ **禁用** 不适合你业务的技能——每项技能都可以在管理设置中切换开关。
