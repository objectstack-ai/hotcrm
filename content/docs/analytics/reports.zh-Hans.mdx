# 报表

报表是可筛选、可导出的列表，带有分组和汇总合计。仪表盘展示*是什么*，而报表回答*为什么*和*哪些*。

## 标准报表

HotCRM 开箱即用地提供以下报表：

### 📈 销售报表

| 报表 | 显示内容 |
| --- | --- |
| **Pipeline by Stage** | 所有未结交易按阶段分组，带 $ 合计 |
| **Forecast vs Actual** | 成交赢单对比预测，按周期 |
| **Win/Loss Analysis** | 已结交易按赢单/丢单分组，带原因分解 |
| **Sales Cycle Length** | 从创建到成交的天数，按所有者和产品 |
| **Top Performing Reps** | 成交排行榜 |
| **Stale Opportunities** | 14 天以上无活动的交易 |
| **Big Deals Won** | ≥ $100K 的成交赢单商机 |
| **Discount Approval Activity** | 所有审批请求，按状态和审批人 |

### 🎯 线索报表

`src/reports/lead.report.ts` 发布的线索报表只有 **一份**：

| 报表 | 显示内容 |
| --- | --- |
| **Lead Engagement by Month × Source** | 已联系线索数量的矩阵 —— 行是线索来源，列是 **Last Contacted** 所在的月份。从未联系过的线索被排除在外：它们没有互动月份 |

本节曾经列出的三份报表，一份都没有发布，其中两份还用了一个并不存在的线索状态：

- **Lead Conversion Funnel** 与 **Aged Leads** 以任何形式都不存在。两者都依赖一个 *Working* 状态，而 `crm_lead.status` 根本没有这个取值 —— 真实路线是 *New → Contacted → Qualified → Unqualified → Converted*（`src/objects/lead.object.ts`），其中 *Unqualified* 从任何开放状态都能进入。*Working* 是导入别名表（`src/mappings/lead_import.mapping.ts`）里的一行，它在记录导入时把这个历史写法映射到 **Contacted**；产品从不显示这个词。声明出来的路线见 [状态机](/zh-Hans/docs/administration/state-machines)。
- **Lead Source ROI** 同样不存在，而且按它写的口径，语义层也答不出来：`lead_metrics`（`src/datasets/lead.dataset.ts`）只声明了一个度量 —— 线索计数 —— 外加四个维度（状态、来源、创建日期、最后联系月份）。「按来源的数量」可以直接从它得到；转化率要你自己在按状态分组的计数上做除法；而收入根本不在这个数据集里 —— 它从不跨到商机那一侧。

线索计数也是别处唯一会读的线索数字：[Executive Overview](/zh-Hans/docs/analytics/dashboards) 仪表盘上的 **Open Leads** 磁贴正是用同一个数据集数未转化线索。其余的请自建 —— 见下文《自定义报表》。

### 🎧 服务报表

`src/reports/case.report.ts` 发布的工单报表共 **三份**：

| 报表 | 显示内容 |
| --- | --- |
| **Cases by Status and Priority** | 工单数与平均解决时长，先按状态、再按优先级分组，并带一张「按状态的工单数」柱状图 |
| **SLA Performance Report** | 工单数、**SLA 违约率** 与平均解决时长，按优先级 —— 只统计已关闭的工单 |
| **Cases Opened by Priority × Day** | 每日新增工单的矩阵：行是优先级，列是工单开出来的那一天 |

本节曾经列出的另外五份报表哪儿都没有发布，而且其中多数是在向语义层要它根本没有的东西。`case_metrics`（`src/datasets/case.dataset.ts`）只读 `crm_case` 一个对象，五个维度 —— **Status**、**Priority**、**Origin**、**Type**、**Created**（按天分桶）—— 外加三个度量：工单数、平均解决时长、SLA 违约率。

- **Case Volume by Origin** 是这五份里唯一你自己建得出来的：**Origin** 是维度，所以「按 Email / Phone / Web / Chat / Portal 数工单」只差一份自建报表。它只是不在随应用发布的那几份里。
- **Case Resolution Time** *按类别和客服* —— 度量本身是真的，上面两份汇总报表都带着它；但 **客服** 这一维根本够不着：`owner_id` 是工单上的字段，没有任何维度把它暴露出来。最接近「类别」的是 **Type**（*Question / Problem / Feature Request / Bug*）。
- **Top Accounts by Case Volume** 同样建不出来 —— 没有客户维度，这个数据集也从不跨到 `crm_account`。
- **Reopened Cases** 数的是没有任何东西在记的事。工单确实会重开 —— 状态机允许 *Resolved* 与 *Closed* 回到 *In Progress* —— 但没有任何字段标记一张工单曾被重开，也没有任何度量在数它。
- **CSAT by Agent** 两头都不成立：**Customer Satisfaction**（`customer_rating`）是工单上真实的 1–5 星字段，但 `case_metrics` 没有为它声明任何度量，也没有「客服」这一维可分组。

**SLA Performance Report 里同样没有任何首次响应数字**，而且它那个 SLA 数字是 **SLA Violated** 标志的平均值，也就是违约 *率*，不是准时率。本应用根本不度量首次响应：**First Response Date** 只在工单上第一次记录 *已经发生过* 的通话或会议时被盖上，此后从不与任何目标比较；`case_metrics` 没有声明任何首次响应度量，所以没有报表、也没有仪表盘磁贴能报出一个来。参见 [SLA 与升级](/zh-Hans/docs/service/sla-and-escalation)。

## 使用报表

每个报表都有相同的基本控件：

| 控件 | 作用 |
| --- | --- |
| **Filter** | 添加条件（日期范围、所有者、阶段等） |
| **Group by** | 按任意字段汇总——所有者、阶段、产品、地区 |
| **Sort** | 点击任意列标题 |
| **Summary** | 在分组和整体层级显示合计、平均值、最小值、最大值 |
| **Drill in** | 点击任意行以打开源记录 |
| **Export** | 下载为 CSV 或 Excel |
| **Save as** | 用新名称保存你筛选/分组后的版本 |
| **Schedule** | 按重复计划通过电子邮件发送 PDF 或 CSV |
| **Subscribe** | 报表变更时收到通知 |

## 权限

- 用户只能看到他们有权访问的记录——运行 *Pipeline by Stage* 的销售代表看到自己的交易；经理看到团队的。
- 管理员可以通过**字段级安全**锁定哪些字段出现在报表中。
- 敏感报表可以限制给特定的 [配置文件](/zh-Hans/docs/administration/profiles)。

## 自定义报表

拥有 *Report Builder* 权限的任何人都可以：

1. 选择一个**源对象**（线索、商机、工单等）。
2. 选择要显示的**列**。
3. 添加**筛选条件**。
4. 选择**分组**和**汇总字段**。
5. 选择一个**图表**进行可视化。
6. **保存并共享**。

对于更高级的分析——多对象联接、时间序列、群组分析——请使用 [多维数据集](/zh-Hans/docs/analytics/cubes)。

## 订阅与定时推送

消费报表最常见的方式是**电子邮件订阅**：

- **频率**：每日、每周、每月。
- **推送日期与时间**。
- **格式**：PDF（已格式化）或 CSV（原始数据）。
- **收件人**：你自己、团队别名，或特定用户（受其自身权限约束）。

一种常见模式：

- *Pipeline by Stage* → 周一早上 8 点发给销售团队。
- *SLA Performance Report* → 每日下午 6 点发给服务经理。
- *Cases Opened by Priority × Day* → 周五下午 4 点发给客户成功团队。

## 给用户的提示

- ✅ 为你每周运行的视图保存筛选版本——不要从头重新筛选。
- ✅ 在团队报表上使用 **Group by Owner**，以突出表现优异者和落后者。
- ✅ 仅在需要与外部数据合并时才导出到 Excel——否则留在应用内以获取实时数据。

## 给经理的提示

- ✅ 每周向你的团队安排 **Stale Opportunities**——它能强制跟进纪律。
- ✅ 每月与销售教练一起使用 **Win/Loss Analysis**——它是最好的单一辅导工具。

## 给管理员的提示

- ✅ 当用户反复构建同一份报表时，**将其提升**到标准库。
- ✅ 淘汰无人运行的报表——保持库的精炼。
- ✅ 按团队（销售、服务、市场营销、高管）设置**默认报表文件夹**，以便轻松发现。
