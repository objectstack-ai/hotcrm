# 匯入與匯出

如何把資料**匯入** HotCRM，以及如何**匯出**。下文全部按應用當前實際的樣子書寫；標註 *（尚未落地）* 的小節保留的是設計意圖——請把它們當作需求文件來讀，而不是操作步驟。

> **不存在「設定 → 資料」選單。** Setup 應用的分組是 *概覽*、*應用*、*人員與組織*、*存取控制*、*簽核*、*設定*、*診斷*、*整合* 和 *進階*。既沒有 **資料** 分組，也沒有 **隱私** 分組。本頁較早的版本幾乎把每一個步驟都指向 `設定 → 資料 → …`，而照著走的人去找的是並不存在的畫面。匯入與匯出都在**物件自己的清單檢視**上；其餘的部分是資料 API。

## 從 CSV / Excel 匯入

兩條路，都是真的，而且落到同一個地方：

- **在應用裡**——打開物件的清單檢視，點工具列的**匯入**。適合那種你想先親眼過一遍再寫入的一次性檔案。
- **透過 API**——匯入端點，帶試算、背景作業與復原。分步說明見[匯入你自己的資料](/zh-Hant/docs/guides/importing-your-data)。

兩條路共用伺服器端同一條匯入通路，因此對應、驗證與逐列錯誤碼都是同一套。

### 應用內的匯入精靈

1. **打開該物件的清單檢視**，點**匯入**。目標物件由你從哪裡進來決定——精靈不會讓你再選一次。
2. **上傳**——把 CSV 或 Excel 檔案拖進去，或者直接從試算表裡貼上。**下載範本** 會給你一個帶該物件各欄的 CSV，必填欄標著 `*`。
3. **對應**——各欄按表頭名自動比對到欄位，每條比對都帶一個信心度讀數；其餘的由你手動修正或略過。如果 HotCRM 為該物件隨附了**已儲存的對應**，就直接選它：重新命名、值轉換與型別強制轉換隨後都在伺服器端執行，欄位對應變為唯讀。今天隨附三個——`crm_account_import`、`crm_contact_import` 與 `crm_lead_import`——和 API 那條路點名的是同樣三個。
4. **匯入選項**——*當某列比對到既有記錄時* 提供 **總是新建**、**更新既有（無比對則略過）** 與 **比對則更新，否則新建**，並由 **比對依據** 決定按哪個（哪些）欄位去比對。已儲存的對應會自帶預設寫入模式與比對鍵，所以在上面那三個物件上你幾乎不需要動它。
5. **驗證資料**——把每一列拿到伺服器端核對一遍，不寫入任何東西。每次匯入前都做。
6. **預覽 → 匯入**——大檔案會交給背景作業，並顯示 `正在匯入 n / m 列`。**歷史** 列出該物件最近的匯入作業，並提供**復原匯入**：作業建立的記錄會被刪除，它更新過的記錄會還原到之前的值。

> **匯入完成時不會有郵件送達。** 作業執行時進度顯示在畫面上，跑完後這次執行列在**歷史**裡——通知就到此為止。HotCRM 不寄送任何完成郵件，而平台的郵件服務只有出站方向，且在部署設定傳輸方式之前根本什麼都不投遞。

單一作業最多 **50,000 列**；更大的檔案請拆分。復原的上限更緊，另外還有幾個前提條件——見[匯入你自己的資料](/zh-Hant/docs/guides/importing-your-data)。

### 欄位對應提示

- **擁有者**——填使用者的郵件地址，它會去解析到使用者記錄。比對不到任何使用者的地址會讓**該列失敗**，錯誤碼 `reference_not_found`；系統不做任何猜測。把儲存格留空，則記錄歸執行匯入的人所有。
- **查閱欄位**——填被引用記錄的 id，或者那個物件用來標識自己的文字（其顯示欄位，其次是 `name` / `title` / `label` / `full_name` / `email` / `username`）。父記錄即使排在同一個檔案的後面，也仍然能解析到。
- **選項清單**——按欄位選項的標籤*和*值做比對，不區分大小寫，所以 *Technology* 和 *technology* 都能落地。隨附的對應還額外翻譯其他系統匯出時使用的詞彙——*SaaS*、*Trade Show*、*Client*。仍然認不出來的值會讓該列以 `invalid_option` 失敗，而不是被悄悄丟掉。
- **日期**——`YYYY-MM-DD` 最穩妥。
- **數字**——純數字（`1500000`，不是 `1.5M`）。
- **地址**——聯絡人有真實的通訊地址欄；客戶和潛在客戶把地址存為一個結構化欄位，無法由分散的表格欄拼裝出來。已知限制列在[匯入你自己的資料](/zh-Hant/docs/guides/importing-your-data)。

### 比對鍵——而不是外部 ID

本頁較早的版本讓你加一個 `external_id` 欄並把它標記為比對鍵。**HotCRM 的物件沒有任何一個帶 `external_id` 欄位**，而具名對應是嚴格投影——它沒有宣告的每一欄都會在寫入前被丟棄——所以那一欄只會被忽略。

它承諾的冪等性是真的，只不過來自業務鍵：

| 對應 | 與既有記錄的比對依據 |
| --- | --- |
| `crm_account_import` | 客戶名稱 |
| `crm_contact_import` | 郵件地址 |
| `crm_lead_import` | 郵件地址 |

重新執行同一個檔案，比對上的列會被更新而不是重複建立。在精靈裡，**比對依據** 就是同一個想法的手動版。跨物件引用也是同樣的機制：聯絡人用*客戶名稱*指向它的客戶，而不是某個遺留 id。

不過客戶名稱是**逐字**比對的——*Acme Corp* 和 *ACME Corp* 是兩個不同的客戶。

## 從 Salesforce 遷移（尚未落地）

設計意圖是這樣的：隨箱提供一個專門建構的遷移精靈。你透過 OAuth 授權到自己的 Salesforce 沙箱或生產環境，精靈自動把 Salesforce 物件對應到 HotCRM 的對應項，你審閱欄位、選項清單與擁有者對應，選擇資料切片（全部歷史，或用於分階段切換的一個日期範圍），試算，然後提交——並保留 Salesforce 的記錄 id 以便追溯。

| Salesforce | HotCRM 對應項（設計意圖） |
| --- | --- |
| Account | `crm_account` |
| Contact | `crm_contact` |
| Lead | `crm_lead` |
| Opportunity | `crm_opportunity` |
| OpportunityLineItem | `crm_opportunity_line_item` |
| Quote / QuoteLineItem | `crm_quote` / `crm_quote_line_item` |
| Contract | `crm_contract` |
| Case | `crm_case` |
| Campaign / CampaignMember | `crm_campaign` / `crm_campaign_member` |
| Product2 | `crm_product` |
| Task / Event | `crm_task` / `crm_event` |
| User | 使用者 *（按郵件比對，或發出邀請）* |

**這些一樣都沒有落地。** 應用裡沒有遷移精靈，沒有 Salesforce 連接器，也沒有任何一個會去讀 Salesforce 的操作。原始碼裡提到 Salesforce 有十來處，每一處都是把它當作業界設計參照來引用的註解——預測分類階梯、首次回應時間的定義、Lightning 風格的記錄頁版面，以及匯入對應裡那條關於「Salesforce 匯出會寫哪些詞彙」的說明。

也沒有對外的 OAuth。Setup 的 **OAuth 應用** 畫面登記的是呼叫*進入* ObjectStack 的用戶端；產品裡沒有任何東西負責讓 HotCRM 去*向別人的組織*取得授權。

它甚至也不在路線圖上：路線圖那一行寫的是 *「更多連接器 —— Slack、Microsoft Teams、Google Workspace、HubSpot 匯入」*。

**今天該怎麼做。** 從 Salesforce 匯出 CSV，用上文的匯入把它裝進來。隨附的對應已經會說這門方言的一部分——*SaaS* 與 *Financial Services* 會變成 *Software / SaaS* 與 *Finance*，*Trade Show* 變成 *Event / Trade Show*，*Client* 變成客戶類型的客戶——所以客戶、聯絡人與潛在客戶這一段，通常只需要正確的表頭列。沒有隨附對應的物件，走精靈裡的手動欄位對應，或者走資料 API。

## 從 HubSpot 遷移（尚未落地）

同樣的情況，但有一點不同：**HubSpot 匯入是路線圖上點名的一項**，所以這一條是排上了日程，而不只是一個願望。

| HubSpot | HotCRM 對應項（設計意圖） |
| --- | --- |
| Company | `crm_account` |
| Contact | `crm_contact` |
| Deal | `crm_opportunity` |
| Ticket | `crm_case` |
| Line item | `crm_opportunity_line_item` |
| Product | `crm_product` |
| Quote | `crm_quote` |

交易管道會對應到商機階段，那是最值得手動審閱的一處對應。在它落地之前，上文的 CSV 路線就是遷移路徑。

## 遷移操作手冊

依然是對的建議——只是現在它是關於 CSV 這條路的建議。

1. **先把使用者建好。** 匯入器從不建立使用者，而一個比對不到任何人的擁有者郵件儲存格會讓該列失敗。先把使用者裝進 HotCRM（或者清空擁有者欄、匯入後再分配），然後再做別的。
2. **按相依順序載入**——先客戶，再聯絡人，最後潛在客戶。每個聯絡人都要指名一個必須已經存在的客戶。除這三者之外也守同一條原則：指向別人的記錄排在後面。
3. **寫入前先驗證**，每次都做。精靈裡的*驗證資料*，API 上的 `dryRun`。報告裡的 `row` 就是你檔案裡的列號，改好表格再跑一遍即可。
4. **核對數量**——來源系統的總數與 HotCRM 的總數對一對，有差距就去查。
5. **手動端到端抽查十筆記錄。** 數量對上，不等於欄位都落對了。
6. **動手前先弄清你的復原視窗。** 復原是按作業來的，而且涵蓋不了大作業，所以如果你要這層保險，就把大資料集分塊匯入。

## 匯出資料

### 從清單檢視匯出

有四個清單檢視宣告了 `exportOptions: ['csv', 'xlsx']`——**客戶**、**聯絡人**、**潛在客戶** 與 **商機**。打開其中之一，用工具列的**匯出**，選 CSV 或 Excel。你拿到的就是你正在看的那個檢視：它的篩選、排序與欄位都會隨匯出一起走。

### 誰可以匯出

匯出是一項獨立權限，不是「能讀」的副產品。`allowExport` 是選擇性開啟的，未設定即**拒絕**；`viewAllRecords` 與 `modifyAllRecords` 都不能替代它。HotCRM 按角色逐一撰寫了這些授權：

| 角色 | 可匯出的物件 |
| --- | --- |
| 業務代表 | 潛在客戶、客戶、聯絡人、商機、工單 |
| 業務經理 | 潛在客戶、客戶、聯絡人、商機、工單 |
| 客服專員 | 潛在客戶、客戶、聯絡人、工單 |
| 行銷使用者 | 潛在客戶、客戶、聯絡人、商機 |
| 系統管理員 | 潛在客戶、客戶、聯絡人、商機、工單 |
| 訪客入口 | 沒有，這是刻意的 |

授權只是打開那扇門，它不會放寬列範圍。匯出是從讀衍生的，因此記錄範圍與共享規則仍然疊加在上面——一個業務代表匯出商機，拿到的是自己那本帳，而不是全公司的。

工單雖然帶有匯出授權，卻沒有任何工單清單檢視宣告 `exportOptions`：那條授權面向的是報表匯出，而報表匯出依託平台的 `reports` 能力。本應用的 `requires` 沒有列出它，所以在預設啟動下，上面那四個清單檢視與資料 API 就是你擁有的匯出面。

### 透過資料 API 匯出

清單檢視上的**匯出**按鈕呼叫的就是該物件的匯出路由，你也可以自己呼叫它：格式為 `csv`、`xlsx` 或 `json`，並可帶 `fields`、`orderby`、`filter`、`search` 與 `limit`。或者用 ObjectQL 查詢該物件並分頁取回。路由形態請按你所執行的版本、以及身分驗證方式，參見 [API 參考](/zh-Hant/docs/customization/api-reference)。

### 排程匯出到資料倉儲（尚未落地）

設計意圖是這樣的：選擇物件、欄位、篩選條件、排程與目標位置；把檔案以 CSV、Parquet 或 JSON Lines 落到 S3 / Azure Blob / GCS / SFTP；首次之後轉為增量。

這些一概不存在——沒有排程匯出畫面，沒有資料倉儲目標位置，沒有 Parquet 寫出器，也沒有 `設定 → 資料` 選單來承載它。今天要麼從清單檢視手動匯出，要麼把匯出路由掛到你自己掌控的排程上——一個 cron 作業、一個 Lambda、一個 GitHub Action。參見[整合](/zh-Hant/docs/guides/integrations)。

## 資料刪除請求（尚未落地）

設計意圖是這樣的：`設定 → 隱私 → 資料主體請求`，按郵件或聯絡人 id 識別該人，看到與他關聯的全部內容，選擇**刪除**或**匿名化**（姓名與郵件替換為 `[redacted]`，記錄保留以供分析），並交給客戶一份稽核憑證。

這些一概不存在。Setup 裡沒有隱私分組，沒有資料主體請求物件，沒有匿名化操作，也沒有稽核憑證——平台的稽核能力並不在本應用啟用的那批能力裡。

今天你能做的，是直接刪除或編輯記錄：

- **刪除該聯絡人。** 指名這個人的與會人列會隨之刪除；會議本身保留，因此團隊的歷史不會因此出現空洞。
- **刪除該客戶**，它的聯絡人會級聯刪除。先看清還有什麼掛在它下面——這條級聯值得事先規劃，而不是事後發現。
- **手動匿名化**：在你要保留的那筆記錄上清空可識別欄位。沒有一鍵等價物，末尾也不會產出任何憑證。

## 備份與災難復原

備份行為取決於 HotCRM 的託管方式：

- **SaaS** —— 備份由平台管理（通常每日快照，30 天保留期）。
- **自託管** —— 由你負責；備份資料庫和檔案儲存桶。請參閱 [管理 › 設定](/zh-Hant/docs/administration/setup) 了解推薦的頻率。

要獲取經過測試的**災難復原**操作手冊，請參閱 [參考 › 安全與合規](/zh-Hant/docs/reference/security-and-compliance)。

## 提示

- ✅ **每次匯入前都先驗證**——精靈裡的*驗證資料*，API 上的 `dryRun`。它只花幾秒鐘，卻是擋在「一欄寫錯」和「五萬列」之間的唯一一道東西。
- ✅ **按相依順序載入**——先客戶，再聯絡人，最後潛在客戶。
- ✅ **讓業務鍵去做去重。** 不要自己發明 `external_id` 欄；重跑同一個檔案本來就是更新而不是重複建立。
- ✅ **大批量匯入前先確認復原視窗**，如果你要這層回滾保險，就把檔案分塊。
- ✅ **謹慎授予 `allowExport`**——它之所以是選擇性開啟的，正因為它是批量外流，資料會跟著人一起離開。
- ✅ **把每一個 *（尚未落地）* 小節當作需求文件來讀，而不是設定指南**——並關注[路線圖](/zh-Hant/docs/whats-new)。
