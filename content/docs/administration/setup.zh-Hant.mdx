# 設定清單

為新 HotCRM 管理員準備的實用的第一週清單。請按順序逐項完成 —— 每個部分都建立在前一個之上。

## ✅ 第 1 天 —— 基礎

### 1. 公司資料

導覽至 **Setup → Company**（平台未附繁體中文語言包，主控台介面會回退為簡體中文，因此本頁的導覽路徑一律以英文標示，以免簡繁混用）：

- [ ] 公司名稱、地址、時區、預設貨幣
- [ ] 財年起始月份（所有預測報表都會用到）
- [ ] 預設語言

### 2. 營業時間 —— 沒有需要設定的東西

**不存在「Setup → Business Hours」這個畫面。** 本應用沒有工作日日曆，沒有工作時段設定，也沒有假日清單 —— 這裡沒有任何可填的項目，也不存在任何可供截止時間去對照的東西。這一節保留下來，只是為了讓被指去找那個畫面的管理員別再找了。

由此帶來的後果落在 SLA 一側：截止時間按**日曆小時**走。現在每一張工單都會被算出一個截止時間 —— `src/objects/case.hook.ts` 拿工單的優先順序去和其帳戶的**客戶層級**對查，再把相應的實際小時數加到當前時鐘上 —— 所以一個週五下午 4 點建的 Critical 工單，截止時間就是同一個週五晚上 8 點；一個在長假前建的 Low 工單，那一週就這麼在假期裡跑完。夜間、週末與假日在每個優先順序上都一律照算。參見 [SLA 與升級](/zh-Hant/docs/service/sla-and-escalation)。

### 3. 電子郵件設定

**Setup → Email**：

- [ ] 工單的入站郵件轉發（例如 `support@yourdomain.com`）
- [ ] 出站郵件簽名範本
- [ ] 用於寄件人身份驗證的 DKIM / SPF

## ✅ 第 2 天 —— 人員

### 4. 使用者邀請

**Setup → Users**：

- [ ] 匯入或邀請所有使用者
- [ ] 為每個使用者指派一個 [權限設定檔](/zh-Hant/docs/administration/profiles)
- [ ] 為每個使用者指派職位 —— 一個使用者可以持有多個
- [ ] 為每個使用者設置一名經理（驅動審批路由）

### 5. 職位

**Setup → Users**，以及[共享與安全](/zh-Hant/docs/administration/sharing-and-security)列出的 12 個職位：

- [ ] 把你的組織對應到內建職位上。職位是**扁平的** —— 它們分發存取權限，不會疊成一條匯報線，一個職位也不會向另一個職位上捲
- [ ] 每新增一個職位，就為它補上點名該職位的共享規則（或權限集繫結）—— 沒有任何規則點名的職位什麼也授予不了

### 6. 權限設定檔與權限

**Setup → Permission Sets** —— 本清單裡所說的*權限設定檔*就是權限集，Setup 裡沒有叫 *Profiles* 的頁面：

- [ ] 審查六種內建權限設定檔（參見 [權限設定檔](/zh-Hant/docs/administration/profiles)）
- [ ] 如有需要，複製並自訂（例如一個刪除權限有限的 *初級銷售代表* 權限設定檔）

## ✅ 第 3 天 —— 資料基礎

### 7. 客戶與聯絡人所有權

- [ ] 為客戶和聯絡人決定組織範圍預設值（私有 vs 公開讀取 vs 公開讀/寫）—— 參見 [共用與安全](/zh-Hant/docs/administration/sharing-and-security)
- [ ] 如果你以小組而非單個代表的方式銷售，設定客戶團隊

### 8. 潛在客戶路由 —— 沒有需要設定的東西

**不存在「Setup → Lead Settings」這個畫面**，也沒有任何路由規則可寫。一條無所有者的潛在客戶 —— 網頁表單、CSV 匯入、API 擷取 —— 會在插入時由 `src/objects/lead.hook.ts` 指派：交給持有 `sales_rep` 職位的人當中**未結潛在客戶最少**的那一位。這是一個自平衡的輪詢，而不是按區域、行業或來源比對的規則；沒有區域路由，沒有佇列，也沒有發給提交者的自動回覆郵件。如果沒有人持有 `sales_rep`，這個掛鉤什麼也不做，潛在客戶就一直無主，直到有人認領。

- [ ] 把 `sales_rep` 職位指派給每一位應當接收潛在客戶的業務代表 —— 這個人員池*就是*路由表
- [ ] 在 **Studio → Automation → Flows** 中查看接下來 `lead_assignment` 流程做了什麼（按評級設定跟進日期，並提醒新的所有者）

### 9. 產品目錄

- [ ] 匯入 [產品](/zh-Hant/docs/revenue/products) —— 至少：代碼、名稱、標價
- [ ] 設置產品經理（每條產品線的聯絡人）
- [ ] 上傳資料表 —— 產品記錄上的一個 PDF 檔案欄位，供人開啟檢視；沒有任何知識庫會攝取它

## ✅ 第 4 天 —— 流程

### 10. 商機階段

確認 7 階段預設管道與你的銷售流程相符。各階段及其概率為：

| 階段 | 概率 |
| --- | --- |
| Prospecting | 10% |
| Qualification | 25% |
| Needs Analysis | 40% |
| Proposal | 60% |
| Negotiation | 80% |
| Closed Won | 100% |
| Closed Lost | 0% |

如果你的流程不同，那是一次原始碼修改，不是在某個畫面上調整：**並不存在「Setup → Opportunity → Stages」這個頁面**。七個階段是 `stage` 欄位自己的選項（`src/objects/_picklists.ts` 裡的 `OPPORTUNITY_STAGE_OPTIONS`），機率則是 `src/objects/opportunity.hook.ts` 裡的 `STAGE_PROBABILITY` 對應表 —— 它在每次儲存時都按階段重新推導 **Probability** 與 **Expected Revenue**，所以手工填在商機上的機率撐不過下一次儲存。改動其中任何一項都是程式碼改動加一次重新部署。

### 11. 工單 SLA

確認預設的 [SLA 矩陣](/zh-Hant/docs/service/sla-and-escalation)：

| 優先級 | Strategic | Enterprise | Mid-Market | SMB |
| --- | --- | --- | --- | --- |
| Critical | 4h | 4h | 4h | 4h |
| High | 6h | 8h | 8h | 8h |
| Medium | 24h | 36h | 48h | 48h |
| Low | 96h | 120h | 168h | 168h |

**每一個格子都是應用真正在守的期限。** `case_sla_defaults` 鉤子（`src/objects/case.hook.ts`）在每一張工單上把 `sla_due_date` 蓋成 *目前時間 + 相應的日曆小時數*，每小時跑一次的 `case_sla_monitor` 會撈起其中任何一張到期日已過的。走哪一欄由帳戶的**客戶層級**決定 —— 所以確認這張矩陣，也就意味著確認你的帳戶確實分好了層級。層級為空的帳戶，或者建單人讀不到的帳戶，一律按 **SMB** 對待。

**這裡沒有「首次回應目標」可確認。** 本清單曾經帶著整整一欄 *首次回應*（Critical 1 小時一直到 Low 1 個工作日），這四個數字在應用裡哪兒都不存在；本節連過去的那一頁 SLA 文件也沒有首次回應目標。真正存在的是那個時間戳：**First Response Date** 在工單上第一次記錄 *已經發生過* 的互動時被寫入（`event_activity_bubble` 鉤子，`src/objects/event.hook.ts`）。它從不與任何目標比較 —— `case_metrics` 沒有宣告任何首次回應度量，因此沒有報表、沒有儀表板磁貼會報它，也沒有任何流程會為它告警。你當然可以對客戶承諾一個首次回應時長；應用只是記下它何時發生，別的什麼都不做。

如果你的支援承諾不同，請自行調整 —— 這十六個數字寫在 `src/objects/_case-sla.ts` 與 `src/objects/case.hook.ts` 裡的一張對應表中，不在任何 Setup 畫面上，而且兩處必須同步修改。

### 12. 工單路由 —— 沒有需要設定的東西

**不存在「Setup → Case Settings」這個畫面**，也沒有任何路由規則可寫。一張無所有者的工單 —— 最常見的來路是網頁轉工單（web-to-case）提交 —— 會在插入時由 `case_auto_assign`（`src/objects/_case-assignment.ts`）指派：交給持有 `service_agent` 職位的人當中**未結工單最少**的那一位，這裡的「未結」指狀態既不是 *Resolved* 也不是 *Closed*。這和潛在客戶那一側是同一種自平衡輪詢：比的是誰負載最輕，而不是按次序輪換，也不是按產品、區域或來源比對的規則；沒有區域路由，也沒有佇列。它**只在插入時執行**，而且只處理到達時就沒有所有者的工單 —— 它不會在之後把工單從某個人手上拿走，也不會在客服自己新建工單時觸發，因為掛鉤跑起來之前平台已經把建立者蓋成了所有者。它也從不阻斷工單進入：當人員池根本讀不到時（匿名網頁轉工單表單就是這種情形），工單照樣被記錄下來，只是無主。而如果沒有人持有 `service_agent`，這個掛鉤什麼也不做，工單就一直無主，停在[工單](/zh-Hant/docs/service/cases)頁面的 **未分派 — 待分診** 頁籤裡。那個頁籤正是這個掛鉤「什麼也不做」這條路徑的可見化，所以給這個職位配上人本身就是一次行為變化：新工單不再無主到達，也不再出現在那裡。**這不是升級交接**：那是另一個人員池、另一個時機 —— 它掛在轉為 *Escalated* 的狀態遷移上，把工單交給持有 `service_manager` 職位的人當中負載最輕的那一位（參見 [SLA 與升級](/zh-Hant/docs/service/sla-and-escalation)）。

- [ ] 把 `service_agent` 職位指派給每一位應當接收工單的客服 —— 這個人員池*就是*路由表
- [ ] 在還沒有人持有它的時候，盯住工單頁面的 **未分派 — 待分診** 頁籤：它列出的正是這個掛鉤沒能指派掉的工單

### 13. 審批流程

- [ ] 確認折扣審批閾值（預設 $500K）—— 參見 [審批](/zh-Hant/docs/revenue/approvals)
- [ ] 確認審批人（按角色：經理 + 總監）
- [ ] 透過提交一個範例商機進行測試

## ✅ 第 5 天 —— 知識與 AI

### 14. 知識文章

HotCRM 只附帶**一個**知識物件，而不是一組知識庫。下面每一條都是你在**服務 → 知識**下建立的普通記錄，歸入該物件定義的七個分類之一。

- [ ] 把最熱門的 20 個 FAQ 寫成文章，歸入**故障排查**、**操作指南**或**入門指南**
- [ ] 把支援時間、SLA 承諾和資料處理說明歸入**政策制度**
- [ ] 逐篇設定**受眾** —— 操作手冊用*僅內部*，你願意發給客戶的用*公開*
- [ ] 把它們**發布** —— Copilot 只查詢已發布的文章，草稿等於不存在
- [ ] 收工前複核一遍分類和標籤：匹配靠的是分類與標籤而不是語義，歸錯的文章就是找不到的文章

沒有任何叫 *銷售知識*、*產品資訊* 或 *競爭情報* 的東西可以填充種子內容 —— HotCRM 不附帶這些庫，也沒有可供對戰卡掛靠的競爭對手物件。Copilot 拿一篇文章能做什麼、不能做什麼，參見 [知識庫](/zh-Hant/docs/ai-copilot/knowledge-bases)。

### 15. AI Copilot

Setup 裡沒有 *AI* 分組，也沒有任何畫面能把 Copilot 打開。Setup 裡與 AI 相關的只有兩處：**Setup → Configuration → AI & Embedder**（設定供應商、模型與 Embedder），以及 **Setup → Configuration → Feature Flags** 底下那個預設關閉、平台裡沒有任何東西讀取的測試版 *AI Assistant* 開關。讓 Copilot 能作答的是一個設定好的供應商；它能跑哪些技能由應用本身決定，不屬於安裝環節。作為導覽分組的 *AI* 在 **Studio → AI**（Agents / Tools / Skills）。

- [ ] 確認 **Setup → Configuration → AI & Embedder** 裡選的是一個真實供應商 —— 它預設是 *Memory (echo — testing only)*，只把你的輸入原樣回顯而不作答 —— 然後按 *Test connection*
- [ ] 執行一個範例查詢（*「給我 [測試客戶] 的 Customer 360」*）以驗證 —— 能引用真實記錄作答，就表示供應商已生效
- [ ] 在 **Studio → AI → Skills** 裡過一遍 Copilot 隨附的技能 —— 它們都是啟用的；有哪些技能由應用決定，而不是在這裡挑選（參見 [技能](/zh-Hant/docs/ai-copilot/skills)）
- [ ] 不要去找 AI 脫敏規則，去看欄位層級安全：Copilot 以目前登入使用者的身分讀取，某個欄位在他的權限設定檔裡被遮罩，就永遠到不了 Copilot（參見 [共用與安全](/zh-Hant/docs/administration/sharing-and-security)）

## ✅ 第 6 天 —— 儀表板與報表

- [ ] 將 **CRM 概覽** 固定為所有人的主頁儀表板
- [ ] 設定團隊專屬儀表板（銷售 / 服務 / 高管）
- [ ] 為經理安排每週訂閱郵件
- [ ] 審查 [標準報表](/zh-Hant/docs/analytics/reports) 並自訂篩選器

## ✅ 第 7 天 —— 上線

- [ ] 執行 **遷移檢查**（所有匯入的記錄都有所有者和必填欄位）
- [ ] 執行 **冒煙測試**：建立潛在客戶 → 轉化 → 商機 → 報價 → 贏單 → 合約
- [ ] 培訓使用者掌握他們的日常工作流（45 分鐘的基於角色的會話）
- [ ] 設置一個內部 **#hotcrm-help** 頻道用於答疑

## 上線後

- **第 2 週**：審查儀表板使用情況和採用指標。
- **第 1 個月**：首次回顧 —— 哪些有效，哪些無效。
- **每季度**：審查權限設定檔、共用規則、知識庫是否有漂移。
