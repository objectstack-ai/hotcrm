# 自動化

自動化讓 HotCRM *為你完成工作* —— 傳送通知、更新欄位、建立任務、升級案例，全程無需任何人點擊按鈕。提供四種自動化，每一種都適用於不同的工作。

> **HotCRM 如何實作它們：** 驗證與欄位邏輯以 **物件鉤子**（`beforeInsert` / `beforeUpdate`）執行；所有多步驟、排程或審批類邏輯以 **流程** 執行；審批則是 **流程中的 `approval` 節點**（ADR-0019），而非獨立的審批流程類型。獨立的工作流規則與審批流程中繼資料在平台上同樣不存在 —— ADR-0019 與 ADR-0020 已移除這兩種類型。

## 四種類型

| 類型 | 觸發時機 | 最適合 |
| --- | --- | --- |
| **驗證規則** | 儲存前 | 攔截不良資料 |
| **流程** | 螢幕、記錄變更或按排程 | 多步驟邏輯、分支、迴圈、等待、審批 |
| **排程作業** | 按排程 | 每日清掃、每週報表 |
| **審批流程** | 流程中（approval 節點） | 帶記錄鎖定的多步驟簽核 |

## 驗證規則

最簡單的類型。當某個條件為真時，它們會阻止儲存。

**內建範例**：

- *「結束日期必須晚於開始日期」*（用於合約）。
- *「標價必須大於零」*（用於產品）。
- *「行銷活動成員必須有一個潛在客戶或一個聯絡人，但不能兩者都有」*（用於行銷活動成員）。
- *「折扣百分比必須介於 0 和 100 之間」*（用於報價行項目）。

要新增一條：

1. **設定 → 物件 → 驗證規則 → 新增**。
2. 撰寫條件（*失敗* 條件）。
3. 撰寫向使用者顯示的錯誤訊息。
4. 啟用。

## 流程（多步驟）

> **在找「工作流規則」？** 沒有可找的東西 —— 本應用沒有，平台上也沒有。ObjectStack 已退休獨立的工作流規則類型（ADR-0019 / ADR-0020）：不存在 `workflow` 中繼資料類型，stack 上沒有 `workflows` 集合，**設定 → 自動化** 下也沒有 *工作流規則* 入口，只有 *流程*。所謂「這條記錄一儲存就做某事」的規則就是 **記錄變更類流程**，本應用發布的每一條都在下表中占一行。

當單純的欄位更新不夠用時 —— 分支、迴圈、等待、跨物件寫入、審批 —— 使用 **流程**。流程是一張視覺化的節點圖：取得資料 → 判斷 → 建立/更新記錄 → 通知 → 等待 → 呼叫子流程。

流程有三種觸發方式，由起始節點決定：

- **螢幕（Screen）** —— 從按鈕/操作手動啟動，在螢幕上收集輸入。
- **記錄變更（Record change）** —— 在記錄插入/更新時觸發（`record-after-create` / `record-after-update`）。
- **排程（Schedule）** —— 按 cron 排程執行。

> **自動觸發需要 `triggers` 能力。** 記錄變更與排程類流程，只有當 stack 的 `requires` 列表包含 `triggers` 時才會觸發 —— 它會安裝記錄變更與排程觸發器提供方（排程觸發器還依賴 job 服務）。螢幕類流程始終為手動啟動。

**HotCRM 中的內建流程**（26 個）。每一行用的都是流程自身的標籤 —— 也就是你在 **設定 → 流程監控器** 與 **設定 → 排程作業** 裡看到的名字，因此監控器裡的一次執行可以逐字回到這張表裡查：

| 流程 | 觸發 | 它做什麼 |
| --- | --- | --- |
| **線索轉化流程** | 螢幕 | 將合格潛在客戶轉化為客戶 + 聯絡人（+ 可選商機），然後通知 |
| **由商機產生報價** | 螢幕 | 從商機生成報價，並將其推進到 *Proposal* |
| **安排跟進** | 螢幕 | 在線索上建立下一個跟進任務，並已掛好關聯與負責人 |
| **將成員登記進行銷活動** | 螢幕 | 批次把符合條件的線索或聯絡人登記進本行銷活動，跳過已登記與已退訂的 |
| **升級案例** | 螢幕 | 收集升級原因，然後標記案例並調整其優先級 |
| **關閉案例** | 螢幕 | 收集處理結論，然後關閉案例並停掉 SLA 計時 |
| **新線索路由與 SLA** | 記錄變更（插入） | 按評級寫入跟進 SLA，並提醒新線索的負責人 |
| **聯絡人歡迎** | 記錄變更（插入） | 新建聯絡人後，提醒負責人去做首次問候 |
| **緊急任務提醒** | 記錄變更（插入） | 任務以 *Urgent* 建立時通知其負責人 |
| **大額商機審批** | 記錄變更（更新） | 透過 approval 節點分級簽核 —— 銷售經理 > $100K，銷售總監 > $500K |
| **大額商機審批（新建時）** | 記錄變更（插入） | 同一套受理邏輯，用於*建立時*金額已超過閾值的商機 |
| **大額商機贏單提醒** | 記錄變更（更新） | 金額超過 $100K 的商機轉為 *Closed Won* 時，通知負責人 —— 只通知負責人本人，不通知其經理 |
| **計費交接：贏單** | 記錄變更（更新） | 商機轉入 *Closed Won* 的那一刻，向計費端點投遞一次帶重試的 POST：商機 + 客戶 + 行項目 |
| **計費交接：合約啟用** | 記錄變更（更新） | 合約轉入 *Activated* 的那一刻，向計費端點投遞一次帶重試的 POST：合約 + 客戶 + 來源商機的行項目 |
| **案例升級流程** | 記錄變更（更新） | 當案例變為 *Critical* 時，標記為已升級、移交給 `service_manager` 職位中負載最輕的持有者（該職位無人時案例保留原負責人），並通知它原來那位負責人；升級同時會給客戶負責人建立一條緊急跟進任務 |
| **案例升級流程（新建時）** | 記錄變更（插入） | 同一套升級邏輯，用於*建立時*就是 *Critical* 的案例 |
| **案例滿意度回訪** | 記錄變更（更新） + 等待 | 案例關閉後等待 1 天，再提醒負責人收集滿意度評分 |
| **合約自動到期** | 排程（每日 0 點） | 將已啟用且超過 `end_date` 的合約置為到期，並通知負責人 |
| **報價自動過期** | 排程（每日 1 點） | 將超過 `expiration_date` 且仍未關閉的報價置為過期 |
| **行銷活動自動完成** | 排程（每日 2 點） | 將 `end_date` 已過的進行中行銷活動標記為 *Completed* |
| **預測快照** | 排程（每日 3 點） | 為每位活躍商機負責人寫入本季預測行 —— 管道、最佳情況、承諾與已成交金額 |
| **停滯商機提醒** | 排程（每日 7:30） | 提醒負責人關注在某階段停留過久的未結商機 |
| **合約續約提醒** | 排程（每日 8 點） | 為臨近 `end_date` 的合約開出續約任務/商機 |
| **案例 SLA 監控** | 排程（每小時） | 標記並升級超過 SLA 到期時間的未結案例 |
| **任務到期提醒** | 排程（每小時） | 通知負責人：其任務的提醒時間已到 |
| **展示資料啟動** | 排程（每 10 分鐘） | 為首位使用者認領無歸屬的種子記錄，寫入其 `owner_id` |

有兩組條目帶 **（新建時）** 孿生流程。記錄變更類流程每條只訂閱一種觸發類型 —— `record-after-create` *或* `record-after-update` —— 所以「新建與後續修改都要管」的自動化會被寫成條件相同的一對流程。它們在這裡各占一行，因為在流程監控器裡它們就是兩次獨立執行。

**展示資料啟動** 屬於腳手架，而非業務自動化。種子寫入會繞過安全中介層，因此種子記錄落地時沒有負責人 —— 這會讓所有「我的 …」檢視變空，並讓所有寄給負責人的通知無人可達。這條清掃把它們寫到首位使用者名下。在記錄本就有負責人的組織裡，它每十分鐘選中零條記錄、什麼也不做。

流程內的通知由 **`notify` 節點** 投遞（透過訊息服務傳送站內信 + 郵件）—— 而非舊的 `script`/郵件步驟（在 7.4 中已是空操作）。

如果你需要建構新的流程，請參見 [自訂 › 擴充物件](/zh-Hant/docs/customization/extending-objects)。

## 排程類自動化

基於時間的自動化以 **排程類流程** 實作 —— 即起始節點帶 cron 排程的流程。上表中九個 `排程` 行就是全部；不存在另一套需要另找的「排程作業」中繼資料。它們透過 job 服務執行，因此 `triggers` 能力需與 `job` 搭配（兩者都在預設能力集中）。

無需編排的日期驅動欄位邏輯 —— 例如為報價設定預設過期日、凍結已過期/已接受的報價、推導預測週期 —— 放在輕量的 **物件鉤子**（`beforeInsert` / `beforeUpdate`）中，而非排程清掃。

預測這一塊的分工值得單獨點出來，因為它正是要照抄的模式：**預測快照** 流程決定*誰*會拿到快照、*各項合計是多少*，而預測物件的鉤子決定*這筆快照屬於哪個日曆週期*。一條 cron 排程說得出「每晚」，卻說不出「本季的第一天」—— 所以這個週期邊界由物件統一推導一次，供每個寫入方共用。

## 審批

自 ObjectStack 7.4 起，審批被建模為 **流程中的 `approval` 節點**（ADR-0019），而非獨立的審批流程類型。進入節點時會建立審批請求、在該步驟待批期間 **鎖定記錄**、將即時狀態鏡像到 `approval_status` 欄位，並沿 *approve* / *reject* 分支繼續。

HotCRM 內建的 **商機審批** 流程串聯兩個 approval 節點實作分級簽核（經理 → 總監）。關於閾值、審批人所見以及稽核軌跡，參見 [收入 › 審批](/zh-Hant/docs/revenue/approvals)。

## 操作順序

當一條記錄被儲存時，順序是固定的：

1. **系統** 執行自動計算（公式欄位、自動編號）。
2. **驗證規則** 執行 —— 如果有任何失敗，儲存被阻止。
3. **記錄被儲存** 到資料庫。
4. **流程觸發器** 觸發 —— 視本次儲存而定，是 `record-after-create` 或 `record-after-update`。
5. 這些流程內的 **`notify` 節點** 將站內信與郵件排入佇列。

流程自身的寫入也是普通儲存，因此它們會重新進入上面這份順序，並可能觸發更多流程。沒有可依賴的固定重評估次數：引擎用 **重入守衛** 打斷自觸發環 —— 若某條流程在上一次執行尚未結束時又因 *同一條記錄* 被重入，這次會被跳過，並記一條警告日誌。請把每條記錄變更類流程的起始條件寫到能自行止住對自身寫入的再觸發；守衛是兜底，不是停止條件。

理解這個順序有助於除錯 *「為什麼我的流程沒有觸發？」* 這類問題。

## 電子郵件範本

大多數自動化操作會傳送電子郵件。範本位於 **設定 → 電子郵件範本**，並支援：

- **合併欄位** —— `{{path.to.value}}` 佔位符，依每次傳送傳入的 `data` 酬載渲染。路徑的每一段都寫 HotCRM 自己的拼寫 —— 物件是 `crm_opportunity`、`crm_contact`，欄位是 `name`、`owner_id`、`email` —— 而不是 Salesforce 式的 `Opportunity.Name`。路徑從哪一層寫起，取決於傳送方傳入的酬載形狀；本應用沒有任何 `sendTemplate()` 呼叫方可供照抄，因此請把範本要讀取的名稱宣告在它的 `variables` 清單裡，並與傳送方約定好酬載形狀。
- **條件區塊** —— 僅在條件為真時顯示。
- **HTML + 純文字** 版本。
- **附件** —— 報價 PDF、合約 PDF。

HotCRM 自身不發布任何郵件範本：`src/` 下沒有撰寫任何一條，編譯產物裡也不含郵件範本中繼資料。潛在客戶路由、商機贏單、案例處理與續約提醒的通知，都由上表那些流程裡的 **`notify` 節點** 發出 —— 標題與內文直接寫在各自的流程裡，要改措辭就去改那裡。合約啟用不發任何通知：它由物件鉤子（`src/objects/contract.hook.ts`）執行，鏈路上沒有通知步驟；真正發出的合約郵件來自 **合約自動到期** 與 **合約續約提醒** 兩條流程。需要自行發送範本化外寄郵件時，再到 **設定 → 電子郵件範本** 裡新建範本。

## 在哪裡監控自動化

- **設定 → 流程監控器** —— 過去 24 小時的自動化執行及其成功/失敗。
- **設定 → 排程作業 → 歷史** —— 每個排程作業的過往執行。
- **物件 → 稽核日誌** —— 記錄上發生了什麼變化，誰/什麼進行了變更。

## 給管理員的提示

- ✅ **驗證規則** 是強制資料品質最廉價的方式 —— 放開手用。
- ✅ **每個條件一條流程** 比有 10 個分支的超級流程更易於維護。
- ✅ 只要超出單個欄位寫入 —— 分支、跨物件寫入、等待、審批 —— 就該放進 **流程** 而非物件鉤子：流程的每次執行在流程監控器裡看得到，鉤子程式碼看不到。
- ✅ 在生產中啟用前 **在沙箱中測試** —— 糟糕的自動化會快速級聯。
- ✅ 在描述欄位中 **記錄每條規則的作用** —— 未來的你會感謝現在的你。

## 給使用者的提示

如果一條記錄的行為不符合預期：

1. 檢查 **稽核日誌** —— 該欄位是被流程或物件鉤子更新的嗎？
2. 檢查 **任務清單** —— 是否有流程自動建立了一個你錯過的任務？
3. 請管理員檢查該記錄的 **流程監控器**。
