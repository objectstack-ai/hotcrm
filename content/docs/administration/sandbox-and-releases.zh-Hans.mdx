# 沙箱与发布管理

切勿直接在生产中进行配置变更。本页介绍安全的工作流：在沙箱中构建、测试、打包、提升到生产，必要时回滚。

**下文点名的这些屏幕，一个也不存在。** 设置里没有*沙箱管理*，没有*变更包*，也没有 *Git 同步* 入口 —— 它的导航是总览、应用、人员与组织、访问控制、审批、配置、诊断、集成、高级，而这些分组下面没有任何东西能开出一个租户或攒出一个变更集。下面写的是发布管理*应有*的形态，之所以保留，是因为它讲的纪律是对的。HotCRM 今天真正的做法是：它的元数据就是 `src/` 下的 TypeScript，在 git 里评审，随应用一起发布；已安装的软件包列在 **设置 → 软件包**。

> **下面每一条断言都被实测过，而且大多数没能存活。** 本页逐条对照应用自身的元数据
> （`src/`、`objectstack.config.ts`）与已安装的 `@objectstack/*` 包（spec 17.0.0-rc.6）
> 进行了核对。标注 *（未落地）* 的标题与表格行表示该能力并不存在 —— 没有对象、没有
> schema 键、没有 API。标注 *（无来源）* 的行保留了一个数字，但应用与平台都没有任何东西
> 在执行它。凡是真实能力以**另一种形态**存在的地方，都点名了真正的那一个。有两条断言
> 完全无法从这棵树上判定，就地说明。没有任何内容被删除 —— 对下一位读者而言，被删掉的
> 断言和错误的断言看起来一模一样。

## 什么是沙箱？

**沙箱** 是你的生产租户的全保真副本 —— 相同的模式，可选地包含相同的数据 —— 在隔离环境中运行，可以毫无后果地把它弄坏。这个概念是成立的，在 ObjectStack 里也确实存在。它只是不在本租户里面。

| 沙箱类型 | 其中包含什么 | 刷新频率 |
| --- | --- | --- |
| **仅配置** *（未落地）* | 仅模式 + 元数据，无记录 | 按需 *（无来源）* |
| **部分数据** *（未落地）* | 模式 + 一小部分记录样本 | 每周 *（无来源）* |
| **完整副本** *（未落地）* | 模式 + 所有生产数据（已匿名化） | 每月 *（无来源）* |

*未落地，而且在任何地方都不是这个形状。* 不存在 `sys_sandbox` 对象，任何已安装包里都没有 `sandboxType` 键，也没有"配置 / 部分 / 完整"这套分类。这张表真正想描述的东西是 ObjectStack **Cloud** 的*环境*，声明在 `@objectstack/spec/cloud` 的 `EnvironmentSchema` —— 一个组织的一个逻辑运行时对应一行，各自带有数据库、凭据与成员。它的 `type` 是一个七元枚举：

```
production | sandbox | development | test | staging | preview | trial
```

所以 `sandbox` 确实是一个真实取值 —— 但它是一种**环境姿态**，不是数据保真度层级，而上面那三种刷新频率没有任何对应物。环境活在控制面，通过 `/api/v1/cloud/environments/…` 寻址，而不是本租户内部的某一页。

企业版套餐通常包含 **3 个沙箱**；可按需添加更多。**未落地。** 任何地方都不存在沙箱数量权益 —— 已安装的包里没有 `sandboxLimit`、`maxSandboxes` 或 `sandboxQuota`。Cloud 的 `EnvironmentSchema` 确实带有 `plan` 字段（`free | starter | pro | enterprise | custom`），但挂在它上面的配额只有 `storageLimitMb`；没有任何东西在数环境个数。无论你的商业套餐怎么写，它描述的都不是这个应用能展示给你的能力。

## 创建与刷新沙箱

设计意图是这样的：有一个*沙箱管理*屏幕，在那里选择**类型**（配置 / 部分 / 完整）、命名（`dev`、`uat`、`training`）并点击**创建**；每一行上还有一个**刷新**，把最新的生产数据重新拉下来 —— 同时清掉沙箱里原有的一切。

并没有这样一个屏幕。开出一个环境是 ObjectStack Cloud 控制面的事，不是本租户设置里的某一页；设置里唯一与云相关的入口是 **设置 → 云连接**。

有一件事值得知道，因为它是这个应用真正能表达的唯一一条环境轴：在 `objectstack.config.ts` 里声明的种子数据是**按环境区分**的。每个 `data[]` 条目接受一个 `env` 列表，而这套词汇恰好只有三个取值：

```
data: [{ object: 'crm_account', env: ['prod', 'dev', 'test'], records: [...] }]
      env: ['sandbox'] → 被拒绝 —— Invalid option: expected one of "prod"|"dev"|"test"
      env: ['uat']     → 同样被拒绝
```

这也正是上面那套命名值得一提的原因：`uat` 与 `training` 不是平台认得的写法，在这条轴上 `sandbox` 也不是。

### 刷新时的匿名化 *（未落地）*

设计意图是这样的：对于完整副本沙箱，PII 会在数据拉下来的同时被匿名化 ——

- 电子邮件地址 → `user-{id}@example-anon.test`
- 电话号码 → 随机化但保留格式
- 姓名 → 看起来真实的假名
- 自由文本字段 → 保持原样（注意 —— 请审查敏感内容）

—— 这样沙箱就可以放心交给合作伙伴或外包人员。

这些都不存在。任何已安装的包里都没有匿名化、假名化或假数据生成器：在 51 个已安装 `@objectstack/*` 包的 1,158 个非 map 分发文件中，`anonymi[sz]`、`pseudonymi[sz]` 与 `fakeName` 的命中数都是零。也没有可以挂载它的"刷新"动作，因为根本没有沙箱可刷新。

有一个相邻机制确实是真的，而且是另一回事：对象上的 `publicSharing.redactFields` 会把点名的字段从通过公开分享链接暴露出去的记录中**去掉**。它是在某一个分享视图里隐藏字段；它不转换取值，不生成假值，和复制一个租户毫无关系。不要把它当成匿名化。

## 变更工作流

```
┌───────────┐   build    ┌─────────┐   test    ┌─────────┐   promote   ┌────────────┐
│ Developer ├──────────▶│   dev   ├──────────▶│   uat   ├────────────▶│ production │
└───────────┘            └─────────┘           └─────────┘             └────────────┘
                                                                              │
                                                                       rollback│
                                                                              ▼
                                                                       last working
                                                                          package
```

1. 在 `dev` 沙箱中 **构建** 变更。
2. **提升** 到 `uat` —— 业务用户在那里测试。
3. 需要 **UAT 签核** 才能继续。
4. 在变更窗口期间 **提升** 到 `production`。
5. 在生产中立即进行 **冒烟测试**。
6. 必要时 **回滚**。

*纪律是对的，但应用内没有任何机制。* 这里没有一步是被强制或被 HotCRM 看见的：租户内部没有提升动作、没有签核闸门、也没有环境阶梯。对这个应用来说，阶梯就是你的 git 分支和你的部署流水线，上面每一步都是人或 CI 做的事。纪律请保留；别去找按钮。

## 变更包

**变更包** 将一组元数据变更（对象、字段、验证、流程、共享规则等）捕获为单个可部署的工件。

这个工件是真实的，而且这是全页中心智模型最接近事实的一处 —— 只不过该单位是构建产出的，不是手工拼装的。`objectstack compile` 产出一份编译后的 `ObjectStackDefinitionSchema`，Cloud 控制面把它包进一个**环境工件**（`EnvironmentArtifactSchema` —— `environmentId`、`commitId`、SHA-256 `checksum`，外加编译后的定义），并在启动时交给运行时。它是不可变的、内容寻址的。另外，`@objectstack/spec/system` 里的 `ChangeSetSchema` 才是真正的*迁移*单位：一份具名、有序的 `add_field` / `rename_object` / `delete_object` / `execute_sql` 操作列表，带声明的依赖，记录在 `sys_migration` 与 `sys_migration_journal` 中。

### 创建包

设计意图是这样的：一个*变更包 → 新建*的屏幕，填名称与描述，用手动 / 按标签 / 自上次打包以来自动这三种方式添加组件，再**验证**一致性并**保存**。

并没有这样一个屏幕。这里的"包"是平台自己的单位 —— 列在 **设置 → 软件包** 和 **Studio → 软件包** —— 而 HotCRM 自己的元数据是在构建时从源码打包的，从不在界面里拼装。

### 部署包

设计意图是一个五步向导。实测下来，其中一步是真的，两步描述的是构建，还有两步没有落地：

1. 从源沙箱 → **部署 → 选择目标租户**。*（未落地）* —— 没有部署屏幕、没有租户选择器，也没有可供部署的源沙箱。
2. **试运行** —— 将会变更什么、将会创建什么、存在什么冲突。**真实存在，形态是一条 CLI 命令。** `os migrate plan` 在 `@objectstack/cli` 中被记述为"元数据与物理数据库之间的试运行差异对比，按 安全 / 需确认 / 破坏性 分类"，并且"从不改动模式" —— 这是被强制的而非仅仅写在文档里，因为该栈启动时会推迟 DDL 并抑制工件种子。本应用依赖 `@objectstack/cli`，所以这条命令你今天就能用。
3. 审查变更集。**真实存在** —— 那就是 `os migrate plan` 的输出，在终端里读，而不是在某个评审屏幕里。
4. **部署** —— 仅配置变更通常 &lt;2 分钟。*（无来源）* —— 这个数字没有任何东西在测量。应用与已安装包里没有任何东西给部署计时；而对 HotCRM 来说，"部署"意味着你自己的流水线发布一个新构建，其耗时是那条流水线的属性。
5. **审计日志** 捕获谁在何时部署了什么。*（对部署而言未落地。）* `sys_audit_log` 是真实的，会记录数据与元数据活动，但没有任何部署事件写入其中 —— 租户内部根本没有部署这件事可记。

### 哪些可以打包

诚实的答案不是一张九是三否的表，而是编译后工件的键集合。`ObjectStackDefinitionSchema` 恰好接受 **42** 个顶层键：

```
manifest datasources datasourceMapping translations i18n objects
objectExtensions apps views pages dashboards reports datasets actions
themes flows jobs emailTemplates docs books positions permissions
capabilities sharingRules apis webhooks api server agents tools skills
hooks functions mappings analyticsCubes connectors data plugins requires
tiers devPlugins runtimeModule
```

逐行对照旧表：

| 旧表行 | 判定 |
| --- | --- |
| 对象、字段、验证 | ✅ `objects`（字段与验证声明在对象内部） |
| 流程 | ✅ `flows` |
| 共享规则、权限档案、权限集 | ✅ `sharingRules` + `permissions` —— 但没有 `profiles` 键；权限档案就是权限集 |
| 页面、列表视图、仪表板 | ✅ `pages`、`views`、`dashboards` |
| 报表、dataset | ✅ `reports`、`datasets` |
| AI 技能、知识库配置 | ⚠️ `skills` 是键；**不存在知识库配置这个键** —— 知识文章就是普通记录 |
| 审批流程 | ⚠️ **没有这个键。** 独立的 `approvals` 栈字段在 ObjectStack 7.4 被移除；审批是带 `approval` 节点的 `flows`（ADR-0019），因此按流程打包 |
| 电子邮件模板 | ✅ `emailTemplates` 是键 —— 尽管本应用一个都没写 |
| **数据记录** | ❌ → **✅ 写错了，而且这条值得纠正。** `data` 是顶层工件键，HotCRM 通过它发布了 21 个种子族。记录完全可以打包，还能按环境区分（`env: ['prod','dev','test']`），并带 upsert `mode` 与 `externalId` |
| **文件** | ✅ ❌ 判定正确 —— 没有文件键，而且**不存在文件同步 API** 可用；那条建议指向的是空的 |
| **用户账户** | ✅ ❌ 判定正确 —— 没有用户键。SCIM 作为平台面确实存在（`sys_scim_provider`），但在本租户里没有任何屏幕 |

⚠️ 未知的顶层键是**被丢弃，而不是被拒绝** —— `ObjectStackDefinitionSchema` 解析一个含 `approvalProcesses` 的栈会成功，并悄悄把它扔掉。所以不在上述 42 个之列的键不会让你的构建失败；它只是永远到不了工件里。

## 版本控制（基于 git）

没有 *Git 同步* 这个入口可连 —— 而对 HotCRM 来说，它也无事可做。元数据**本身**就是 git 仓库：每一个对象、字段、验证、流程、视图和共享规则都是 `src/` 下的 TypeScript。所以一个同步页面本该解锁的东西，本来就是这个应用的构建方式：

- 通过 PR 进行 **代码审查**。
- 分支之间的 **差异对比**。
- 每次变更的 **历史**。
- 在合并前运行 `pnpm typecheck` 等的 **CI**。

把团队指向仓库，而不是设置页。

## 回滚

两种形式：

### 快速回滚（24 小时内）

设计意图是这样的：每次部署都留下一个**还原点**，再由一份*部署历史*列表让你在 24 小时内回滚某一次 —— 还原元数据，同时保留部署之后新建的记录。

并没有任何部署历史被记录下来，也没有回滚按钮。回滚的做法是把上一个版本的应用重新部署一次 —— 从产出当前版本的同一份源码。

### 重新部署之前的包 *（本租户内未落地）*

如果已经过去 >24 小时，请重新部署 **上一个成功的包** —— 同样的 UI，只需选择较旧的包版本。这里没有这样的 UI，也没有包版本列表：HotCRM 的版本就是它的构建（`manifest.version`，`2.2.2`），而上一个版本是一个 git tag。

这背后确实有两套真实机制，都在租户之外。在 Cloud 控制面，`RollbackEnvironmentPackageRequestSchema` 能把一次**包安装**回滚到点名的 `targetPackageVersionId`。在元数据存储里，`sys_metadata_commit` 把一次编写回合的变更归为一组，是 `revertCommit` / `rollbackToPackageCommit` 的句柄 —— 只追加，所以一次撤销会被记为一次新提交，而不是抹掉旧的。两者都不是本页上的按钮，而且都不适用于一个元数据从源码发布的应用。

⚠️ 如果你回滚模式变更，针对新模式创建的数据可能需要迁移。请务必在真正需要之前先演练回滚 —— 另外注意，`os migrate plan` 会在你执行之前就把破坏性变更给你分好类。

## 生产变更窗口

最佳实践，而且完全是人的流程 —— 下面没有一条是应用强制的：

- **非高峰窗口**（通常是周末或周五晚 7 点）用于非简单部署。
- 在重大业务事件前设置 **冻结期**（季度末、大型发布）。
- 在公司 #cm-announcements 频道 **公告**。
- 任何生产部署都要有 **2 名管理员** 在场（四眼原则）。
- 部署后立即运行 **冒烟测试清单**。

## 冒烟测试清单

每次生产部署后 —— 除标注处外，下面每一步都会真正走通 HotCRM 已落地的东西：

- [ ] 以测试用户身份登录。
- [ ] 创建潜在客户 → 转化 → 商机 → 报价 → 合同。
- [ ] 创建工单 → 分诊 → 解决。
- [ ] 运行主页仪表板 —— 所有图块加载。
- [ ] 在联系人上用 **发送邮件** 发一封测试邮件。（原步骤写的是"通过已连接的收件箱"—— 并不存在收件箱连接器；见[电子邮件与日历](/zh-Hans/docs/guides/email-and-calendar)。）
- [ ] 在真实记录上调用一个 Copilot 技能。
- [ ] 抽查变更的组件。

## 监控与提醒

本节承诺的三种提醒全部不存在，其中第三条要仔细读：

- 每次提升时向 Slack/Teams 发送 **部署提醒**。*（未落地。）* 缺的是两样东西，不是一样。本租户里没有可供提醒的部署事件；而且没有安装任何 Slack 或 Teams 连接器 —— `connector_action` 是平台内建的流程节点，但平台交付它时连接器注册表是**空的**，具体连接器（`@objectstack/connector-slack`、`@objectstack/connector-rest` 等）以独立插件形式提供，而本应用一个都没装、一个都没注册。流程的 `http` 节点可以向任意 URL 发送请求，所以这个提醒你可以自己搭 —— 只是这里没有任何现成的东西在做它。
- **错误激增** 检测 —— 如果部署后错误激增，自动建议回滚。*（未落地。）* 已安装树中 `errorSpike` 与 `rollbackRecommend` 的命中数为零，也不存在任何形式的告警规则、阈值或异常检测面。"automatic rollback on failure" 这个说法确实出现在 `@objectstack/spec/kernel` 里 —— 那是一个**插件自动更新**设置（`rollback.automatic`、`keepVersions: 3`），讲的是某个插件版本安装失败，与部署本应用无关。
- **性能回归** 检测 —— 如果 p95 延迟下降 >20%，发出提醒。*（作为检测器未落地。）* `p95` 是真实词汇 —— `MetricAggregationType` 的成员，与 `p50`/`p90`/`p99` 并列 —— 所以 p95 是可以被*计算*出来的。不存在的是任何把它与基线做比较并发出提醒的东西：没有回归检测器、没有阈值规则，而且 `@objectstack/observability` 既不是本应用的依赖，也没有在 `objectstack.config.ts` 中接线。

> **本页无法判定的两条断言。** ObjectStack **Cloud** 控制面是否会向 Slack 或 Teams
> 发送部署通知，以及它是否会为其托管的环境监视错误率或 p95 延迟，都是那项托管服务的
> 属性 —— 不是本应用元数据的属性，也无法从已安装的包中读出。上面的表述的作用域是
> HotCRM 与已安装树：它们说的是这里没有任何东西在做这件事。如果你跑在 Cloud 上，
> 请询问运维你那套实例的人。

## 提示

- ✅ **小而频繁** 的发布胜过大型的季度发布 —— 上面每一个屏幕都不存在，这条纪律依然成立。
- ✅ **为发布清晰命名** —— `2026-Q1-pipeline-revamp` 而非 `Package 47`。对这个应用而言，名字就是一个 git tag 加一次 `manifest.version` 提升。
- ✅ 在发布模式变更前 **运行 `os migrate plan`**。它是设想中那个部署向导里你真正拥有的那一块，会告诉你哪些变更是破坏性的。
- ✅ **在 git 里评审。** 元数据就是仓库，所以 PR 评审*就是*变更控制流程 —— 没有第二套可供连接。
- ✅ **演练回滚** —— 对 HotCRM 来说就是重新部署上一个 tag，所以要确保真的有人做过一次。
- ⛔ 不要围绕沙箱、变更包、部署提醒或自动回滚来规划。上面它们每一个都被标注为 *（未落地）*，在它们之上搭流程等于搭在空气上。
