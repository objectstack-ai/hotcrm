# 知識庫

HotCRM 的知識只有**一個**去處：**知識文章**物件（`crm_knowledge_article`），從導覽的**服務 → 知識**進入。Copilot 讀它用的，是它讀客戶、工單、商機時的同一批記錄工具。它下面沒有另一套檢索子系統，也沒有多個按團隊劃分的庫讓你挑。

## 並不存在四個知識庫

這一頁過去描述過四個內建知識庫——**銷售知識**、**產品資訊**、**支援知識**和**競爭情報**。HotCRM 一個都不附帶，也從未附帶過：沒有任何元資料以這些名字宣告過知識庫，沒有任何技能繫結到其中之一，Setup 裡也沒有可供填充種子內容的地方。如果你照著舊版頁面去找過，那就是你什麼也沒找到的原因。

真正存在的，是一個文章物件加一個**分類**選項集。四條承諾各自的實際落點是：

| 舊名字 | 今天的實情 |
| --- | --- |
| **銷售知識**——銷售劇本、異議處理、資格判定框架 | 在現有選項集裡無處安放。七個分類是為產品與支援內容寫的，沒有銷售劇本這一類。把劇本歸到**操作指南**或**政策制度**下也能用，但那是你自己的約定，不是產品自帶的約定。 |
| **產品資訊**——資料表、規格、版本說明 | 歸入**版本說明**、**API 與整合**或**帳務與價格**的文章。產品自己的**規格書**仍舊只是產品記錄上的一個檔案——見下文。 |
| **支援知識**——故障排查、操作手冊、FAQ | 歸入**故障排查**、**入門指南**或**操作指南**的文章。選項集本來就是為這類內容寫的，也是四條承諾裡唯一大體兌現的一條。 |
| **競爭情報**——競爭對手畫像、對戰卡 | 沒有落點。HotCRM 沒有競爭對手物件：僅供示範的 `crm_competitor` 模組已被刪除，這一行是活得比它久的文字（#790 從共享與權限頁面清掉的是同一批殘留）。應用裡僅有的競爭對手資料，是商機上"輸給競爭對手"這一條丟單原因，以及它旁邊的自由文字**丟單詳情**——商機上原有的**競爭對手**選項集只有無人讀取的佔位選項，已由 #1061 退役。 |

## 一篇文章是什麼

一筆記錄，加上幾個真正決定檢索結果的欄位：

| 欄位 | 作用 |
| --- | --- |
| **文章編號** | `KA-0001`，自動產生——Copilot 引用的就是它。 |
| **標題**與**摘要** | 兩者都可檢索。摘要是一段話的要點，顯示在搜尋結果和 AI 引用裡。 |
| **正文** | 文章本身，Markdown 格式。 |
| **分類** | 入門指南 · 操作指南 · 故障排查 · 帳務與價格 · API 與整合 · 版本說明 · 政策制度。 |
| **標籤** | 身分認證 · 單一登入 · 行動端 · 郵件 · 報表 · 效能 · 資料匯入 · Webhook。 |
| **狀態** | 草稿 → 審核中 → 已發布 → 已歸檔。 |
| **受眾** | 公開或僅內部。 |
| **語言** | 英語 · 簡體中文 · 西班牙語 · 日語。 |

分類與標籤是 Copilot 用來匹配的那套固定詞彙，因此這兩個欄位決定一篇文章能不能被找到。客服如何撰寫、複核、下架文章，參見 [服務 › 知識庫](/zh-Hant/docs/service/knowledge-base)。

## Copilot 如何取到一篇文章

靠查詢這個物件——和它查詢工單的方式一模一樣：

1. 讀取眼前的工單，取它們的**分類**和**標籤**。
2. 在 `crm_knowledge_article` 上查詢與之匹配的**已發布**文章。
3. 按文章編號（`KA-0007`）標注用了哪幾篇，你可以開啟記錄核對。

這是一次帶過濾條件的記錄查詢，不是語義檢索。匹配依據是人工設定的分類與標籤，所以一篇歸錯分類的文章，正文答得再好，對 Copilot 也是不可見的。

### 到底哪些技能會讀文章

| 技能 | 會讀文章嗎？ |
| --- | --- |
| 🔭 **Customer 360°** | **會**——它的指令第 3 步會按剛讀到的工單的分類或標籤去查詢已發布文章。也只有它會。 |
| 🚦 **工單分流** | 不會。它宣告了 `describe_object` 與 `get_record` 兩個工具，完全沒有檢索類工具——它檢索不了任何東西，文章也不例外。 |
| ✍️ **郵件撰寫** | 不會。它*本可以*——它帶著 `query_records`——但它的指令裡沒有任何一步去取文章，因此沒有哪份草稿會引用文章。 |
| 🎯 **潛在客戶資格判定** · 📈 **收入預測** · 🔄 **即時資料** | 不會。它們都沒有取知識的步驟。 |

所以"問 Copilot，它會找到那篇文章"具體指的是 **Customer 360°**。向工單分流要匹配文章，你只會拿到一個優先級。

### 為什麼沒有語義檢索

平台確實提供了一個知識檢索工具，但它檢索的是一個*已宣告的知識來源*，而知識來源只能宣告在 agent 上。HotCRM 交付的是技能而不是 agent，因此沒有地方去宣告它——那個工具即便掛上也只會解析成功、返回為空。直接查詢物件，是同一件事的誠實版本，也正是這些技能在做的事。

## 不存在的東西

明確列出來，因為舊版頁面把這些全都承諾過：

- **沒有文件攝取。** 沒有任何東西會把 PDF、Word 或 Markdown 上傳進一個知識索引。一篇文章就是有人敲進去或貼上進去的一筆記錄。
- **沒有 `/knowledge/...` 目錄。** 應用裡不存在這樣一個 Markdown 檔案目錄，也沒有任何東西在監聽它。
- **沒有嵌入、分塊、檢索閾值和快取**，因此也沒有所謂"高於品質閾值的最相關的 5 個片段"。查詢返回的是匹配的記錄。
- **沒有夜間重新索引，也沒有手動重建索引的按鈕。** 一篇已發布文章在儲存的那一刻就可被查詢到，因為它是一筆記錄。
- **沒有連接器**去接 Confluence、Notion、Google Drive 或 SharePoint。
- **沒有按技能繫結知識的機制**，因此也無法新增一個知識庫（比如一個合規庫）再把它接到某個技能上。給文章物件加一個**分類**，才是產品自帶的劃分新內容域的方式，而那是一次元資料變更。

產品的**規格書**欄位最像例外：它確實是產品記錄上的一個真實檔案欄位，可放不超過 20 MB 的 PDF。但沒有任何東西讀取該檔案的內容——沒有技能，也沒有索引。它在那裡是給人下載的。

## 給管理員的提示

- ✅ **分類和標籤就是檢索面。** 一篇沒人找得到的文章，通常是歸錯了，而不是寫差了。重寫正文之前先審一遍分類。
- ✅ **發布它，否則它不存在。** 查詢只過濾已發布的文章；草稿和已歸檔文章對 Copilot 不可見。
- ✅ **內部文章要標成僅內部。** 受眾是人工設定的欄位，而面向客戶的答覆不該引用一份內部操作手冊。

## 給知識管理員的提示

- ✅ 文章要**短、可掃讀**，並把具體症狀（"Error 503"、"無法登入"）寫進**標題**和**摘要**——檢索讀的就是這兩個欄位加文章編號。
- ✅ **一篇文章只回答一個問題。** 分類匹配是粗粒度的，一篇同時回答三個不相關問題的文章，總會在錯誤的那個問題上被匹配出來。
- ✅ 當 **Customer 360°** 按某個工單的分類或標籤匹配不到任何文章時，那就是一個值得記下來的知識空缺。

各技能分別讀什麼、寫什麼，參見 [技能](/zh-Hant/docs/ai-copilot/skills)；自己寫一個技能，參見 [定制 › 新增 AI 技能](/zh-Hant/docs/customization/ai-skills)。
