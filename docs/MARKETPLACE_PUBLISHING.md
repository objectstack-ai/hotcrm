# ObjectStack Marketplace Publishing Guide

> **Last Updated**: February 16, 2026  
> **Target Audience**: Third-party plugin developers  
> **Protocol**: @objectstack/spec v3.0.0

## Overview

This guide explains how to publish HotCRM plugins or custom business packages to the **ObjectStack Cloud Application Marketplace**. The marketplace uses a two-phase publish workflow with automated security scanning and quality scoring to ensure plugin reliability and safety.

## 📋 Prerequisites

Before publishing to the marketplace, ensure you have:

### 1. ObjectStack CLI Installed

```bash
npm install -g @objectstack/cli
```

The `os` command provides marketplace publishing capabilities.

### 2. Verified Vendor Account

- Create an account at [ObjectStack Cloud](https://cloud.objectstack.dev)
- Complete vendor verification (admin/owner role required)
- Your vendor namespace will be used for package naming (e.g., `@vendor/plugin-name`)

### 3. Spec v3 Compliance

Your plugin must conform to `@objectstack/spec` v3.0.0:

- All objects validated with `ObjectSchema.create()`
- Plugin definition uses `PluginSchema.parse()`
- TypeScript with strict type checking enabled
- Zero TypeScript compilation errors

## 🏗️ Plugin Project Structure

A publishable plugin must follow this standard structure:

```
packages/my-plugin/
├── objectstack.json          # 📦 Publishing Manifest (required for marketplace)
├── objectstack.config.ts     # ⚙️ Runtime Configuration (defineStack)
├── package.json              # npm package metadata
├── tsconfig.json             # TypeScript configuration
├── README.md                 # Plugin documentation
├── CHANGELOG.md              # Version history
├── src/
│   ├── plugin.ts             # Plugin entry point (PluginSchema)
│   ├── *.object.ts           # Business object definitions
│   ├── hooks/
│   │   └── *.hook.ts         # Automation hooks/triggers
│   ├── actions/
│   │   └── *.action.ts       # AI actions and API endpoints
│   ├── workflows/
│   │   └── *.workflow.ts     # Workflow rules
│   └── translations/
│       └── *.ts              # i18n translations
├── __tests__/                # Test files
│   └── *.test.ts
└── dist/                     # Build output (generated by tsc)
    ├── index.js
    ├── index.d.ts
    └── ...
```

### `objectstack.json` vs `objectstack.config.ts`

HotCRM plugins use **two separate configuration files** with distinct purposes:

| File | Purpose | Format | Consumer | When Used |
|------|---------|--------|----------|-----------|
| **`objectstack.json`** | Marketplace publishing manifest | JSON | `@objectstack/cli` marketplace command | During `os marketplace publish` |
| **`objectstack.config.ts`** | Runtime stack configuration | TypeScript (defineStack) | `@objectstack/runtime` kernel | During app startup and local dev |

**Key Differences**:

- **`objectstack.json`**: Static metadata for the marketplace (name, version, category, permissions). Read by the CLI during publishing. Contains marketplace-specific fields like `category` and `objectstack.minVersion`.
- **`objectstack.config.ts`**: Dynamic configuration that defines the runtime stack (plugins array, manifest, features). Used by the ObjectStack kernel when loading the plugin at runtime.

**Workflow**:
1. Developer creates `objectstack.json` for marketplace metadata
2. CLI reads `objectstack.json` during `os marketplace publish`
3. Cloud validates and stores the package
4. User installs package from marketplace
5. Runtime loads plugin using `objectstack.config.ts` and `src/plugin.ts`

## 📦 `objectstack.json` Manifest Format

Create an `objectstack.json` file in your plugin root directory:

```json
{
  "name": "@vendor/plugin-name",
  "version": "1.0.0",
  "description": "Brief description of your plugin (max 200 characters)",
  "category": "app",
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "objectstack": {
    "minVersion": "3.0.0",
    "permissions": ["network", "storage"]
  }
}
```

### Field Descriptions

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | ✅ | Package name with vendor namespace (e.g., `@hotcrm/crm`) |
| `version` | string | ✅ | Semantic version (e.g., `1.0.0`) |
| `description` | string | ✅ | Brief description (max 200 characters) |
| `category` | string | ✅ | Marketplace category (see below) |
| `main` | string | ✅ | Entry point (relative to package root, e.g., `dist/index.js`) |
| `types` | string | ⚠️ | TypeScript declarations (e.g., `dist/index.d.ts`) |
| `objectstack.minVersion` | string | ✅ | Minimum runtime version (e.g., `3.0.0`) |
| `objectstack.permissions` | string[] | ⚠️ | Required permissions (e.g., `["network", "storage"]`) |

## ✅ Quality Requirements

ObjectStack Cloud enforces a **5-dimension quality scoring system** to ensure marketplace plugins meet professional standards.

### Scoring Dimensions

| Dimension | Weight | Requirements | Score Impact |
|-----------|--------|--------------|--------------|
| **Tests** | 25% | At least one test file (`.test.ts`), higher coverage = higher score | 0-25 points |
| **Documentation** | 25% | README.md, CHANGELOG.md, code examples | 0-25 points |
| **Types** | 20% | TypeScript type definitions (`.d.ts`), config schema validation | 0-20 points |
| **Security** | 15% | No critical/high vulnerabilities (see scanning rules below) | 0-15 points |
| **Structure** | 15% | Standard OPS directory layout (src/, dist/, tests/) | 0-15 points |

### Quality Grades

| Grade | Score Range | Publish Status |
|-------|-------------|----------------|
| **A** | 90-100 | ✅ Excellent - Featured in marketplace |
| **B** | 75-89 | ✅ Good - Published |
| **C** | 60-74 | ✅ Acceptable - Published with warning |
| **D** | 40-59 | ✅ Minimal - Published (low visibility) |
| **F** | 0-39 | ❌ **Rejected** - Does not meet minimum quality |

**Minimum Publishing Threshold**: **40/100** (Grade D or higher)

### Documentation Requirements

To achieve a high Documentation score (25 points):

1. **README.md** (required):
   - Installation instructions
   - Usage examples
   - API reference
   - Configuration options

2. **CHANGELOG.md** (recommended):
   - Version history
   - Breaking changes
   - Bug fixes and features

3. **Code Examples** (bonus):
   - Sample workflows
   - Integration examples
   - Common use cases

### TypeScript Requirements

To achieve a high Types score (20 points):

1. **Type Definitions**:
   - All `.ts` files compile to `.d.ts` declarations
   - Exported types are properly documented
   - No `any` types in public API

2. **Config Schema Validation**:
   - Plugin uses `PluginSchema.parse()`
   - All objects use `ObjectSchema.create()`
   - Workflows use `WorkflowRuleSchema.parse()`

## 🔒 Security Scanning Rules

ObjectStack Cloud performs **automated static analysis** on all published packages. The scanner enforces **12 security rules**:

| # | Rule | Severity | Pattern | Impact |
|---|------|----------|---------|--------|
| 1 | **Eval Usage** | Critical | `eval(` | ❌ Blocks publish |
| 2 | **Function Constructor** | Critical | `new Function(` | ❌ Blocks publish |
| 3 | **Child Process Execution** | High | `child_process`, `exec(`, `spawn(` | ❌ Blocks publish |
| 4 | **Environment Variable Access** | High | `process.env` without validation | ⚠️ Warning |
| 5 | **File System Operations** | High | `fs.writeFileSync`, `fs.unlinkSync` | ⚠️ Warning |
| 6 | **Hardcoded Credentials** | Critical | `password=`, `apiKey=`, `secret=` in code | ❌ Blocks publish |
| 7 | **SQL Injection Risk** | High | String concatenation in SQL queries | ❌ Blocks publish |
| 8 | **XSS Vulnerability** | High | `innerHTML=`, `dangerouslySetInnerHTML` | ⚠️ Warning |
| 9 | **Insecure Random** | Medium | `Math.random()` for security tokens | ℹ️ Info |
| 10 | **Unsafe Redirect** | High | `window.location=` with user input | ⚠️ Warning |
| 11 | **Prototype Pollution** | High | `__proto__`, `constructor.prototype` | ❌ Blocks publish |
| 12 | **Unsafe Deserialization** | Critical | `JSON.parse()` without validation | ⚠️ Warning |

### Severity Impact

- **Critical + High Severity**: **Blocks publishing** (exit code 1)
- **Medium Severity**: Warning (does not block)
- **Low Severity**: Informational only

### Allowed Patterns

Some operations are permitted if properly sandboxed:

- ✅ `process.env` access with schema validation (e.g., Zod)
- ✅ `fs` operations within plugin's designated storage path
- ✅ `JSON.parse()` with Zod schema validation
- ✅ `child_process` for official ObjectStack integrations (requires manual review)

## 🚀 Publishing Steps

### 1. Build Your Plugin

Compile TypeScript to JavaScript:

```bash
cd packages/my-plugin
pnpm build
```

This generates `dist/` with compiled `.js` and `.d.ts` files.

### 2. Validate Locally (Dry Run)

Test the publish workflow without actually uploading:

```bash
os marketplace publish --dry-run
```

This performs:
- ✅ Reads and validates `objectstack.json`
- ✅ Runs security scanner
- ✅ Calculates quality score
- ✅ Creates tarball (`.tar.gz`)
- ❌ Does **not** upload to Cloud

**Expected output:**

```
✓ Manifest validated: @vendor/my-plugin@1.0.0
✓ Security scan: 0 critical, 0 high, 1 medium
✓ Quality score: 85/100 (Grade B)
✓ Bundle created: my-plugin-1.0.0.tar.gz (245 KB)
✓ Dry run complete (use --publish to upload)
```

### 3. Authenticate with Cloud

Log in to ObjectStack Cloud:

```bash
os auth login
```

This opens a browser window for OAuth authentication. After login, a session token is stored locally (`~/.objectstack/credentials.json`).

### 4. Publish to Marketplace

Upload your plugin:

```bash
os marketplace publish
```

**Publishing workflow:**

```
1. Read objectstack.json
2. Run security scanner     → Critical/High vulnerabilities block publish
3. Calculate quality score  → Score < 40 blocks publish
4. Create tarball (.tar.gz)
5. Request publish URL      → POST /api/v1/marketplace/packages/publish
6. Upload tarball           → PUT {presignedUrl}
7. Confirm publication      → POST /api/v1/marketplace/packages/publish/confirm
8. Package available in marketplace ✅
```

**Example output:**

```
✓ Manifest validated: @hotcrm/crm@1.0.0
✓ Security scan passed: 0 critical, 0 high
✓ Quality score: 92/100 (Grade A) ⭐
✓ Bundle created: crm-1.0.0.tar.gz (1.2 MB)
✓ Uploading to ObjectStack Cloud...
✓ Package published successfully!

   📦 @hotcrm/crm@1.0.0
   🔗 https://cloud.objectstack.dev/marketplace/packages/@hotcrm/crm
   ⭐ Quality: A (92/100)
   📊 Category: app
```

### 5. Manage Published Packages

#### Unpublish a Version

Remove a specific version from the marketplace:

```bash
os marketplace yank @vendor/name@1.0.0
```

**Note**: Unpublishing does **not** affect users who have already installed the package. It only prevents new installations.

#### Update Package Metadata

To update description, category, or other metadata:

1. Edit `objectstack.json`
2. Increment `version` field (e.g., `1.0.0` → `1.0.1`)
3. Run `os marketplace publish`

Each publish creates a **new immutable version**. You cannot modify existing versions.

## 🔄 Publishing Flow Internals (Three-Phase Protocol)

Understanding the internal protocol helps debug publishing issues.

### Phase 1: Initiate Publish

**Client → Cloud**

```http
POST /api/v1/marketplace/packages/publish
Content-Type: application/json

{
  "name": "@vendor/my-plugin",
  "version": "1.0.0",
  "category": "app",
  "description": "My awesome plugin",
  "qualityScore": 85,
  "securityReport": {
    "critical": 0,
    "high": 0,
    "medium": 1
  }
}
```

**Cloud → Client**

```json
{
  "packageId": "pkg_abc123",
  "versionId": "ver_xyz789",
  "uploadUrl": "https://s3.amazonaws.com/objectstack-marketplace/uploads/...",
  "expiresAt": "2026-02-16T12:00:00Z"
}
```

The Cloud:
1. Validates session (requires authenticated vendor)
2. Creates or finds existing package record
3. Creates a new version record with `status: "pending"`
4. Generates a **presigned S3 upload URL** (15-minute expiration)
5. Returns upload URL to client

### Phase 2: Upload Bundle

**Client → S3**

```http
PUT https://s3.amazonaws.com/objectstack-marketplace/uploads/...
Content-Type: application/gzip
Content-Length: 1234567

<tarball binary data>
```

The client uploads the `.tar.gz` tarball directly to S3 using the presigned URL. No authentication required (URL contains temporary credentials).

### Phase 3: Confirm Publish

**Client → Cloud**

```http
POST /api/v1/marketplace/packages/publish/confirm
Content-Type: application/json

{
  "versionId": "ver_xyz789",
  "checksum": "sha256:abc123..."
}
```

**Cloud → Client**

```json
{
  "success": true,
  "package": {
    "name": "@vendor/my-plugin",
    "version": "1.0.0",
    "status": "published",
    "publishedAt": "2026-02-16T11:30:00Z"
  }
}
```

The Cloud:
1. Validates the version is in `pending` status
2. Verifies checksum matches uploaded file
3. Updates version status to `published`
4. Updates package `latestVersion` field
5. Triggers indexing for marketplace search

## ⚠️ Current Known Limitations

The ObjectStack Cloud marketplace is actively under development. The following limitations exist as of **February 16, 2026**:

### 🚧 Incomplete Features

| Feature | Status | Impact | Expected Completion |
|---------|--------|--------|---------------------|

| **Security Scanner Integration** | ⚠️ Code ready but not integrated | Scanner runs locally but not on Cloud | Cloud Phase 3 (Q1 2026) |
| **Quality Scoring Integration** | ⚠️ Code ready but not integrated | Scoring runs locally but not on Cloud | Cloud Phase 3 (Q1 2026) |
| **CLI npm Package** | ❌ Not published | Must build CLI from source | Cloud Phase 2 (Q1 2026) |
| **Runtime Plugin Loading** | ❌ Not implemented | Installed plugins not loaded at runtime | Cloud Phase 5 (Q3 2026) |

## 🎯 Best Practices

### Before Publishing

1. **Run Full Test Suite**:
   ```bash
   pnpm test
   pnpm typecheck
   ```

2. **Update Documentation**:
   - Write clear README with installation steps
   - Document all exported functions and types
   - Add code examples for common use cases
   - Update CHANGELOG with version changes

3. **Review Security**:
   - Avoid hardcoded credentials
   - Validate all user inputs
   - Use ObjectQL (not raw SQL)
   - Sanitize HTML output

4. **Optimize Bundle Size**:
   - Remove dev dependencies from production build
   - Use tree-shaking (ES modules)
   - Compress assets

### After Publishing

1. **Monitor Downloads**:
   - Check marketplace analytics
   - Review user feedback
   - Track error reports

2. **Maintain Regular Updates**:
   - Publish bug fixes promptly
   - Follow semantic versioning
   - Mark deprecated versions

3. **Engage with Community**:
   - Respond to issues
   - Accept pull requests
   - Provide migration guides for breaking changes

## 🆘 Troubleshooting

### "Quality score too low (X/100)"

**Cause**: Plugin does not meet minimum 40/100 threshold.

**Solution**:
1. Add test files (25 points)
2. Create README.md and CHANGELOG.md (25 points)
3. Add TypeScript declarations (20 points)
4. Fix security vulnerabilities (15 points)
5. Organize code in standard structure (15 points)

### "Security scan failed: critical vulnerabilities found"

**Cause**: Code contains patterns like `eval()`, `new Function()`, or hardcoded credentials.

**Solution**:
1. Run local security scan: `os marketplace scan .`
2. Review flagged lines
3. Replace with safe alternatives:
   - ❌ `eval(code)` → ✅ Use AST parser or domain-specific language
   - ❌ `apiKey = "sk_live_..."` → ✅ Use environment variables
   - ❌ String SQL → ✅ Use ObjectQL

### "Upload failed: presigned URL expired"

**Cause**: Upload took longer than 15 minutes.

**Solution**:
1. Optimize bundle size (remove unnecessary files)
2. Use faster internet connection
3. Request new upload URL: `os marketplace publish --retry`

### "Version already exists"

**Cause**: Version `1.0.0` was already published.

**Solution**:
1. Increment version in `objectstack.json`: `1.0.0` → `1.0.1`
2. Update `CHANGELOG.md` with changes
3. Run `os marketplace publish` again

**Note**: You cannot overwrite existing versions (immutability ensures users always get the same code for a given version).
