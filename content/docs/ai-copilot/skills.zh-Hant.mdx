# 技能

**技能**是平台助手可以執行的細分到點的 AI 能力——比如 *「判定此潛在客戶資格」* 或 *「撰寫客戶回覆」*。技能是 HotCRM 對助手的全部貢獻；它們按兩組編寫文件：[銷售技能](/zh-Hant/docs/ai-copilot/sales-copilot) 和 [服務技能](/zh-Hant/docs/ai-copilot/service-copilot)。

## 為什麼用技能，而非「一個大 AI」

把能力打包為技能（而不是一段大提示詞）使它：

- **可預測**——每項技能都有明確定義的輸入、輸出和行為。
- **可稽核**——管理員可以看到每項技能從哪裡讀取、向哪裡寫入。
- **可改進**——你可以優化某一項技能（例如更好的潛在客戶資格判定），而不觸及其他技能。
- **感知權限**——技能繼承使用者的記錄可見性。

## 內建技能

HotCRM 內建六項核心技能：

| 技能 | 使用者 | 它做什麼 |
| --- | --- | --- |
| **🔄 即時資料** | 銷售 + 服務 | 讀取即時結構和即時記錄——每一輪 |
| **🎯 潛在客戶資格判定** | 銷售 | 按 BANT 為潛在客戶評分，推薦下一步操作 |
| **✍️ 郵件撰寫** | 銷售 + 服務 | 撰寫感知上下文的郵件或回覆 |
| **📈 收入預測** | 銷售 | 按階段彙總管道並給出一個預測區間，點名有風險的交易 |
| **🔭 Customer 360°** | 銷售 + 服務 | 客戶或聯絡人的一頁式摘要 |
| **🚦 工單分流** | 服務 | 建議一個優先級，並給出判定它的那條理由 |

### 🔄 即時資料

| | |
| --- | --- |
| **輸入** | 任何關於 CRM 資料的自然語言問題（「哪些客戶……」、「給我展示排名前……」） |
| **讀取** | 提問那一刻的 **即時** 物件元資料（`describe_object`、`list_objects`）和 **即時** 記錄（`query_records`、`get_record`、`aggregate_data`）——無快取快照 |
| **輸出** | 帶引用記錄 ID 的直接答案 |
| **寫入** | 無——唯讀 |
| **知識庫** | 無——純粹是元資料 + 記錄 |

這是 **[Wow #1 — 即時結構](/zh-Hant/docs/ai-copilot/live-schema)** 背後的技能：在管理主控台中新增一個欄位，助手在下一輪就會使用它。其他每項銷售 / 服務技能都構建在即時資料之上，因此同樣的即時結構特性會傳遞地適用——潛在客戶資格判定可以根據 10 秒前新增的自訂欄位為潛在客戶評分。

### 🎯 潛在客戶資格判定

| | |
| --- | --- |
| **輸入** | 一條潛在客戶記錄——技能在任何 `crm_lead` 上啟用 |
| **讀取** | 潛在客戶本身（先 `describe_object` 讀 `crm_lead`，再 `get_record`）和它的相關活動歷史（`query_records`）。不讀行銷活動參與，也不讀匹配的客戶歷史：技能指令裡沒有這兩步 |
| **輸出** | 0–100 的 BANT 評分、每個維度一行理由（點名它讀到的欄位或活動），以及唯一一條建議的下一步，並引用潛在客戶 ID。它不返回熱門/溫熱/冷淡評級，也不返回建議狀態 |
| **寫入** | 它自己不寫——兩個結果都是它呼叫的真實動作。評分 ≥ 70 且你同意時呼叫 **轉化潛在客戶**（`action_convert_lead`），其流程建立客戶、聯絡人和可選的商機，並把潛在客戶標記為 `is_converted` / `status: converted`；否則呼叫 **安排跟進**（`action_schedule_followup`），其流程新建一條 `crm_task` 並回填潛在客戶的下次跟進日期。兩者都不會寫 `rating`——那是由人設定的 1–5 星 **潛在客戶評分** |
| **知識庫** | 無。沒有取知識的步驟——也不存在一個叫*銷售知識*的庫讓它去取（參見 [知識庫](/zh-Hant/docs/ai-copilot/knowledge-bases)） |

### ✍️ 郵件撰寫

| | |
| --- | --- |
| **輸入** | 一句目標，加上它所針對的記錄——指令把文案落在聯絡人上，並在請求點名時帶上相關的客戶或商機 |
| **讀取** | 聯絡人記錄（`get_record`），以及上面那條相關的客戶或商機；需要近期往來時用 `query_records` |
| **輸出** | 一份主題 + 正文的草稿——主題 60 字元以內、一個明確訴求、不超過 150 詞——外加第二個主題行備選，並說明兩個裡推薦哪一個 |
| **寫入** | 無，而且它也沒有途徑寫：聯絡人上的 **發送郵件** 沒有開啟 AI 曝光，因此執行時不會為這項技能產生任何發送工具。它只把草稿擺出來，並指向那個按鈕，由人在那裡審閱並發送 |
| **知識庫** | 無。起草指令裡沒有任何一步去取文章，而這裡曾點名的三個庫並不存在 |

### 📈 收入預測

| | |
| --- | --- |
| **輸入** | 一個關於管道健康度、預測、風險或交易滑期的問題 + 它涵蓋的週期（預設：本季度） |
| **讀取** | `crm_opportunity`——用 `describe_object` 拿到它當前的結構，用 `aggregate_data` 按階段統計數量與金額合計，用 `query_records` 撈出有風險的交易（預計成交日期已過、30 天以上沒有活動、階段停留過久）。指令裡沒有任何一步去讀欄位歷史；階段停留時長直接來自記錄自己的 **當前階段天數** |
| **輸出** | 按階段展開的管道及加權價值（金額 × 機率，由它自己從讀到的資料算出）、逐條點名的風險交易及其信號，以及一個以區間給出的預測——從僅承諾口徑（高機率階段）到完整加權管道——並在圖表更能說明問題時用 `visualize_data` 出圖。**已關閉 / 承諾 / 最佳情況 / 管道** 這幾個桶不是這項技能的輸出：它們是 `crm_opportunity` 的 **預測類別** 欄位，以及定時的銷售預測快照寫入 **銷售預測** 記錄的那幾個金額 |
| **寫入** | 無——唯讀 |
| **知識庫** | 無。方法論寫在這個技能自己的指令裡，不在任何庫中 |

### 🔭 Customer 360°

| | |
| --- | --- |
| **輸入** | 一個客戶或聯絡人 |
| **讀取** | `crm_account`，然後按這家客戶過濾讀取：`crm_contact`、未結的 `crm_case`（`is_closed` 為 false）、進行中的 `crm_opportunity`，以及已發布的 `crm_knowledge_article`；合計數來自 `aggregate_data`，而不是逐列加出來的。合約、近期活動和行銷活動成員資格**不在**它讀的範圍裡：技能帶著 `query_records`，夠得著 `crm_contract`、`crm_campaign`、`crm_event` 和 `crm_task`，只是指令從沒讓它去讀（與 [服務技能](/zh-Hant/docs/ai-copilot/service-copilot) 頁寫實的是同一件事） |
| **輸出** | 固定三段——**Account Snapshot**（客戶快照）· **Active Work**（進行中的工作）· **Risks & Notes**（風險與備註），這三個小標題在技能裡就是英文原文——並在行內引用記錄 ID 以便深連結。每條風險都要點名它的記錄和引出它的信號；某一段沒有記錄時如實說明為空。沒有合約段，也沒有參與度段 |
| **寫入** | 無——唯讀 |
| **知識庫** | 已發布的**知識文章**，按它剛讀到的工單的分類或標籤匹配——唯一會讀文章的技能 |

### 🚦 工單分流

| | |
| --- | --- |
| **輸入** | 一個工單——技能在 `crm_case` 上啟用 |
| **讀取** | 工單本身：先 `describe_object` 讀 `crm_case`，再 `get_record` 取當前這條工單，加上評判標準排在最前面的客戶上下文（**客戶分層**、合約金額）。它沒有宣告任何檢索類工具，因此過往工單夠不著；也沒有產品可讀：`crm_case` 上沒有任何名字的產品欄位，也沒有指向 `crm_product` 的 lookup |
| **輸出** | 一個優先順序（低 / 中 / 高 / 緊急）和驅動它的**那一條**理由，並引用工單 ID 與它讀到的欄位值；隨後給出指向 **升級工單**（附一段可直接貼上的 `reason`）或 **關閉工單**（附一段 `resolution` 摘要）的指引。沒有分類、沒有團隊、沒有文章清單；面向客戶的回覆交給 **郵件撰寫** |
| **寫入** | 無。它的工具只有 `describe_object` 和 `get_record`，而兩個會改動工單的動作——`escalate_case` / `close_case`——都沒有開啟 AI 曝光，因此執行時不會為它產生任何寫工具。這一行過去點名的 `category` 與 `queue`，在 `crm_case` 上根本不存在（以任何名字都不存在；工單自己的分類欄位是 **類型**：諮詢 / 故障 / 功能需求 / 缺陷，由人來選）。分流給出判斷，按鈕由坐席來點 |
| **知識庫** | 無。它沒有宣告任何檢索類工具，因此根本檢索不了文章 |

## 技能如何協同工作

技能之間不會互相呼叫。助手為你問的這個問題挑選合適的那一項技能，一個問題跑一項技能——不會有第二項技能被串接在它後面。

唯一寫進技能自身指令裡的移交是工單分流的那一條：面向客戶的回覆，它點名交給 *郵件撰寫*，而不是自己動筆。這條移交是給你的指引，所以把草稿作為下一個問題再問一次，那項技能就會接手。*工單分流* 不會呼叫 *Customer 360* 去判斷客戶是否高價值，*郵件撰寫* 也不會呼叫它去取客戶上下文——這兩次呼叫都不存在。當你需要分流或草稿背後的客戶歷史時，請自己去問 *Customer 360°*：它才是帶著 `query_records` 的那一項。

真正被所有技能共享的，是資料底座：每一項都透過同一套即時元資料與記錄工具去讀，因此即時資料的即時結構特性對它們全部成立。

## 每項技能都遵循什麼

- **共享規則**——為使用者 X 執行的技能只能讀取對 X 可見的記錄。
- **欄位級安全**——受限欄位會從技能輸入中隱藏。
- **稽核日誌**——每次技能呼叫，連同輸入和輸出，都會記錄以供審查。
- **確認**——潛在客戶資格判定是唯一有寫入路徑的技能，而且它寫的是真實動作而非欄位：**轉化潛在客戶** 不可逆，因此會要求確認，由 AI 發起的轉化會等待人工簽核而不是無人值守地跑完；**安排跟進** 是增量且可撤回的，因此沒有簽核閘門。其餘五項技能都沒有宣告任何寫工具。

## 新增你自己的技能

管理員和開發者可以構建自訂技能——例如：

- 為即將到期的合約 *生成續約推介*。
- *評估客戶健康度*，綜合使用情況、NPS 和工單量。
- 當某個產品達到里程碑時 *撰寫一封發布說明郵件*。

參見 [自訂 › AI 技能](/zh-Hant/docs/customization/ai-skills)，了解如何定義一項新技能、它可以使用哪些知識庫，以及如何測試它。

## 給管理員的提示

- ✅ 在 AI 儀表板中 **監控技能使用情況**——哪些技能使用最多，哪些接受率低。
- ✅ 為表現不佳的技能 **調優知識庫**——大多數準確性問題都是知識問題。
- ✅ **禁用** 不適合你業務的技能——每項技能都可以在管理設定中切換開關。
