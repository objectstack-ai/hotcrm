# 工單

**工單**是一張客戶支援單據。每個客戶報告的問題、疑問或功能請求都以工單的形式存在，以便團隊能夠一致地路由、處理和解決它。

## 7 種工單狀態

| 狀態 | 含義 |
| --- | --- |
| ⚪ **New** | 剛收到，尚未分配給客服 *(預設)* |
| 🟠 **In Progress** | 客服正在積極處理 |
| 🟡 **Waiting on Customer** | 等待客戶回覆 |
| 🔵 **Waiting on Support** | 等待另一團隊（工程、財務等） |
| 🔴 **Escalated** | 上交給資深客服或管理層 |
| 🟢 **Resolved** | 修復已交付，等待客戶確認 |
| 🟢 **Closed** | 工單已完成 |

一個典型的快速解決工單：**New → In Progress → Resolved → Closed**。
一個典型的卡住工單：**New → In Progress → Waiting on Customer → In Progress → Resolved → Closed**。

## 4 個優先順序級別

| 優先順序 | 典型 SLA 目標 | 使用場景 |
| --- | --- | --- |
| 🔵 **Low** | 7 個工作日 | 外觀問題、低影響的疑問 *(預設)* |
| 🟠 **Medium** | 2 個工作日 | 標準問題，工作繼續 |
| 🔴 **High** | 8 小時 | 影響顯著，客戶不滿 |
| 🔴 **Critical** | 4 小時 | 生產中斷，需要立即回應 |

**四行裡只有 Critical 那行背後真有一隻時鐘。** `case_sla_defaults` 鉤子只給 Critical 工單標記 `sla_due_date`，別的一律不標，所以另外三個目標是團隊的服務承諾，應用裡沒有任何東西去度量它們 —— 機制詳見 [SLA 與升級](/zh-Hant/docs/service/sla-and-escalation)。

當工單被設為 **Critical** 時，工單升級流程透過站內訊息 + 郵件提醒**工單負責人**——它的收件人列表只有 `{caseRecord.owner_id}` 這一項，本應用中不存在 `support_manager@example.com` 這個收件人。**High** 工單永遠不會被自動升級，無論帳戶是什麼：沒有任何升級條件會讀取帳戶，要升級它靠的是手動的 **Escalate Case** 按鈕。

## 工單類型

| 類型 | 用於 |
| --- | --- |
| **Question** | 操作類諮詢 |
| **Problem** | 某項功能無法使用 |
| **Feature Request** | 客戶請求新功能 |
| **Bug** | 已確認的軟體缺陷 |

## 工單來源

工單的來源：**Email · Phone · Web · Chat · Social Media**。

這驅動報表（哪些渠道產生的工單量最大），並在工單從來訪渠道建立時自動填充（例如，郵件轉工單整合會將來源設為 Email）。

## 工單記錄儲存的內容

詳情介面分為 6 個區塊：

| 區塊 | 欄位 |
| --- | --- |
| **Case Information** | 工單編號、主題、描述、帳戶、聯絡人 |
| **Origin & Routing** | 來源、所有者、父工單 |
| **SLA & Priority** | 狀態、優先順序、類型、首次回應時間、SLA 截止日期、SLA Violated |
| **Resolution** | 關閉日期、解決方案、客戶簽名 |
| **Escalation** *(預設折疊)* | 升級標記、升級日期、升級原因 |
| **System** *(預設折疊)* | 審計追蹤、時間戳 |

## 自動發生的事

- **首次回應日期**（`first_response_date`）——在工單上記錄一次**已經發生過**的通話或會議時才打戳，而且只打第一次。它唯一的寫入方是 `logActivityAction`（`src/actions/global.actions.ts`），只在 `held` 這兩種活動上打戳——**Log a Call** 與 **Log a Meeting**——並且寫之前先把庫裡存著的值讀回來，所以第二次記錄不會覆蓋第一次。別的動作都不打這個戳：評論進的是動態流，郵件進的是 `sys_email`，狀態變更是被刻意排除的（客服可以把工單轉到 *In Progress* 然後自己查一小時，客戶什麼都沒聽到），僅僅**預約**了一場會議也不算回應。所以一張全程靠評論和郵件處理的工單，這個欄位始終是空的。
- **關閉標記**——狀態變為 *Closed* 時自動設定。
- **關閉日期**——狀態變為 *Closed* 時標記為 NOW。
- **解決時間（小時）**——按 *Created date* 與 *Closed date* 之間的差值計算。
- **SLA 截止日期**——只給 **Critical** 工單標記。工單在建單時被設為 Critical、或後來被改為 Critical，且該欄位仍為空時，`case_sla_defaults` 把它填成 *目前時間 + 4 小時*。High、Medium、Low 一個位元組都不寫，欄位就停在空值，除非有人手工填一個日期進去。
- **SLA Violated**（`is_sla_violated`）——不存在名為 *SLA Breached?* 的欄位。每小時一次的 `case_sla_monitor` 掃描把它置真，選中的是**仍未結**（狀態既不是 *Resolved* 也不是 *Closed*）且 **SLA 截止日期** 已經過去的工單。它從不拿解決時間去比對目標，所以沒有截止日期的工單永遠不是候選，晚解決但趕在下一次掃描前解決的工單也永遠不會被標記。
- **帳戶的最後活動日期**——工單更新時刷新為今天。

## 內建規則

- **已關閉工單必須有解決方案**——解決方案欄位為空時無法關閉工單。
- **升級工單必須有升級原因**——解釋為何引入了資深客服。
- **狀態推進是建議，不是閘門**——轉換表寫的是 *New* 之後可以去 *In Progress*、*Waiting on Customer*、*Escalated* 或 *Closed*，所以直接跳到 *Resolved* 是走出了這張表。但這攔不下儲存：工單照樣以 *Resolved* 落庫，引擎只在伺服器日誌裡寫一行 `WARN Validation rule 'case_status_progression' (warning): Invalid status transition`。與上面兩條不同——那兩條是 `error` 級、確實會拒絕儲存——這一條只做提示。轉換表到底有什麼用，見[狀態機](/zh-Hant/docs/administration/state-machines)。

## 流程與物件鉤子自動化

- **緊急時通知**——當優先順序被設為 Critical 時，工單升級流程的 `notify` 節點發出站內訊息 + 郵件，只發給**工單負責人一人**：收件人列表只有 `{caseRecord.owner_id}` 這一項。本應用中不存在 `support_manager@example.com` 這個收件人。
- **升級時通知**——當狀態變更為 *Escalated* 時，不會發出任何郵件：`escalation_team@example.com` 在本應用中根本不存在，也不存在「升級團隊」這樣一個收件目標。狀態轉為已升級真正觸發的是 `case_status_side_effects` 鉤子，它開出的是一條**次日到期、優先順序為緊急、歸帳戶負責人的跟進任務**——且僅限有關聯帳戶的工單，因為該任務是掛在那個帳戶上的。
- **計算解決時間**——關閉時自動進行。
- **自動設定關閉日期和標記**——狀態變更時。

## 工單升級

[工單升級流程](/zh-Hant/docs/service/sla-and-escalation)只在一個條件下執行：**工單處於 Critical 優先順序**。不存在 High 優先順序這一分支，也沒有任何升級條件會讀取帳戶——Customer 的 High 工單與潛在客戶的 High 工單待遇完全相同：兩者都不會自行升級，要升級它靠的是手動的 **Escalate Case** 按鈕。

它會執行：

1. **標記**為已升級，標記升級日期。
2. **設定狀態**為 *Escalated*。
3. **通知工單負責人**——透過站內訊息與郵件送達，帶上工單編號和優先順序。

狀態轉為 *Escalated* 隨後會觸發 `case_status_side_effects` 鉤子，由它開出一條**次日到期、優先順序為緊急、歸帳戶負責人的跟進任務**——且僅限有關聯帳戶的工單，因為該任務是掛在那個帳戶上的。

以下三件事這份清單刻意不寫，因為升級並不做：

- **工單不會被重新指派。** 升級寫入的是 `is_escalated`、`escalation_reason`、`escalated_date` 和 `status`，從不碰 `owner_id`。不存在向客服的經理或資深員工的交接——升級通知的正文自己就是這麼寫的：`It remains assigned to you.`（工單仍指派給你）。
- **通知只發給工單負責人一人。** 收件人列表只有 `{caseRecord.owner_id}` 這一項——不含其經理，也不含更廣泛的 `support-team@example.com` 列表，這個地址在本應用中根本不存在。
- **跟進任務不落在原客服身上。** 它歸**帳戶負責人**所有，既不歸正在處理該工單的客服，也不歸某位資深客服。流程裡根本沒有任務節點——跟進任務由鉤子獨家建立，因此每次升級恰好一條。

完整機制參見 [SLA 與升級](/zh-Hant/docs/service/sla-and-escalation)。

## 共享——誰可以看到哪個工單

- 預設情況下，工單是**私有的**——只有所有者和角色層級中的上級經理可見。
- **緊急未結工單**會自動共享（讀/寫）給所有服務經理及其下屬。緊急問題會獲得全團隊可見性。

## 欄位級安全

- **SLA Violated**（`is_sla_violated`）和**解決時間**對客服是**唯讀的**——這些是自動計算的，無法手動篡改。鎖是欄位級安全給的：Service Agent 設定檔把這兩個欄位遮罩為可讀不可編輯。

## 標準列表檢視

`crm_case` 一共發布 **7 個**檢視（`src/views/case.view.ts`），工單列表把它們做成頁籤：

| 檢視 | 展示什麼 | 頁籤 |
| --- | --- | --- |
| **All Cases** | 全部工單，先按優先順序、再按 SLA 截止日期排序，列底色鍵在**優先順序**上 | *All* |
| **Service Workflow** | 未結工單的看板，按狀態分欄 | *Workflow* |
| **SLA Calendar** | 按 **SLA 截止日期** 把工單鋪在行事曆上——實際上就是那些 Critical 工單，外加手工填過日期的 | *SLA* |
| **Case Timeline** | 工單按「建立 → 關閉」鋪在時間軸上，按負責人分組 | *Timeline* |
| **Escalated Cases** | `is_escalated` 為真 | *Escalated* |
| **⏰ SLA at Risk** | 未結的 **High 與 Critical** 工單，截止日期最近的排在前面 | *SLA at Risk* |
| **My Open Cases** | 你名下尚未關閉的工單 | *My Cases* |

本節原先列的七個名字裡，有六個根本不是檢視：

- **Critical Cases** 與 **Breached SLA** 是指標磁磚，不是列表。[服務概覽](/zh-Hant/docs/analytics/dashboards)（Service Overview；該儀表板自身的標題是 **Customer Service**）上有 *Critical Cases*（未結且 Critical）和 **SLA Violations**（`is_sla_violated` 為真）兩個磁磚；本應用裡沒有任何一個列表檢視按違約過濾。真要有一份能逐條處理的清單，用 **Escalated Cases**——SLA 掃描會把它標記的每一條都升級，所以每次違約都會落到那裡。
- **Service Board** 不是本應用裡任何東西的名字。看板叫 **Service Workflow**，在 *Workflow* 頁籤上。
- **Cases Due Today**、**Recently Closed** 與 **By Account** 以任何形式都不存在：沒有任何檢視按「截止日期 = 今天」或 `closed_date` 過濾，`crm_case` 上也沒有任何分組檢視。

## 工單詳情佈局

打開一個工單時，你會看到：

- **頁首**——標題是工單編號與主題（`{case_number} · {subject}`），副標題是**帳戶**，此外只有一個圖示、麵包屑和幾個動作按鈕。頁首就這些：上面**沒有狀態徽章、沒有優先順序徽章，也沒有 SLA 倒數計時**。本應用裡沒有任何東西會計算剩餘時間或超時時長——頁首上沒有，工單上別的任何地方也沒有——所以根本沒有倒數計時可渲染。那兩個 SLA 欄位實際做什麼，見 [SLA 與升級](/zh-Hant/docs/service/sla-and-escalation)。
- **關鍵資訊**——緊貼頁首下方的摘要欄，也是**狀態**與**優先順序**真正待的地方：它們在這裡是普通欄位而不是徽章，與 **SLA 截止日期**、**SLA Violated**、**負責人**、**帳戶**並排。
- **狀態路徑**——一個 Salesforce 風格的水平流程，顯示 New → In Progress → Waiting on Customer → Escalated → Resolved → Closed，讓客服一眼就能看出工單的進展和下一站。
- **客戶面板**——不存在這樣一個面板。這一頁（`src/pages/case_detail.page.ts`）只宣告了兩個區域，再無其他：一個頁首區域裝著上面那三個元件，一個主區域裝著下面那組頁籤。客戶脈絡就散落在這兩處：**帳戶**在頁面上出現了三次——頁首副標題、關鍵資訊摘要欄，以及 *Details* 頁籤裡的一個欄位；**主要聯絡人**則是同一頁籤 *Case Information* 分區裡的一個欄位。**合約等級**與**本月未結工單**在工單的任何介面上都沒有承載：工單不關聯任何合約，`crm_contract` 上也沒有等級欄位；最接近的真實欄位是帳戶記錄上的 **Customer Tier**（中文介面作「客戶分層」），而這一頁並不展示它。本應用裡也沒有任何東西按月統計一個客戶的工單數。
- **三個標籤頁：**
  - **Details**——完整的工單描述和解決方案、所有元資料欄位。
  - **Related**——只有一個列表，不是四個：**Open Tasks**——透過**關聯工單**（`related_to_case`）指向本工單的 `crm_task` 記錄，過濾掉狀態為 *Completed* 的，一次最多十筆。整個頁籤就這些。沒有附件列表：工單是可以掛附件的（物件上開了這項能力），但這一頁沒有任何元件把它們列出來。沒有關聯商機列表，因為 `crm_case` 與商機之間雙向都不存在任何關係欄位。也沒有里程碑列表——工單的三個里程碑（*escalated*、*resolved*、*closed*）是以條目形式發到 **Activity** 時間線上的，不是在這裡當記錄列出來。
  - **Activity**——統一的時間線（下文詳述）。
- **AI 參考欄**——這一頁上不存在任何形式的參考欄。主區域裡除了那組頁籤什麼都沒有，頁面上也沒有任何一個元件是 AI 驅動的。服務技能本身是真實存在的——見下文《AI Copilot 如何提供幫助》一節——但你是靠提問去用它們，而不是靠工單旁邊的一塊面板。本應用裡唯一真正渲染出來的參考欄在商機詳情頁上，而且即便在那裡，它列的也是關聯記錄（報價、產品、未完成任務），不是什麼建議。

### 活動時間線

Activity 標籤頁是工單上發生過什麼的唯一可信來源。它將四個資料流合併為一個按時間排序的資訊流：

| 資料流 | 來自哪裡 | 你會看到什麼 |
|--------|---------------------|------------------|
| **評論** | 隊友或客戶在工單上發布 | 主題式討論、@提及、內部/外部可見性 |
| **已記錄通話** | "Log a Call" 操作——儲存為類型為 *completed* 的 `sys_activity` | 通話主題、時長、結果、記錄人 |
| **外發郵件** | "Send Email" 操作——透過 `sys_email` 排隊 | 主題、收件人、投遞狀態（queued / sent / bounced） |
| **欄位變更** | 工單上每個被追蹤欄位的每次變更 | 改了什麼、誰改的、何時、變更前 → 變更後 |

你無需配置任何這些內容——每個 CRM 物件都自帶 `trackHistory: true`，平台的 feeds 引擎會自動將評論、活動和審計日誌接入同一時間線。

> 提示——如果你只想看討論，使用 Activity 標籤頁頂部的篩選下拉選單；你也可以從那裡訂閱該工單，這樣任何未來的發布都會在鈴鐺中提醒你。

## AI Copilot 如何提供幫助

[服務技能](/zh-Hant/docs/ai-copilot/service-copilot) 會在任何工單上自動啟動。你可以問：

- *"分流這個工單"*——工單分流技能根據主題和描述推薦優先順序。
- *"建議一個解決方案"*——沒有哪個技能能端到端做完這件事。**工單分流**只宣告了 `describe_object` 與 `get_record` 兩個工具，完全沒有檢索類工具，因此它什麼都不檢索。請向 **Customer 360°** 要按工單分類或標籤匹配出來的已發布[知識文章](/zh-Hant/docs/service/knowledge-base)，再向**郵件撰寫**要客戶回覆——草稿的依據是聯絡人與帳戶記錄，而不是那些文章，需要援引哪一篇請自己貼進去。
- *"Customer 360"*——拉取完整的帳戶上下文（未結商機、過往工單、合約等級）。

如果 Copilot 判斷優先順序為 *Critical*，它還會建議立即升級並起草內部通知訊息。

## 給服務客服的提示

- ✅ **及時分流來訪工單**——但要知道，應用裡沒有任何東西在盯著這件事。不存在可供違反的首次回應目標：**First Response Date** 只是記錄在工單上，從不與任何東西比對，`case_metrics` 裡沒有首次回應這個度量，所以沒有任何報表或儀表板磁磚報它，也沒有任何流程為它告警。這裡的「及時」是團隊自己的承諾，不是應用跑著的一隻時鐘。
- ✅ **當你確實被阻塞時使用 "Waiting on Customer"**——但它**不會停止 SLA 計時**，任何設定下都不會。`sla_due_date` 只寫一次，從不重算；每小時的 `case_sla_monitor` 掃描收的是狀態既不是 *Resolved* 也不是 *Closed* 的未結工單，而 *Waiting on Customer* 不在這份排除名單上。一張掛在客戶那邊的 Critical 工單照樣把四小時走完，照樣被標記 **SLA Violated** 並按時升級。
- ✅ **始終寫下解決方案**——這是強制的，但也會為未來的工單提供知識庫素材。
- ✅ **關聯一個任務**——當工單需要未來跟進時（例如"7 天後驗證修復是否有效"）。
- ❌ 不要在未確認修復有效之前關閉工單。

## 給服務經理的提示

- ✅ 沒有 **Breached SLA** 這個檢視可看，也沒有什麼紅色徽章——工單列表上唯一的顏色規則是 *All Cases* 的列底色，它鍵在**優先順序**上，不是違約。每天改看 **Escalated Cases**，數量則看服務概覽上的 **SLA Violations** 磁磚。
- ✅ 用看板開每日站會——它叫 **Service Workflow**，在工單列表的 *Workflow* 頁籤上。
- ✅ 輔導那些 **Resolution Time** 趨勢上升的客服——但這個趨勢只能從工單本身讀出來。不存在什麼客服排行榜：`case_metrics` 這個資料集（服務側每一張報表和每一個儀表板部件都建在它上面）只宣告了 Status、Priority、Origin、Type、Created 五個維度，所以分析層裡沒有任何東西能按客服分組。

## 給管理員的提示

- 每個優先順序的 SLA 目標儲存在工單物件的自動化中。要更改它們，請編輯工單自動化——參見 [管理 › 自動化](/zh-Hant/docs/administration/automation)。
- `escalation_team@example.com` 和 `support_manager@example.com` 都沒有在任何地方設定過——這兩個地址在本應用中根本不存在。真實存在的收件人列表只有一處：工單升級流程 `notify` 節點的 `recipients: ['{caseRecord.owner_id}']`，即工單負責人一人；它在 `src/flows/case-escalation.flow.ts` 裡改，不是 Setup 介面上的設定項。
- 郵件轉工單接入（從來訪郵件自動建立工單）需要郵件外掛——參見 [定制 › 擴展物件](/zh-Hant/docs/customization/extending-objects)。
