# 沙箱與發布管理

切勿直接在生產中進行設定變更。本頁介紹安全的工作流：在沙箱中建構、測試、打包、提升到生產，必要時回滾。

**下文點名的這些畫面，一個也不存在。** Setup 裡沒有 *Sandbox Management*，沒有 *Change Packages*，也沒有 *Git Sync* 入口 —— 它的導覽是 Overview、Apps、People & Organization、Access Control、Approvals、Configuration、Diagnostics、Integrations、Advanced，而這些分組底下沒有任何東西能開出一個租戶或攢出一個變更集。下面寫的是發布管理*應有*的形態，之所以保留，是因為它講的紀律是對的。HotCRM 今天真正的做法是：它的中繼資料就是 `src/` 下的 TypeScript，在 git 裡審查，隨應用一起發布；已安裝的套件列在 **Setup → Packages**。（平台未附繁體中文語言包，主控台介面顯示英文，因此本頁的導覽路徑一律以英文標示。）

## 什麼是沙箱？

**沙箱** 是你的生產 HotCRM 租戶的全保真副本 —— 相同的模式，可選地包含相同的資料 —— 在隔離環境中執行。你可以毫無後果地把它弄壞。

| 沙箱類型 | 其中包含什麼 | 重新整理頻率 |
| --- | --- | --- |
| **僅設定** | 僅模式 + 中繼資料，無記錄 | 按需 |
| **部分資料** | 模式 + 一小部分記錄樣本 | 每週 |
| **完整副本** | 模式 + 所有生產資料（已匿名化） | 每月 |

企業版套餐通常包含 **3 個沙箱**；可按需新增更多。

## 建立與重新整理沙箱

設計意圖是這樣的：有一個*沙箱管理*畫面，在那裡選擇**類型**（設定 / 部分 / 完整）、命名（`dev`、`uat`、`training`）並點擊**建立**；每一行上還有一個**重新整理**，把最新的生產資料重新拉下來 —— 同時清掉沙箱裡原有的一切。

並沒有這樣一個畫面。開出一個環境是 ObjectStack Cloud 控制面的事，不是本租戶設定裡的某一頁；設定裡唯一與雲相關的入口是 **Setup → Cloud Connection**。

### 重新整理時的匿名化

對於完整副本沙箱，PII 可以在重新整理時匿名化：

- 電子郵件地址 → `user-{id}@example-anon.test`
- 電話號碼 → 隨機化但保留格式
- 姓名 → 看起來真實的假名
- 自由文字欄位 → 保持原樣（注意 —— 請審查敏感內容）

推薦用於由合作夥伴 / 外包人員存取的沙箱。

## 變更工作流

```
┌───────────┐   build    ┌─────────┐   test    ┌─────────┐   promote   ┌────────────┐
│ Developer ├──────────▶│   dev   ├──────────▶│   uat   ├────────────▶│ production │
└───────────┘            └─────────┘           └─────────┘             └────────────┘
                                                                              │
                                                                       rollback│
                                                                              ▼
                                                                       last working
                                                                          package
```

1. 在 `dev` 沙箱中 **建構** 變更。
2. **提升** 到 `uat` —— 業務使用者在那裡測試。
3. 需要 **UAT 簽核** 才能繼續。
4. 在變更視窗期間 **提升** 到 `production`。
5. 在生產中立即進行 **冒煙測試**。
6. 必要時 **回滾**。

## 變更包

**變更包** 將一組中繼資料變更（物件、欄位、驗證、流程、共用規則等）捕獲為單個可部署的成品。

### 建立包

設計意圖是這樣的：一個*變更包 → 新增*的畫面，填名稱與描述，用手動 / 按標籤 / 自上次打包以來自動這三種方式加入元件，再**驗證**一致性並**儲存**。

並沒有這樣一個畫面。這裡的「包」是平台自己的單位 —— 列在 **Setup → Packages** 和 **Studio → Packages** —— 而 HotCRM 自己的中繼資料是在建構時從原始碼打包的，從不在介面裡拼裝。

### 部署包

1. 從源沙箱 → **部署 → 選擇目標租戶**。
2. **試執行** —— 將會變更什麼、將會建立什麼、存在什麼衝突。
3. 審查變更集。
4. **部署** —— 僅設定變更通常 &lt;2 分鐘。
5. **稽核日誌** 捕獲誰在何時部署了什麼。

### 哪些可以打包

| 類型 | 可打包 |
| --- | --- |
| 物件、欄位、驗證 | ✅ |
| 流程 | ✅ |
| 共用規則、權限設定檔、權限集 | ✅ |
| 頁面、清單檢視、儀表板 | ✅ |
| 報表、dataset | ✅ |
| AI 技能、知識庫設定 | ✅ |
| 審批流程 | ✅ |
| 電子郵件範本 | ✅ |
| **資料記錄** | ❌（使用資料匯入） |
| **檔案** | ❌（使用檔案同步 API） |
| **使用者帳戶** | ❌（使用 SCIM） |

## 版本控制（基於 git）

沒有 *Git 同步* 這個入口可連 —— 而對 HotCRM 來說，它也無事可做。中繼資料**本身**就是 git 儲存庫：每一個物件、欄位、驗證、流程、檢視和共用規則都是 `src/` 下的 TypeScript。所以一個同步頁面本該解鎖的東西，本來就是這個應用的建構方式：

- 透過 PR 進行 **程式碼審查**。
- 分支之間的 **差異對比**。
- 每次變更的 **歷史**。
- 在合併前執行 `pnpm typecheck` 等的 **CI**。

把團隊指向儲存庫，而不是設定頁。

## 回滾

兩種形式：

### 快速回滾（24 小時內）

設計意圖是這樣的：每次部署都留下一個**還原點**，再由一份*部署歷史*清單讓你在 24 小時內回滾某一次 —— 還原中繼資料，同時保留部署之後新建的記錄。

並沒有任何部署歷史被記錄下來，也沒有回滾按鈕。回滾的做法是把上一個版本的應用重新部署一次 —— 從產出當前版本的同一份原始碼。

### 重新部署之前的包

如果已經過去 >24 小時，請重新部署 **上一個成功的包**。同樣的 UI，只需選擇較舊的包版本。

⚠️ 如果你回滾模式變更，針對新模式建立的資料可能需要遷移。請始終先在 UAT 中測試回滾。

## 生產變更視窗

最佳實踐：

- **非高峰視窗**（通常是週末或週五晚 7 點）用於非簡單部署。
- 在重大業務事件前設置 **凍結期**（季度末、大型發布）。
- 在公司 #cm-announcements 頻道 **公告**。
- 任何生產部署都要有 **2 名管理員** 在場（四眼原則）。
- 部署後立即執行 **冒煙測試清單**。

## 冒煙測試清單

每次生產部署後：

- [ ] 以測試使用者身份登入。
- [ ] 建立潛在客戶 → 轉化 → 商機 → 報價 → 合約。
- [ ] 建立案例 → 分診 → 解決。
- [ ] 執行主頁儀表板 —— 所有圖塊載入。
- [ ] 透過已連接的收件匣傳送一封測試郵件。
- [ ] 在真實記錄上呼叫一個 Copilot 技能。
- [ ] 抽查變更的元件。

## 監控與提醒

- 每次提升時向 Slack/Teams 傳送 **部署提醒**。
- **錯誤激增** 偵測 —— 如果部署後錯誤激增，自動建議回滾。
- **效能回歸** 偵測 —— 如果 p95 延遲下降 >20%，發出提醒。

## 提示

- ✅ **始終** 在 `dev` 中建構、在 `uat` 中測試、部署到 `prod`。切勿跳過 uat。
- ✅ **小而頻繁** 的包勝過大型的季度發布。
- ✅ **為包清晰命名** —— `2026-Q1-pipeline-revamp` 而非 `Package 47`。
- ✅ 按舉措為元件 **打標籤** —— 讓打包變得輕而易舉。
- ✅ 一旦有 >2 名管理員進行變更，就盡快 **連接到 git**。
- ✅ 每月 **重新整理沙箱** —— 陳舊的沙箱會給人虛假的信心。
- ✅ 每季度 **演練回滾** —— 切勿在真實事故中第一次使用它。
