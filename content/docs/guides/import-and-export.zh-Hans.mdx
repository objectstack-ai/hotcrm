# 导入与导出

如何把数据**导入** HotCRM，以及如何**导出**。下文全部按应用当前实际的样子书写；标注 *（尚未落地）* 的小节保留的是设计意图——请把它们当作需求文档来读，而不是操作步骤。

> **不存在「设置 → 数据」菜单。** Setup 应用的分组是 *概览*、*应用*、*人员与组织*、*访问控制*、*审批*、*配置*、*诊断*、*集成* 和 *高级*。既没有 **数据** 分组，也没有 **隐私** 分组。本页较早的版本几乎把每一个步骤都指向 `设置 → 数据 → …`，而照着走的人去找的是并不存在的界面。导入与导出都在**对象自己的列表视图**上；其余的部分是数据 API。

## 从 CSV / Excel 导入

两条路，都是真的，而且落到同一个地方：

- **在应用里**——打开对象的列表视图，点工具栏的**导入**。适合那种你想先亲眼过一遍再写入的一次性文件。
- **通过 API**——导入端点，带试运行、后台作业与撤销。分步说明见[导入你自己的数据](/zh-Hans/docs/guides/importing-your-data)。

两条路共用服务端同一条导入通路，因此映射、校验与逐行错误码都是同一套。

### 应用内的导入向导

1. **打开该对象的列表视图**，点**导入**。目标对象由你从哪里进来决定——向导不会让你再选一次。
2. **上传**——把 CSV 或 Excel 文件拖进去，或者直接从电子表格里粘贴。**下载模板** 会给你一个带该对象各列的 CSV，必填列标着 `*`。
3. **映射**——各列按表头名自动匹配到字段，每条匹配都带一个置信度读数；其余的由你手工纠正或跳过。如果 HotCRM 为该对象随附了**已保存的映射**，就直接选它：重命名、值转换与类型强制转换随后都在服务端执行，列映射变为只读。今天随附三个——`crm_account_import`、`crm_contact_import` 与 `crm_lead_import`——和 API 那条路点名的是同样三个。
4. **导入选项**——*当某行匹配到已有记录时* 提供 **总是新建**、**更新已有（无匹配则跳过）** 与 **匹配则更新，否则新建**，并由 **匹配依据** 决定按哪个（哪些）字段去匹配。已保存的映射会自带默认写入模式与匹配键，所以在上面那三个对象上你几乎不需要动它。
5. **校验数据**——把每一行拿到服务端核对一遍，不写入任何东西。每次导入前都做。
6. **预览 → 导入**——大文件会交给后台作业，并显示 `正在导入 n / m 行`。**历史** 列出该对象最近的导入作业，并提供**撤销导入**：作业创建的记录会被删除，它更新过的记录会恢复到之前的值。

> **导入完成时不会有邮件送达。** 作业运行时进度显示在屏幕上，跑完后这次运行列在**历史**里——通知就到此为止。HotCRM 不发送任何完成邮件，而平台的邮件服务只有出站方向，且在部署配置传输方式之前根本什么都不投递。

单个作业最多 **50,000 行**；更大的文件请拆分。撤销的上限更紧，另外还有几个前提条件——见[导入你自己的数据](/zh-Hans/docs/guides/importing-your-data)。

### 字段映射提示

- **所有者**——填用户的邮件地址，它会去解析到用户记录。匹配不到任何用户的地址会让**该行失败**，错误码 `reference_not_found`；系统不做任何猜测。把单元格留空，则记录归运行导入的人所有。
- **查找字段**——填被引用记录的 id，或者那个对象用来标识自己的文本（其显示字段，其次是 `name` / `title` / `label` / `full_name` / `email` / `username`）。父记录即使排在同一个文件的后面，也仍然能解析到。
- **选项列表**——按字段选项的标签*和*值做匹配，不区分大小写，所以 *Technology* 和 *technology* 都能落地。随附的映射还额外翻译其他系统导出时使用的词汇——*SaaS*、*Trade Show*、*Client*。仍然认不出来的值会让该行以 `invalid_option` 失败，而不是被悄悄丢掉。
- **日期**——`YYYY-MM-DD` 最稳妥。
- **数字**——纯数字（`1500000`，不是 `1.5M`）。
- **地址**——联系人有真实的通讯地址列；客户和潜在客户把地址存为一个结构化字段，无法由分散的表格列拼装出来。已知限制列在[导入你自己的数据](/zh-Hans/docs/guides/importing-your-data)。

### 匹配键——而不是外部 ID

本页较早的版本让你加一个 `external_id` 列并把它标记为匹配键。**HotCRM 的对象没有任何一个带 `external_id` 字段**，而具名映射是严格投影——它没有声明的每一列都会在写入前被丢弃——所以那一列只会被忽略。

它承诺的幂等性是真的，只不过来自业务键：

| 映射 | 与已有记录的匹配依据 |
| --- | --- |
| `crm_account_import` | 客户名称 |
| `crm_contact_import` | 邮件地址 |
| `crm_lead_import` | 邮件地址 |

重新运行同一个文件，匹配上的行会被更新而不是重复创建。在向导里，**匹配依据** 就是同一个想法的手工版。跨对象引用也是同样的机制：联系人用*客户名称*指向它的客户，而不是某个遗留 id。

不过客户名称是**逐字**匹配的——*Acme Corp* 和 *ACME Corp* 是两个不同的客户。

## 从 Salesforce 迁移（尚未落地）

设计意图是这样的：随箱提供一个专门构建的迁移向导。你通过 OAuth 授权到自己的 Salesforce 沙盒或生产环境，向导自动把 Salesforce 对象映射到 HotCRM 的对应项，你审阅字段、选项列表与所有者映射，选择数据切片（全部历史，或用于分阶段切换的一个日期范围），试运行，然后提交——并保留 Salesforce 的记录 id 以便追溯。

| Salesforce | HotCRM 对应项（设计意图） |
| --- | --- |
| Account | `crm_account` |
| Contact | `crm_contact` |
| Lead | `crm_lead` |
| Opportunity | `crm_opportunity` |
| OpportunityLineItem | `crm_opportunity_line_item` |
| Quote / QuoteLineItem | `crm_quote` / `crm_quote_line_item` |
| Contract | `crm_contract` |
| Case | `crm_case` |
| Campaign / CampaignMember | `crm_campaign` / `crm_campaign_member` |
| Product2 | `crm_product` |
| Task / Event | `crm_task` / `crm_event` |
| User | 用户 *（按邮件匹配，或发出邀请）* |

**这些一样都没有落地。** 应用里没有迁移向导，没有 Salesforce 连接器，也没有任何一个会去读 Salesforce 的操作。源码里提到 Salesforce 有十来处，每一处都是把它当作业界设计参照来引用的注释——预测分类阶梯、首次响应时间的定义、Lightning 风格的记录页版面，以及导入映射里那条关于「Salesforce 导出会写哪些词汇」的说明。

也没有对外的 OAuth。Setup 的 **OAuth 应用** 界面登记的是调用*进入* ObjectStack 的客户端；产品里没有任何东西负责让 HotCRM 去*向别人的组织*取得授权。

它甚至也不在路线图上：路线图那一行写的是 *「更多连接器 —— Slack、Microsoft Teams、Google Workspace、HubSpot 导入」*。

**今天该怎么做。** 从 Salesforce 导出 CSV，用上文的导入把它装进来。随附的映射已经会说这门方言的一部分——*SaaS* 与 *Financial Services* 会变成 *Software / SaaS* 与 *Finance*，*Trade Show* 变成 *Event / Trade Show*，*Client* 变成客户类型的客户——所以客户、联系人与潜在客户这一段，通常只需要正确的表头行。没有随附映射的对象，走向导里的手工列映射，或者走数据 API。

## 从 HubSpot 迁移（尚未落地）

同样的情况，但有一点不同：**HubSpot 导入是路线图上点名的一项**，所以这一条是排上了日程，而不只是一个愿望。

| HubSpot | HotCRM 对应项（设计意图） |
| --- | --- |
| Company | `crm_account` |
| Contact | `crm_contact` |
| Deal | `crm_opportunity` |
| Ticket | `crm_case` |
| Line item | `crm_opportunity_line_item` |
| Product | `crm_product` |
| Quote | `crm_quote` |

交易管道会映射到商机阶段，那是最值得手工审阅的一处映射。在它落地之前，上文的 CSV 路线就是迁移路径。

## 迁移操作手册

依然是对的建议——只是现在它是关于 CSV 这条路的建议。

1. **先把用户建好。** 导入器从不创建用户，而一个匹配不到任何人的所有者邮件单元格会让该行失败。先把用户装进 HotCRM（或者清空所有者列、导入后再分配），然后再做别的。
2. **按依赖顺序装载**——先客户，再联系人，最后潜在客户。每个联系人都要指名一个必须已经存在的客户。除这三者之外也守同一条原则：指向别人的记录排在后面。
3. **写入前先校验**，每次都做。向导里的*校验数据*，API 上的 `dryRun`。报告里的 `row` 就是你文件里的行号，改好表格再跑一遍即可。
4. **核对数量**——源系统的总数与 HotCRM 的总数对一对，有差距就去查。
5. **手工端到端抽查十条记录。** 数量对上，不等于字段都落对了。
6. **动手前先弄清你的撤销窗口。** 撤销是按作业来的，而且覆盖不了大作业，所以如果你要这层保险，就把大数据集分块导入。

## 导出数据

### 从列表视图导出

有五个列表视图声明了 `exportOptions: ['csv', 'xlsx']`——**客户**、**联系人**、**潜在客户**、**商机** 与 **工单**。打开其中之一，用工具栏的**导出**，选 CSV 或 Excel。你拿到的就是你正在看的那个视图：它的筛选、排序与列都会随导出一起走。

### 谁可以导出

导出是一项独立权限，不是「能读」的副产品。`allowExport` 是选择性开启的，未设置即**拒绝**；`viewAllRecords` 与 `modifyAllRecords` 都不能替代它。HotCRM 按角色逐一编写了这些授权：

| 角色 | 可导出的对象 |
| --- | --- |
| 销售代表 | 潜在客户、客户、联系人、商机、工单 |
| 销售经理 | 潜在客户、客户、联系人、商机、工单 |
| 客服专员 | 潜在客户、客户、联系人、工单 |
| 营销用户 | 潜在客户、客户、联系人、商机 |
| 系统管理员 | 潜在客户、客户、联系人、商机、工单 |
| 访客门户 | 没有，这是刻意的 |

授权只是打开那扇门，它不会放宽行范围。导出是从读派生的，因此记录范围与共享规则仍然叠加在上面——一个销售代表导出商机，拿到的是自己那本账，而不是全公司的。

报表在这里不是导出面——报表页渲染它的图表与表格，不提供下载。角色可以导出的每一个对象，背后都有一个带**导出**按钮的列表视图；按钮与下文的数据 API 是同一扇门，两边都由服务端把关。

### 通过数据 API 导出

列表视图上的**导出**按钮调用的就是该对象的导出路由，你也可以自己调用它：格式为 `csv`、`xlsx` 或 `json`，并可带 `fields`、`orderby`、`filter`、`search` 与 `limit`。或者用 ObjectQL 查询该对象并分页取回。路由形态请按你所运行的版本、以及身份验证方式，参见 [API 参考](/zh-Hans/docs/customization/api-reference)。

### 定时导出到数据仓库（尚未落地）

设计意图是这样的：选择对象、字段、筛选条件、计划与目标位置；把文件以 CSV、Parquet 或 JSON Lines 落到 S3 / Azure Blob / GCS / SFTP；首次之后转为增量。

这些一概不存在——没有定时导出界面，没有数据仓库目标位置，没有 Parquet 写出器，也没有 `设置 → 数据` 菜单来承载它。今天要么从列表视图手工导出，要么把导出路由挂到你自己掌控的调度上——一个 cron 作业、一个 Lambda、一个 GitHub Action。参见[集成](/zh-Hans/docs/guides/integrations)。

## 数据删除请求（尚未落地）

设计意图是这样的：`设置 → 隐私 → 数据主体请求`，按邮件或联系人 id 识别该人，看到与他关联的全部内容，选择**删除**或**匿名化**（姓名与邮件替换为 `[redacted]`，记录保留以供分析），并交给客户一份审计证书。

这些一概不存在。Setup 里没有隐私分组，没有数据主体请求对象，没有匿名化操作，也没有审计证书——平台的审计能力并不在本应用启用的那批能力里。

今天你能做的，是直接删除或编辑记录：

- **删除该联系人。** 指名这个人的参会人行会随之删除；会议本身保留，因此团队的历史不会因此出现空洞。
- **删除该客户**，它的联系人会级联删除。先看清还有什么挂在它下面——这条级联值得事先规划，而不是事后发现。
- **手工匿名化**：在你要保留的那条记录上清空可识别字段。没有一键等价物，末尾也不会产出任何证书。

## 备份与灾难恢复

备份行为取决于 HotCRM 的托管方式：

- **SaaS** —— 备份由平台管理（通常每日快照，30 天保留期）。
- **自托管** —— 由你负责；备份数据库和文件存储桶。请参阅 [管理 › 设置](/zh-Hans/docs/administration/setup) 了解推荐的频率。

要获取经过测试的**灾难恢复**操作手册，请参阅 [参考 › 安全与合规](/zh-Hans/docs/reference/security-and-compliance)。

## 提示

- ✅ **每次导入前都先校验**——向导里的*校验数据*，API 上的 `dryRun`。它只花几秒钟，却是挡在「一列写错」和「五万行」之间的唯一一道东西。
- ✅ **按依赖顺序装载**——先客户，再联系人，最后潜在客户。
- ✅ **让业务键去做去重。** 不要自己发明 `external_id` 列；重跑同一个文件本来就是更新而不是重复创建。
- ✅ **大批量导入前先确认撤销窗口**，如果你要这层回滚保险，就把文件分块。
- ✅ **谨慎授予 `allowExport`**——它之所以是选择性开启的，正因为它是批量外流，数据会跟着人一起离开。
- ✅ **把每一个 *（尚未落地）* 小节当作需求文档来读，而不是配置指南**——并关注[路线图](/zh-Hans/docs/whats-new)。
