# 自动化

自动化让 HotCRM *为你完成工作* —— 发送通知、更新字段、创建任务、升级案例，全程无需任何人点击按钮。提供四种自动化，每一种都适用于不同的工作。

> **HotCRM 如何实现它们：** 验证与字段逻辑以 **对象钩子**（`beforeInsert` / `beforeUpdate`）运行；所有多步骤、定时或审批类逻辑以 **流程** 运行；审批则是 **流程中的 `approval` 节点**（ADR-0019），而非独立的审批流程类型。独立的工作流规则与审批流程元数据在平台上同样不存在 —— ADR-0019 与 ADR-0020 已移除这两种类型。

## 四种类型

| 类型 | 触发时机 | 最适合 |
| --- | --- | --- |
| **验证规则** | 保存前 | 拦截不良数据 |
| **流程** | 屏幕、记录变更或按计划 | 多步骤逻辑、分支、循环、等待、审批 |
| **计划作业** | 按计划 | 每日清扫、每周报表 |
| **审批流程** | 流程中（approval 节点） | 带记录锁定的多步骤签核 |

## 验证规则

最简单的类型。当某个条件为真时，它们会阻止保存。

**内置示例**：

- *“结束日期必须晚于开始日期”*（用于合同）。
- *“标价必须大于零”*（用于产品）。
- *“营销活动成员必须有一个潜在客户或一个联系人，但不能两者都有”*（用于营销活动成员）。
- *“折扣百分比必须介于 0 和 100 之间”*（用于报价行项目）。

要添加一条：

1. **设置 → 对象 → 验证规则 → 新建**。
2. 编写条件（*失败* 条件）。
3. 编写向用户显示的错误信息。
4. 激活。

## 流程（多步骤）

> **在找「工作流规则」？** 没有可找的东西 —— 本应用没有，平台上也没有。ObjectStack 已退休独立的工作流规则类型（ADR-0019 / ADR-0020）：不存在 `workflow` 元数据类型，stack 上没有 `workflows` 集合，**设置 → 自动化** 下也没有 *工作流规则* 入口，只有 *流程*。所谓「这条记录一保存就做某事」的规则就是 **记录变更类流程**，本应用发布的每一条都在下表中占一行。

当单纯的字段更新不够用时 —— 分支、循环、等待、跨对象写入、审批 —— 使用 **流程**。流程是一张可视化的节点图：获取数据 → 判断 → 创建/更新记录 → 通知 → 等待 → 调用子流程。

流程有三种触发方式，由起始节点决定：

- **屏幕（Screen）** —— 从按钮/操作手动启动，在屏幕上收集输入。
- **记录变更（Record change）** —— 在记录插入/更新时触发（`record-after-create` / `record-after-update`）。
- **计划（Schedule）** —— 按 cron 计划运行。

> **自动触发需要 `triggers` 能力。** 记录变更与计划类流程，只有当 stack 的 `requires` 列表包含 `triggers` 时才会触发 —— 它会安装记录变更与计划触发器提供方（计划触发器还依赖 job 服务）。屏幕类流程始终为手动启动。

**HotCRM 中的内置流程**（26 个）。每一行用的都是流程自身的标签 —— 也就是你在 **设置 → 流程监控器** 与 **设置 → 计划作业** 里看到的名字，因此监控器里的一次运行可以逐字回到这张表里查：

| 流程 | 触发 | 它做什么 |
| --- | --- | --- |
| **线索转化流程** | 屏幕 | 将合格潜在客户转化为客户 + 联系人（+ 可选商机），然后通知 |
| **由商机生成报价** | 屏幕 | 从商机生成报价，并将其推进到 *Proposal* |
| **安排跟进** | 屏幕 | 在线索上创建下一个跟进任务，并已挂好关联与负责人 |
| **将线索登记进营销活动** | 屏幕 | 批量把符合条件的线索登记进本营销活动，跳过已登记与已退订的 |
| **升级案例** | 屏幕 | 收集升级原因，然后标记案例并调整其优先级 |
| **关闭案例** | 屏幕 | 收集处理结论，然后关闭案例并停掉 SLA 计时 |
| **新线索路由与 SLA** | 记录变更（插入） | 按评级写入跟进 SLA，并提醒新线索的负责人 |
| **联系人欢迎** | 记录变更（插入） | 新建联系人后，提醒负责人去做首次问候 |
| **紧急任务提醒** | 记录变更（插入） | 任务以 *Urgent* 创建时通知其负责人 |
| **大额商机审批** | 记录变更（更新） | 通过 approval 节点分级签核 —— 销售经理 > $100K，销售总监 > $500K |
| **大额商机审批（新建时）** | 记录变更（插入） | 同一套受理逻辑，用于*创建时*金额已超过阈值的商机 |
| **大额商机赢单提醒** | 记录变更（更新） | 金额超过 $100K 的商机转为 *Closed Won* 时，通知负责人 —— 只通知负责人本人，不通知其经理 |
| **计费交接：赢单** | 记录变更（更新） | 商机转入 *Closed Won* 的那一刻，向计费端点投递一次带重试的 POST：商机 + 客户 + 行项目 |
| **计费交接：合同激活** | 记录变更（更新） | 合同转入 *Activated* 的那一刻，向计费端点投递一次带重试的 POST：合同 + 客户 + 来源商机的行项目 |
| **案例升级流程** | 记录变更（更新） | 当案例变为 *Critical* 时，标记为已升级并通知其负责人 —— 不会重新分配给资深客服，案例仍归原负责人；升级同时会给客户负责人创建一条紧急跟进任务 |
| **案例升级流程（新建时）** | 记录变更（插入） | 同一套升级逻辑，用于*创建时*就是 *Critical* 的案例 |
| **案例满意度回访** | 记录变更（更新） + 等待 | 案例关闭后等待 1 天，再提醒负责人收集满意度评分 |
| **合同自动到期** | 计划（每日 0 点） | 将已激活且超过 `end_date` 的合同置为到期，并通知负责人 |
| **报价自动过期** | 计划（每日 1 点） | 将超过 `expiration_date` 且仍未关闭的报价置为过期 |
| **营销活动自动完成** | 计划（每日 2 点） | 将 `end_date` 已过的进行中营销活动标记为 *Completed* |
| **预测快照** | 计划（每日 3 点） | 为每位活跃商机负责人写入本季度预测行 —— 管道、最佳情况、承诺与已成交金额 |
| **停滞商机提醒** | 计划（每日 7:30） | 提醒负责人关注在某阶段停留过久的未结商机 |
| **合同续约提醒** | 计划（每日 8 点） | 为临近 `end_date` 的合同开出续约任务/商机 |
| **案例 SLA 监控** | 计划（每小时） | 标记并升级超过 SLA 到期时间的未结案例 |
| **任务到期提醒** | 计划（每小时） | 通知负责人：其任务的提醒时间已到 |
| **演示数据引导** | 计划（每 10 分钟） | 为首位用户认领无归属的种子记录，写入其 `owner_id` |

有两组条目带 **（新建时）** 孪生流程。记录变更类流程每条只订阅一种触发类型 —— `record-after-create` *或* `record-after-update` —— 所以「新建与后续修改都要管」的自动化会被写成条件相同的一对流程。它们在这里各占一行，因为在流程监控器里它们就是两次独立运行。

**演示数据引导** 属于脚手架，而非业务自动化。种子写入会绕过安全中间件，因此种子记录落地时没有负责人 —— 这会让所有「我的 …」视图变空，并让所有寄给负责人的通知无人可达。这条清扫把它们写到首位用户名下。在记录本就有负责人的组织里，它每十分钟选中零条记录、什么也不做。

流程内的通知由 **`notify` 节点** 投递（通过消息服务发送站内信 + 邮件）—— 而非旧的 `script`/邮件步骤（在 7.4 中已是空操作）。

如果你需要构建新的流程，请参见 [自定义 › 扩展对象](/zh-Hans/docs/customization/extending-objects)。

## 计划类自动化

基于时间的自动化以 **计划类流程** 实现 —— 即起始节点带 cron 计划的流程。上表中九个 `计划` 行就是全部；不存在另一套需要另找的「计划作业」元数据。它们通过 job 服务运行，因此 `triggers` 能力需与 `job` 搭配（两者都在默认能力集中）。

无需编排的日期驱动字段逻辑 —— 例如为报价设置默认过期日、冻结已过期/已接受的报价、推导预测周期 —— 放在轻量的 **对象钩子**（`beforeInsert` / `beforeUpdate`）中，而非计划清扫。

预测这一块的分工值得单独点出来，因为它正是要照抄的模式：**预测快照** 流程决定*谁*会拿到快照、*各项合计是多少*，而预测对象的钩子决定*这条快照属于哪个日历周期*。一条 cron 计划说得出「每晚」，却说不出「本季度的第一天」—— 所以这个周期边界由对象统一推导一次，供每个写入方共用。

## 审批

自 ObjectStack 7.4 起，审批被建模为 **流程中的 `approval` 节点**（ADR-0019），而非独立的审批流程类型。进入节点时会创建审批请求、在该步骤待批期间 **锁定记录**、将实时状态镜像到 `approval_status` 字段，并沿 *approve* / *reject* 分支继续。

HotCRM 内置的 **商机审批** 流程串联两个 approval 节点实现分级签核（经理 → 总监）。关于阈值、审批人所见以及审计轨迹，参见 [收入 › 审批](/zh-Hans/docs/revenue/approvals)。

## 操作顺序

当一条记录被保存时，顺序是固定的：

1. **系统** 运行自动计算（公式字段、自动编号）。
2. **验证规则** 运行 —— 如果有任何失败，保存被阻止。
3. **记录被保存** 到数据库。
4. **流程触发器** 触发 —— 视本次保存而定，是 `record-after-create` 或 `record-after-update`。
5. 这些流程内的 **`notify` 节点** 将站内信与邮件排入队列。

流程自身的写入也是普通保存，因此它们会重新进入上面这份顺序，并可能触发更多流程。没有可依赖的固定重评估次数：引擎用 **重入守卫** 打断自触发环 —— 若某条流程在上一次运行尚未结束时又因 *同一条记录* 被重入，这次会被跳过，并记一条警告日志。请把每条记录变更类流程的起始条件写到能自行止住对自身写入的再触发；守卫是兜底，不是停止条件。

理解这个顺序有助于调试 *“为什么我的流程没有触发？”* 这类问题。

## 电子邮件模板

大多数自动化操作会发送电子邮件。模板位于 **设置 → 电子邮件模板**，并支持：

- **合并字段** —— `{{path.to.value}}` 占位符，按每次发送传入的 `data` 载荷渲染。路径的每一段都写 HotCRM 自己的拼写 —— 对象是 `crm_opportunity`、`crm_contact`，字段是 `name`、`owner_id`、`email` —— 而不是 Salesforce 式的 `Opportunity.Name`。路径从哪一层写起，取决于发送方传入的载荷形状；本应用没有任何 `sendTemplate()` 调用方可供照抄，所以请把模板要读的名字声明在它的 `variables` 列表里，并与发送方约定好载荷形状。
- **条件块** —— 仅在条件为真时显示。
- **HTML + 纯文本** 版本。
- **附件** —— 报价 PDF、合同 PDF。

HotCRM 自身不发布任何邮件模板：`src/` 下没有编写任何一条，编译产物里也不含邮件模板元数据。潜在客户路由、商机赢单、案例处理与续约提醒的通知，都由上表那些流程里的 **`notify` 节点** 发出 —— 标题与正文直接写在各自的流程里，要改措辞就去改那里。合同激活不发任何通知：它由对象钩子（`src/objects/contract.hook.ts`）执行，链路上没有通知步骤；真正发出的合同邮件来自 **合同自动到期** 与 **合同续约提醒** 两条流程。需要自己发模板化外发邮件时，再到 **设置 → 电子邮件模板** 里新建模板。

## 在哪里监控自动化

- **设置 → 流程监控器** —— 过去 24 小时的自动化运行及其成功/失败。
- **设置 → 计划作业 → 历史** —— 每个计划作业的过往运行。
- **对象 → 审计日志** —— 记录上发生了什么变化，谁/什么进行了变更。

## 给管理员的提示

- ✅ **验证规则** 是强制数据质量最廉价的方式 —— 放开手用。
- ✅ **每个条件一条流程** 比有 10 个分支的超级流程更易于维护。
- ✅ 只要超出单个字段写入 —— 分支、跨对象写入、等待、审批 —— 就该放进 **流程** 而非对象钩子：流程的每次运行在流程监控器里看得到，钩子代码看不到。
- ✅ 在生产中激活前 **在沙箱中测试** —— 糟糕的自动化会快速级联。
- ✅ 在描述字段中 **记录每条规则的作用** —— 未来的你会感谢现在的你。

## 给用户的提示

如果一条记录的行为不符合预期：

1. 检查 **审计日志** —— 该字段是被流程或对象钩子更新的吗？
2. 检查 **任务列表** —— 是否有流程自动创建了一个你错过的任务？
3. 请管理员检查该记录的 **流程监控器**。
