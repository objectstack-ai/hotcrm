# Plugin Architecture

HotCRM itself is not a plugin — it is a **stack** (an application). The runtime's plugin concept refers to the **platform services** it loads alongside your stack: auth, sharing, automation, AI, UI shells, drivers, and so on.

## Who loads what

```
objectstack dev
   │
   ▼
@objectstack/cli reads objectstack.config.ts
   │
   ├── Reads stack.requires = ['ai', 'automation', 'analytics', 'auth',
   │                            'ui', 'approvals', 'sharing']
   │
   ▼
For each capability, the CLI looks up its provider plugin
   ── 'auth'       → @objectstack/plugin-auth
   ── 'ui'         → @objectstack/studio + @objectstack/console + @objectstack/account
   ── 'ai'         → @objectstack/service-ai
   ── 'automation' → @objectstack/service-automation
                     + node packs (crud, logic, http, screen)
   ── 'analytics'  → @objectstack/service-analytics
   ── 'approvals'  → @objectstack/service-approvals
   ── 'sharing'    → @objectstack/service-sharing
   │
   ▼
Plus the always-on slate auto-injected for any non-`minimal` preset:
   queue, job, cache, settings, email, storage, audit, i18n,
   metadata, ObjectQL, RestAPI, Dispatcher, HonoServer, Security
   │
   ▼
Runtime.start()
   ├── plugin.init()   for each plugin (in dependency order)
   ├── plugin.start()  for each plugin
   ├── kernel:ready fires → hooks register, automation pulls flows
   └── HTTP server listens on $PORT (default 3000)
```

A typical dev run loads **~29 plugins**. You can see the list in the dev banner.

## What HotCRM contributes

The HotCRM stack itself appears as a single plugin (`com.example.crm`). Its `manifest` is declared in `objectstack.config.ts`:

```ts
manifest: {
  id: 'com.example.crm',
  namespace: 'crm',
  version: '0.1.0',
  type: 'app',
  name: 'Enterprise CRM',
},
```

Everything else — objects, hooks, pages, flows — is just metadata fields on the same stack object. The runtime treats the stack as one "app plugin" and registers its content against:

- `ObjectQL` — for objects + data
- `RestAPI` / `Dispatcher` — for actions
- UI shells — for pages, views, dashboards
- `AutomationServicePlugin` — for flows
- `ApprovalsServicePlugin` — for approval processes
- `SharingServicePlugin` — for sharing rules + role hierarchy
- `AIService` — for agents + skills

## Explicit vs. implicit plugins

You generally do **not** pass `plugins: [...]` to `defineStack`. Doing so disables the capability resolver and forces you to hand-instantiate every service plugin (used only for very minimal stacks or custom embeddings).

The supported way is `requires: [...]`. The CLI's `CAPABILITY_PROVIDERS` map (in `@objectstack/cli/src/commands/serve.ts`) is the authoritative list of capability → plugin bindings.

## Driver plugins

Storage drivers are separate plugins picked by `OS_DATABASE_URL` (or `defaultDatasource` in the stack manifest):

| URL prefix | Plugin |
|---|---|
| `file:` / unset | `@objectstack/driver-sql` (better-sqlite3) |
| `postgres://` | `@objectstack/driver-sql` (pg) |
| `mongodb://` | `@objectstack/driver-mongodb` |
| `libsql://` / Turso | `@objectstack/driver-turso` |
| `memory:` | `@objectstack/driver-memory` |

Only the driver matching the URL is loaded. Switching databases is a config change, not a code change.

## Hook execution

Hook handlers (e.g. `account_protection`) run inside a **QuickJS sandbox** managed by the ObjectQL plugin. Inside the sandbox, handlers receive a `ctx` with `input`, `api` (CRUD), `log`, and `crypto`. Handlers must not capture variables from module scope or use `console` — only the explicitly provided `ctx.*` interface.

This isolation is what allows hooks to be compiled into the artifact and re-executed safely in any deployment without re-loading source code.

## Adding a new platform capability

If you need a new platform-level capability (say, fulltext search), the path is:

1. Author a plugin in `framework/packages/plugin-yourthing` that implements the runtime's `Plugin` interface.
2. Publish it under `@objectstack/plugin-yourthing`.
3. Either register it in your stack's `requires` (after adding it to the CLI's `CAPABILITY_PROVIDERS`), or pass it explicitly via `plugins: [YourThingPlugin]`.

HotCRM itself never authors platform plugins — that's the framework's job. HotCRM only consumes them.

## Reference

The full plugin lifecycle, capability registry, and inter-plugin event bus are documented in the ObjectStack framework repository under `packages/runtime/`. HotCRM-specific behaviour is limited to the metadata it declares; everything else is platform.
