# 状态机

某些对象有严格的 **生命周期** —— 潜在客户从 *New* 推进到 *Working* 再到 *Qualified*，绝不会倒退回 *New*。状态机把这条路线 **声明** 出来，但并不强制执行：本应用的五条状态机全是 **警告** 级，用户把记录挪出这条路线，**保存照样通过** —— 详见下文《声明出来的路线是建议，不是闸门》。

## 状态机在哪里适用

HotCRM 在 **五个** 对象上使用状态机：

- **潜在客户** —— *New → Working → Qualified → Converted / Disqualified*
- **商机** —— 经过 7 个阶段 *Prospecting → Qualification → Proposal → Negotiation → Closed Won / Closed Lost / Closed Without Decision*
- **案例** —— *New → In Progress → Resolved → Closed*；*Waiting on Customer* 与 *Waiting on Support* 用来把未结案的案例挂起，*Escalated* 从任何未解决的状态都能进入，*Resolved* 与 *Closed* 都可以重新打开回 *In Progress*
- **合同** —— *Draft → In Approval → Activated → Expired*；*In Approval* 可以把文件退回 *Draft*，三种在途状态都能直接走到 *Terminated*，*Expired* 与 *Terminated* 都是终点
- **报价** —— *Draft → In Review → Presented → Accepted*；*In Review* 可以退回 *Draft*，*Rejected* 会回到 *Draft* 重来，*Expired* 可从 *Draft*、*In Review*、*Presented* 进入，*Accepted* 与 *Expired* 都是终点

五者的声明方式完全相同 —— 都是对象上一条具名的 `state_machine` 验证规则，作用于该对象的生命周期字段（`status`，商机上是 `stage`）。案例、合同、报价用的不是比潜在客户和商机更轻的机制，就是同一套机制。顶层 `stateMachines` 键在平台 7.7 被移除后，所有状态机都迁到了各自的对象上。

**声明出来的路线是建议，不是闸门。** 五条规则都是 **警告** 级：走出转换表的状态变更只会写进服务端日志——比如 *“Invalid contract status transition”*——而 **保存照样通过**。记录在 **新建** 时也根本不受检查：规则拿新值与前一个值比对，因此只在更新时运行，直接导入到后期状态的记录不会被碰。转换表给你的是一条声明出来、机器可读的路线，供自动化、报表和 Copilot 依赖——而不是给字段上锁。

**营销活动没有状态机，这是有意的。** 营销活动的状态是描述性的（*Planning / In Progress / Completed / Aborted*），不是受控的生命周期；营销活动成员、活动、知识文章和任务的状态字段同理。给它们中任何一个加转换表，只会在正常编辑时报警告，教用户忽略警告。

## 潜在客户状态机

```
        ┌──────────────┐
        │     New      │
        └──────┬───────┘
               │ Begin working
               ▼
        ┌──────────────┐
        │   Working    │
        └──┬────────┬──┘
   Disqual │        │ Qualify
           ▼        ▼
   ┌────────────┐  ┌────────────┐
   │Disqualified│  │ Qualified  │
   └────────────┘  └─────┬──────┘
                         │ Convert
                         ▼
                  ┌────────────┐
                  │ Converted  │
                  └────────────┘
```

**允许的转换**：

| 从 | 到 | 触发 |
| --- | --- | --- |
| New | Working | 手动（“Begin Working”）或首次活动时自动更新 |
| Working | Qualified | 手动（“Mark Qualified”） |
| Working | Disqualified | 手动（“Disqualify”），需填写原因 |
| Qualified | Converted | 转化向导（创建客户/联系人/商机） |
| Disqualified | （终态） | — |
| Converted | （终态） | — |

**不允许**：从 *New* 直接跳到 *Converted*；将 *Converted* 退回到 *Working*。

## 商机状态机

```
Prospecting → Qualification → Proposal → Negotiation
                                              │
                            ┌─────────────────┼────────────────────────┐
                            ▼                 ▼                        ▼
                        Closed Won      Closed Lost        Closed Without Decision
```

**规则**：

- 你可以自由地 **向前** 经过 *Prospecting → Qualification → Proposal → Negotiation*。
- 你可以 **向后** 移动（例如从 *Negotiation* 退回 *Proposal*）—— 有时交易会滑落。
- 从任何开放阶段，你都可以移动到三个 **已关闭** 阶段之一。
- 一旦 *Closed*，商机的金额/阶段编辑就被 **锁定**（除非重新打开 —— 仅限管理员）。

系统还强制执行：

- 移动到 *Proposal* 之前 **必须填写关闭日期**。
- 移动到 *Negotiation* 之前 **必须填写金额**。
- 进入 *Closed Lost* 或 *Closed Won* 时 **必须填写赢单/丢单原因**。
- 如果金额 > $500K 且尚未授予折扣审批，进入 *Closed Won* **可能需要审批**。

## 状态机给你的是什么

不是拦截。本节原先列为「不会发生」的几件事，在转换表声明之后照样发生：代表仍可能不小心把潜在客户标记为 *Converted*，商机仍可以从 *Prospecting* 直接跳到 *Closed Won*，记录仍会跳过阶段。这些写入各自只在服务端日志里留下一条警告，然后照样落库。所以漏斗报表并不会因为存在一张表就 **反映现实** —— 它报的是记录实际走过的那些阶段。

转换表真正给你的，就是这条路线本身 —— **写在一个机器能读的地方**：

- **生命周期只有一处定义。** 评审者、报表作者、为本应用编写元数据的 AI，都能直接从对象上读到设计意图中的路线，而不必从每一条写这个字段的流程和钩子里去反推。
- **非法的移动会被报出来，而不是无声无息。** 移动照样落库，但引擎会在日志里点名 —— *「Invalid opportunity stage transition」*，并带上规则自己的名字 —— 所以一次糟糕的导入或一个行为异常的集成，事后是能被找出来的。走在表内的移动一条日志都不记，这正是那些警告值得一读的原因。
- **给自动化与报表一个可以指向的基准。** 流程条件、报表或技能可以按声明出来的路线来写，而不是把一串状态手工抄过去。

如果你需要某个状态变更真正不可能发生，状态机不是那个工具：能挡下保存的是 `error` 级的验证规则。这五条保持建议级是有意的 —— 理由就写在规则自己身边（`src/objects/quote.object.ts`）：售后的更正不该还要靠一次数据修复才能做到。

## 自定义状态机

管理员可以：

- **添加新状态**（例如为营销跟进添加 *Lead status = Nurturing*）。
- **移除转换**（例如禁止在商机阶段中向后移动）。
- **添加进入条件**（例如 *没有决策者联系人角色就不能进入 Proposal*）。
- **添加退出条件**（例如 *没有更新关闭日期就不能离开 Negotiation*）。
- 在每次转换时 **触发自动化**（对象钩子、流程、通知）。

上面这些都是改源码，不是在设置里点几下：**并不存在「设置 → 对象 → 状态 → 状态机」这个配置面**。每张转换表都是对象上的一条 `validations[]` 条目（类型 `state_machine`，见 `src/objects/*.object.ts`），而这条条目只带一张转换映射表，别的什么都没有 —— 所以上面前两项是改这张映射表，进入/退出条件是另外的 `validations[]` 规则或相关字段上的 `requiredWhen` 谓词，按转换触发自动化则是 `record_change` 流程或对象钩子。每一项都是代码改动加一次重新部署。

## 用户看到什么

- **状态下拉菜单不会被过滤。** 无论记录当前处于什么状态，它都列出该字段声明的全部选项。平台 *能* 算出合法的下一批状态 —— `@objectstack/objectql` 里的 `legalNextStates`，通过 `GET /objects/{name}/state/{field}?from=…` 可以取到 —— 但本应用没有任何一处调用它，也没有任何列表、表单或详情页按它收窄选项列表。
- **不被允许的转换不会报错，也不会弹窗。** 保存照样通过，记录就停在新值上；唯一的痕迹是服务端的一行日志 —— `WARN Validation rule 'lead_status_progression' (warning): Invalid lead status transition` —— 在界面里工作的人永远看不到它。
- 强制执行新状态的必填字段 —— 用户在保存前内联看到它们。这是另一套机制：字段上的 `requiredWhen` 谓词（例如阶段变为 *Closed Won* 时的 `win_reason`），它确实会拒绝保存。

## 状态机与 AI Copilot

Copilot 理解状态机。在建议操作时：

- *“确认这个潜在客户的资格”* → 仅当状态为 *Working* 时建议。
- *“转化这个潜在客户”* → 仅当状态为 *Qualified* 时建议。
- *“将这个商机标记为 Closed Won”* → 仅当赢单条件满足时建议（金额、关闭日期、赢单原因、必要时的审批）。

这可以防止 Copilot 建议非法的转换。

## 给管理员的提示

- ✅ **不要过度约束** —— 太多转换规则会成为团队的摩擦税。
- ✅ 添加新状态时，**先决定进入和退出条件** —— 其余的自然就有了。
- ✅ 使用状态机转换来 **触发自动化**，而非在每次保存时运行自动化 —— 性能要好得多。
- ✅ 每次变更后 **测试向导流程**（转化潜在客户、关闭商机）。

## 给用户的提示

- 状态下拉菜单从不会因为状态机而少给你一个选项 —— 它根本不过滤这个选项列表。缺了你期望的选项，去看该字段自己的选项配置或你所属配置文件的字段级安全，而不是转换表。
- 不存在 *“绕过状态机”* 这项权限可申请，也没有什么需要绕过。把遗留数据直接导入到后期状态不需要任何授权：**新建** 路径根本不查转换表，更新时走出转换表也是记一条日志然后照样保存。真正该做的是知会管理员一声，好让日志里冒出来的那些警告被认成这次导入，而不是被当成 bug 去追。
