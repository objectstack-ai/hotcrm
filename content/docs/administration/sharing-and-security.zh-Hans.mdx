# 共享与安全

共享回答这个问题：*“这个用户能查看和编辑哪些记录？”* 四个层级叠加在一起给出答案：

1. **对象权限** —— 这个用户到底能不能碰这个对象？（参见[权限档案](/zh-Hans/docs/administration/profiles)。）
2. **组织范围默认值 (OWD)** —— 记录级的基线（“商机是私有的”）。
3. **共享规则** —— 各种开口（“EU 团队可以编辑 EU 客户”）。
4. **手工共享** —— 记录级的“你和我一起在跟这一条”。

外加用于遮罩敏感字段的 **字段级安全**。

> 第一层是闸门，不是过滤器。如果权限档案没有授予这个对象，任何 OWD、共享规则或 *查看所有* 设置都无法把记录找回来 —— 请求在触及共享之前就被拒绝了。

## 第 1 层 —— 组织范围默认值

OWD 是每个对象的 *最严格* 设置，其他一切都在此之上放宽。

| 对象 | OWD | 原因 |
| --- | --- | --- |
| 线索 | 私有 | 代表跟自己的线索 |
| 客户 | 私有 | 客户归属很重要 |
| 联系人 | 由父级控制（客户） | 联系人属于它的客户 —— 但今天它实际派生到多大范围，见下面的 *“由父级控制”在实践中* |
| 商机 | 私有 | 敏感的交易数据 |
| 商机行项 | 由父级控制（商机） | 产品行是交易的一部分 |
| 报价 | 私有 | 定价属于所有人 |
| 报价行项 | 由父级控制（报价） | 行项是报价的一部分 |
| 合同 | 私有 | 敏感的商务条款 |
| 工单 | 私有 | 专员的队列是自己的；升级件走共享 |
| 任务 | 私有 | 个人活动条目 |
| 活动 | 私有 | 个人活动条目，与任务同类 |
| 活动参与者 | 由父级控制（活动） | 参与者属于他们参加的那场会议 —— 但今天它实际派生到多大范围，见下面的 *“由父级控制”在实践中* |
| 预测 | 私有 | 快照属于其所有人；经理持有 *查看所有* |
| 产品 | 公共只读 | 所有人都看得到目录 |
| 市场活动 | 公共只读 | 营销创建，销售查看 |
| 营销活动成员 | 由父级控制（市场活动） | 成员关系是市场活动的一个属性 —— 见下面的 *“由父级控制”在实践中* |
| 知识文章 | 公共只读 | 知识库面向全体内部用户；由专员撰写 |

**OWD 的取值**：私有 / 公共只读 / 公共读写 / 由父级控制。

### “由父级控制”在实践中

对于上面五个由父级派生的对象，没有任何按用户配置的东西：访问权限是 *计算* 出来的。

- **读 —— 本版本计算出来的结果是组织范围，而不是按父记录收窄。** “由父级控制”的本意是“你能看到其父记录你能看到的那些行”。今天交付的并不是这个：派生只从 *父对象自身的行级安全策略* 去解析可访问的父记录集合。HotCRM 在这些父对象上只写了一条这样的策略 —— 商机上的私有交易过滤，由 Sales Manager 和 Marketing User 两个权限档案携带 —— 因此对其余每一个父对象、以及每一个不带该策略的调用者来说，父记录集合就是全部记录。对随产品发布的 stack 实测（平台 17.0.0-rc.2）：一个只读得到一个客户的代表，读到了 **两个** 客户的联系人；一个一张报价都读不到的代表，仍然读到了每一张报价的行项。实际效果是：这里的“由父级控制”对象，对每一个权限档案授予了该对象读取权的用户都是可读的。
- **写** —— 新增、修改或移除一行需要对父记录有 **编辑** 权限，而这个父记录是通过与读取相同的过滤解析出来的。所以写入的闸门同样宽：一个对“由父级控制”对象持有编辑权的权限档案，可以写入该对象的任何一行，包括它自己读不到的那些父记录下面的行。

“收窄到可读的父记录”作为平台问题跟踪：objectstack-ai/objectstack#5386。本仓的测试 `test/parent-derived-reach.test.ts` 钉住了上面实测到的可达范围，平台一旦收窄它就会失败 —— 那次失败就是信号：这一节需要重写，HotCRM 的 OWD 取舍也需要重新做一次（#549、#694）。

由于访问是派生的，子记录本身的归属无关紧要 —— 报价生成流程创建的报价行，对报价所有人来说与自己手动录入的一样可见。

## 第 2 层 —— 岗位

**岗位（position）** 是用于分发访问权限的扁平群体。HotCRM 内置十二个：

```
executive
sales_director      sales_manager      sales_rep
service_director    service_manager    service_agent
marketing_director  marketing_manager  marketing_user
na_sales_team       eu_sales_team          （区域分组）
```

岗位 **在设计上是扁平的** —— 没有层级，**什么都不会上卷**。销售总监不会继承销售经理的访问权限；每个需要某条记录的层级都由它自己的共享规则点名。这就是下面若干规则成对出现的原因。

在 **设置 → 用户** 中分配岗位；一个用户可以持有多个。

## 第 3 层 —— 共享规则

共享规则在 OWD 基线之上 **放开** 记录访问。

### 两种形式

| 类型 | 共享什么 | 示例 |
| --- | --- | --- |
| **基于条件** | 匹配某个过滤条件的所有记录 | *“账单国家为 DE/FR/… 的客户”* → 共享给 EU 团队 |
| **基于所有人** | 某个群体拥有的所有记录 | *“SDR 拥有的记录”* → 共享给 AE 群体 |

基于条件的规则是被真正执行的那一种：匹配的记录会实体化为真实的共享授权。

### 内置共享规则

| 规则 | 对象 | 授予 | 给谁 |
| --- | --- | --- | --- |
| Account Team Sharing | 客户 | 编辑 | `sales_manager` —— 活跃的客户型客户 |
| North America Territory | 客户 | 编辑 | `na_sales_team` —— 账单国家为 US/CA/MX 的客户 |
| Europe Territory | 客户 | 编辑 | `eu_sales_team` —— 账单国家为 UK/DE/FR/IT/ES 的客户 |
| Opportunity Sales Team Sharing | 商机 | 读取 | `sales_director` —— 金额 ≥ $100,000 的进行中交易 |
| Large Open Deals — Executive | 商机 | 读取 | `executive` —— 同一批交易，上一层级 |
| Escalated Cases Sharing | 工单 | 编辑 | `service_manager` —— 未关闭的紧急工单 |
| Escalated Cases — Service Director | 工单 | 读取 | `service_director` —— 同一批工单，上一层级 |
| Live Campaigns — Marketing Manager | 市场活动 | 编辑 | `marketing_manager` —— 筹划中 / 进行中的活动 |
| Live Campaigns — Marketing Director | 市场活动 | 编辑 | `marketing_director` —— 同一批活动 |

在 **设置 → 共享设置** 中创建你自己的规则。

> **条件只能过滤普通字段，不能过滤地址的某一部分。** 两条区域规则匹配的是客户上的 **账单国家** —— 一个只读的两位国家代码，由你在 **账单地址** 中填写的国家推导而来 —— 而不是地址本身。条件规则必须以数据库查询的形式运行，而查询无法深入结构化的地址或位置值内部。因此，针对 `账单地址 → 国家` 编写的规则会被**直接拒绝**，而不是被悄悄放宽成"所有客户"：它根本不会被安装，它指定的岗位也就什么都拿不到。界面上不会把这样的规则标记为失效，所以当某个团队反馈记录缺失时，请检查规则里引用的每个字段是否都是该对象上的普通字段。

### 一条规则放开的是一个对象，而不是它下面的记录

共享规则是 **按对象** 编写的。放开 `Account` 只放开客户本身 —— 挂在这个客户下的记录仍然各自守着自己的基线，其中只有联系人是从客户派生的：

| 已共享客户上的相关列表 | 接收者实际看到的 |
| --- | --- |
| 联系人 | 全部 —— 而且不只是这个客户的：Contact 是“由父级控制”，在本版本中派生为组织范围（见上） |
| 商机 | 只有自己的交易；若持有 `sales_director` 或 `executive`，另加金额 ≥ $100,000 的未结交易 |
| 报价 | 只有自己的 |
| 合同 | 只有自己的 |
| 工单 | 只有自己的；若持有 `service_manager` 或 `service_director`，另加未关闭的紧急工单 |
| 任务 | 只有自己的 |
| 活动 | 只有自己的 |

也就是说，区域规则交出的是客户记录；下面的交易、报价、合同、工单、任务和会议历史仍归各自的所有人，用户明明能完整读取这个客户，这些相关列表却可能是空的或残缺的。联系人列表在两个方向上都是例外 —— 它永远不会是空的，因为 Contact 的父级派生触及组织内的每一个联系人，而不只是这个客户的。

让子对象跟随客户是一次有意的放开，而不是一个配置细节：要么在子对象上按与客户规则匹配的条件另写一条共享规则，要么把子对象的 OWD 改成“由父级控制”。两种做法都会对 **所有** 持有该对象的用户放开可见性，而不只是区域规则的接收者 —— 这正是 HotCRM 默认两者都不做的原因。对“由父级控制”来说，无论父级链接看上去是什么意思，今天真正发生的就是这件事：见上面的 *“由父级控制”在实践中*，以及 objectstack-ai/objectstack#5386。

## 第 4 层 —— 手工共享

**手工共享** 在上述一切之上，把某一条记录的 **读取** 或 **读写** 权限授予某个用户或用户组。共享按记录存储。手工共享不会给这条记录下由父级派生的子记录带来任何东西：派生从不把共享授权折算进去 —— 而今天它也不需要，因为那些子记录对每一个持有该子对象读取权的人来说本来就是可读的（见 *“由父级控制”在实践中*）。

HotCRM **不提供客户团队对象** —— 客户上没有团队名单，也没有“团队”页签。上表中那条名为 *Account Team Sharing* 的规则就是一条普通的条件规则：它把活跃客户类账户的编辑权授予每一位 `sales_manager`，而不是按记录组建的小组。以小组方式作战的组织，可以把小组建模为一个岗位并为其编写共享规则，或者在客户上使用手工共享。

## 这些层级如何组合

当以下条件 **全部** 成立时用户才能看到一条记录：其权限档案授予了该 **对象的读取权限**，并且 **以下任意一条** 为真：

1. 他们 **拥有** 这条记录。
2. 其权限档案授予该对象的 **查看所有**。
3. **OWD** 为公共只读或更宽。
4. 该对象是 **“由父级控制”** —— 今天无论父记录对他们是否可见，它都会授予这条记录（见 *“由父级控制”在实践中*）。
5. 某条 **共享规则** 匹配该记录且命中他们的某个岗位。
6. 该记录被 **手工共享** 给了他们。

若都不成立，这条记录只是从列表、搜索和报表中 *消失* —— 而不是给出一条报错。

## 归属与转移

每条记录有且只有一个**负责人（Owner）**。它就是表单上的那个字段、"我的……"视图所过滤的那个字段，也是上面每一条规则说"记录的负责人"时所指的那个字段——一列，一个答案。改动负责人是真正的交接：原负责人立即失去基于归属的访问权，新负责人立即获得，且在所有位置同步生效。

正因为它会移动访问权，**修改负责人是一项独立的权限**，与普通的编辑权限分开：

| 角色 | 可转移的对象 |
| --- | --- |
| 系统管理员 | 全部对象 |
| 销售经理 | 销售簿——线索、客户、联系人、商机、报价、任务、会议、预测 |
| 客服专员 | 仅任务（以便升级时把工作交给客户负责人） |
| 销售代表、市场用户 | 无——记录是被指派给他们的 |

有三类日常操作**不算**转移，因而不需要该权限：

- **新建记录。** 新记录会自动归属到创建者，你无需手动选择自己。
- **保存表单**时未改动负责人——即使表单会把该字段一并提交。
- **自动化代你执行**——分配新线索的轮询、夜间生成续约与跟进任务的批处理。

没有该权限的用户尝试转移时会收到明确的拒绝提示，而不是悄无声息地无效。需要整体移交业务簿时，请联系管理员或你的销售经理。

> **从旧版本升级？** 负责人过去是一个普通字段，任何有编辑权的人都能改——而改动它只会让记录在各种列表和报表里移动，访问权**完全没动**。现在两者是同一个字段。此前显示负责人与实际访问归属已经产生偏离的记录，需要一次性回填对齐；详见发行说明中的回填说明。

### 私有商机

商机上的 `Private` 在上述一切之上生效：用户标记为 **Private** 的交易只对其所有人（以及管理员）可见，即使是像 Sales Manager 和 Marketing User 这类本来持有组织范围商机读取权限的权限档案也看不到。用于董事会级或涉并购敏感的交易。

## 字段级安全 (FLS)

FLS 控制在一条 *可见* 记录内部，某个权限档案能看到和编辑 **哪些字段** —— 例如客户 **健康度评分** 对所有能看到该客户的人可读，但只有销售经理能设置它；而 **工单内部备注** 对销售代表完全隐藏。随产品提供的遮罩清单见[权限档案](/zh-Hans/docs/administration/profiles#字段级安全)。

FLS 在 **所有地方** 生效 —— 列表视图、报表、API 和 AI Copilot。被遮罩的字段也不能用于过滤、排序或分组。

## AI Copilot 的共享

Copilot 代表用户行动 —— 它看到的与用户看到的完全一致，不多一分：

- 对象权限、共享和 FLS 全部自动生效。
- 管理员运行 Copilot 会比代表看到更多 —— 这是设计使然。

不存在“AI 绕过”。

## 给管理员的提示

- ✅ **先检查对象授权。** 空白的相关列表或报错的导航项，几乎总是缺少对象权限，而不是共享问题。
- ✅ **从严开始** —— 线索/客户/商机用私有 OWD，然后用共享规则放开。
- ✅ **记住岗位是扁平的。** 授予经理并不等于授予总监；两者都要写。
- ✅ **每季度审计共享规则** —— 它们会累积。
- ✅ 不要滥用 **查看所有** —— 它是一把绕过所有共享规则的大锤。

## 给用户的提示

如果你认为自己应该能看到某条记录却看不到：

1. 查一下 **谁拥有它**。
2. 如果你是从客户点进去的，先看 **它是哪个对象**：即使客户本身已经共享给你，报价、合同、任务、工单和交易仍归各自的所有人。联系人是唯一从不会被扣下的相关列表 —— Contact 是“由父级控制”，而在本版本中它派生为组织范围，而不是按客户收窄（见 *“由父级控制”在实践中*）。
3. 查一下该交易是否被标记为 **Private**。
4. 询问管理员是否应该有一条 **共享规则** 覆盖你的岗位。
